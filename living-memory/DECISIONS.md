## D-001 — Sleeper as the Sole Identity Provider
**Date:** Pre-changelog (foundational)
**Context:** Need a user-identification mechanism. Dynasty fantasy football is Sleeper-dominated; building separate accounts adds friction.
**Decision:** Use Sleeper username as login. No app-side account creation. Sleeper's public API provides user lookup, league data, and rosters.
**Alternatives considered:** Email/password accounts; OAuth (Yahoo, ESPN, Google).
**Consequences:** Massive UX win (no signup). Hard dependency on Sleeper API. Users without Sleeper accounts can't use the app — acceptable for dynasty focus.
**Status:** Active.

## D-002 — 3-Player Matchups Over 2-Player
**Date:** Pre-changelog
**Context:** Choosing the ranking-interaction primitive. Pairwise comparisons are simplest; full-rank-N is most information-dense per click.
**Decision:** 3-player matchups (rank the 3 in order). Each interaction decomposes into 3 pairwise Elo updates — 2.6× information per swipe vs pure pairwise.
**Alternatives considered:** Pure pairwise (simpler UX); 5-player rank (more info but slower per swipe).
**Consequences:** 2.6× info gain per interaction. Slightly higher cognitive load per swipe. Decomposition keeps Elo math unchanged.
**Status:** Active.
**Related ADR:** consider creating `docs/adr/0001-three-player-matchups.md` if not already there.

## D-003 — Elo Decomposition for 3-Player Rankings
**Date:** Pre-changelog
**Context:** Need an Elo-update rule for 3-player full-rank inputs.
**Decision:** Decompose into 3 pairwise updates per ranking event: rank1>rank2, rank2>rank3, rank1>rank3. Each is a standard Elo update.
**Alternatives considered:** Custom 3-player Plackett-Luce update; Bradley-Terry extensions.
**Consequences:** Reuses standard Elo math. Information theory: each ranking event yields the equivalent of 2.6 pairwise comparisons (vs 1 for pure pairwise). Implementation in `ranking_service.py`.
**Status:** Active.

## D-004 — DynastyProcess CSV as Initial Elo Seed
**Date:** Pre-changelog
**Context:** Need initial Elo ratings for the player base before any user interaction.
**Decision:** Use DynastyProcess GitHub CSV as seed. Mapping: value 10000 ≈ Elo 1800 (elite); value 5000 ≈ Elo 1500 (solid starter); value 0 ≈ Elo 1200 (bench/depth). 660 player rows, 636 with value > 0.
**Alternatives considered:** Other consensus sources (Sleeper trends, KeepTradeCut, FantasyCalc); flat 1500 baseline for all.
**Consequences:** New users get reasonable starting rankings. Hard dependency on DynastyProcess's update cadence and naming conventions. Name mismatches (DynastyProcess ↔ Sleeper) require manual reconciliation via `dump_mismatches.py`.
**Status:** Active. Long-term: evaluate alternative consensus sources or weighted blends.

## D-005 — Anthropic Claude API as Optional Enhancement
**Date:** Pre-changelog
**Context:** Smart matchup selection (picking the most-informative trio) benefits from natural-language reasoning over candidate options.
**Decision:** Use Anthropic Claude API in `smart_matchup_generator.py` when `ANTHROPIC_API_KEY` is set. Fall back to algorithmic selection (tightest Elo cluster) when not.
**Alternatives considered:** OpenAI / Gemini APIs; no AI at all.
**Consequences:** App works fully without an API key. AI is enhancement, not dependency. Per-decision cost is small (~$0.001 with Haiku).
**Status:** Active.

## D-006 — Vanilla Stack for Web Client
**Date:** Pre-changelog
**Context:** Web client choice: framework (React, Vue, Svelte) vs vanilla.
**Decision:** Vanilla HTML/CSS/JS in `web/`. No build step. Files served directly by Flask.
**Alternatives considered:** React (consistency with mobile); Svelte (smaller bundles).
**Consequences:** Trade-off: no component abstraction, more imperative DOM manipulation. Pay-back: zero build tooling, fast iteration, no `node_modules` in `web/`. Mobile diverges intentionally because React Native demands it.
**Status:** Active. Re-evaluate if web UI complexity grows substantially.

## D-007 — SQLite First, Postgres-Swappable
**Date:** Pre-changelog
**Context:** DB choice for personal-use + future-production.
**Decision:** SQLite for local dev (file-based, zero ops). Code uses SQLAlchemy Core with `DATABASE_URL` env var. Switching to Postgres requires only env-var change + smoke test.
**Alternatives considered:** Postgres from day one (more setup); pure JSON files (no querying).
**Consequences:** Easy local dev. WAL mode not enabled — single-process for now. Migration path documented but untested. **Side effect:** the DB file ended up at two paths (`data/trade_finder.db` and `trade_finder.db` at root). Cleanup pending — see [`OPEN_QUESTIONS.md`](OPEN_QUESTIONS.md) Q-001.
**Status:** Active.

## D-008 — In-Memory Ring Buffer Logger (No Log Files)
**Date:** Pre-changelog
**Context:** Need debugging signal without committing to persistent log files.
**Decision:** In-memory ring buffer of last 200 backend events, accessible via `GET /api/debug/log?n=100`. Everything else to stdout.
**Alternatives considered:** Persistent log files (rotated); third-party logging service.
**Consequences:** No disk I/O for logging. Easy forensics during a running session. **Lost on restart** — post-crash forensics is hard. Acceptable for personal-use scale.
**Status:** Active. Reconsider for production.

## D-009 — `docs/` as Source of Truth; Living-Memory Cross-References
**Date:** 2026-05-21
**Context:** Adopting the 17-pattern living-memory layer alongside the existing `docs/` folder. Risk: duplication, conflicting sources of truth.
**Decision:** `docs/` remains authoritative for architecture, schemas, glossary, ADRs, runbook. Living-memory files cross-reference `docs/` rather than duplicating. Specific mappings documented in [`FORMAT.md`](FORMAT.md) §Relationship-with-docs.
**Alternatives considered:** Migrate `docs/` into `living-memory/`; treat `living-memory/` as the new source of truth.
**Consequences:** Two folders to keep in sync — but they have different read triggers and different update cadences (`docs/` = stable reference; `living-memory/` = active state). The `docs/CLAUDE.md` update-trigger table remains authoritative.
**Status:** Active.

## D-010 — Karpathy Four Principles as Coding Discipline
**Date:** Pre-changelog (per [`../docs/coding-guidelines.md`](../docs/coding-guidelines.md))
**Context:** Need a shared discipline for code changes, especially when working with Claude.
**Decision:** Four principles in priority order: (1) Think before coding; (2) Simplicity first; (3) Surgical changes; (4) Goal-driven execution. Bias toward caution over speed; use judgment for trivial tasks.
**Alternatives considered:** No explicit discipline (vibes-only); more granular ruleset.
**Consequences:** Sets the expected posture for every code change. Codified as the project's "engineering brand" — see [`BRAND.md`](BRAND.md).
**Status:** Active.

## D-011 — Fix the Selector, Not the Elo Math
**Date:** 2026-07-09 (`fae6fee`, PR #97)
**Context:** Players never moved across tier boundaries. The obvious suspects were the K-factor and the Elo ceiling.
**Decision:** The *selector* was at fault, not the math. `_algorithmic_trio` picked the tightest uncompared trio within a top-24 seed window, so cross-tier comparisons were literally never asked. Added `_boundary_trio` (pairs a player just below a tier edge with one just above, drawn from the full pool). The Elo math is untouched.
**Alternatives considered:** Raise K; raise the Elo ceiling; ordinal anchor placement (Lever B); K-boost (Lever C) — B and C deliberately deferred unless A proved too slow.
**Consequences:** Tier mobility without destabilizing established ratings. All knobs are DB-seeded `model_config` (`trio_boundary_rate`, `trio_boundary_margin`, `trio_within_tier_rate`, `trio_repeat_avoid`), so `rate=0` is an exact, live-revertible rollback to legacy behavior.
**Status:** Active.

## D-012 — Affine Mapping of the DynastyProcess Scale onto Trade Value
**Date:** 2026-07-12 (`2e9d542`, FB-117/118)
**Context:** Top assets capped around 2.1 firsts, which didn't match how the market actually prices elite dynasty players; a Mid 1st read as 47% of a top asset.
**Decision:** Map the DP scale **affinely** onto trade value — DP 10000 lands on the 4-firsts rung (Elo ~1927). Ladder re-cut to 8 rungs. Value history rescaled by a marker-guarded idempotent migration.
**Alternatives considered:** Rescaling the ladder only (leaves the underlying curve wrong); a non-linear fit (harder to reason about and to revert).
**Consequences:** Top assets read 3.6–4.0 firsts; Mid 1st ~25% of a top asset. `top_tier_firsts` default moved 2→4 with defaults byte-identical, and fairness golden pins were unchanged — so the recalibration is provably value-scale-only.
**Status:** Active.

## D-013 — Blend External Value Sources onto the DP Curve, Never Replace It
**Date:** 2026-07-18 (`71e1a61`, FB-145)
**Context:** KTC is a second consensus source. Swapping to it wholesale would silently move every user's board.
**Decision:** Rank-normalize KTC onto the existing DP curve and blend at `ktc_blend_weight=0.5`. Weight 0 is a DP-only kill switch. The scrape is fail-soft.
**Alternatives considered:** Replace DP with KTC; run them as a user-selectable source (more surface, more support burden).
**Consequences:** One tunable knob and an instant rollback path. The curve shape stays DP's, so downstream calibration (tiers, fairness gates) holds. Same pattern later reused for `tep_te_uplift=1.18`, which exists because DP's `value_2qb` carries no TE uplift.
**Status:** Active.

## D-014 — Two-Stage Layered Experiment Bucketing
**Date:** 2026-07-18 (`877fc91`)
**Context:** Concurrent experiments must not silently interact.
**Decision:** Two independent hashes — `layer_bucket = HMAC(salt : unit)` then `variant_bucket = HMAC(salt : key : version : unit)`. This guarantees mutual exclusivity within a layer while keeping variant assignment independent across layers.
**Alternatives considered:** Single-hash assignment (cheaper, but no exclusivity guarantee); a manual do-not-overlap registry (doesn't scale).
**Consequences:** `EXPERIMENT_SALT_KEY` is **immutable once assignments exist** — changing it rebuckets everyone. See [GOTCHAS G-019](GOTCHAS.md). Statistics are deliberately scipy-free (`backend/analytics_stats.py`), pinned by `stats_golden.json`, to avoid the dependency.
**Status:** Active.

## D-015 — Derive Model State on Read Rather Than Materializing It
**Date:** 2026-07-26 (`e8385ac`, Thompson v2)
**Context:** Thompson v2 needed per-arm posterior state for archetype×shape arms.
**Decision:** Derive arm state on read from the F1 impression tables instead of materializing it. No schema change, and v1 behavior stays byte-identical.
**Alternatives considered:** A materialized arm-state table (faster reads, but a migration plus a second source of truth to keep consistent).
**Consequences:** Rollback is a flag flip with no data to unwind. The same read-time principle was applied to cross-format board derivation (`a8898a7`) — never materialized, explicit rows always win.
**Status:** Active.

## D-016 — A Model Ships Dark Until It Passes an Explicit Numeric Gate
**Date:** 2026-07-26 (`a863f73`, deck F6)
**Context:** The learned value model was built and testable, but shipping it on subjective judgment would have been indistinguishable from guessing.
**Decision:** `deck.value_model` ships **dark** behind a pre-committed graduation gate: a replay win on *both* metrics, ESS≥100, calibration deciles within ±20%, then an interleave test. The unflagged `backend/eval/` replay harness (IPS/SNIPS, cluster-bootstrap CIs, ESS gating) runs nightly to evaluate it.
**Alternatives considered:** Ship behind a flag and watch production metrics (contaminates the baseline); hold the code unmerged (it rots).
**Consequences:** 8 of 9 deck features went live the same day; the ninth is still dark and still gated. The gate is checkable *now* — see [`NEXT.md`](NEXT.md) #4.
**Status:** Active — gate not yet evaluated.

## D-017 — Fail Loud Rather Than Serve a Plausible Wrong Answer
**Date:** 2026-07-25 (`5c29064`)
**Context:** When every roster source came back empty, the free-agents route listed the entire player pool — a confident, completely wrong answer.
**Decision:** Return **503 `rosters_unavailable`** instead. The route now unions `league_members` with a live rosters read, and if both are empty it errors.
**Alternatives considered:** Return an empty list (indistinguishable from "this league has no free agents"); serve the unfiltered pool (the bug).
**Consequences:** The free-agents exclusion had regressed three times in three days (#151 default-pool filtering, #178 `owner_id:null` orphan rosters) because both exclusion sources descended from the client-built session payload. An explicit failure mode stops the class.
**Status:** Active.

## D-018 — Unverified Sessions Keep the Short Expiry
**Date:** 2026-07-20 (`1580064`)
**Context:** `auth.persistent_sessions` moved sessions into a DB table with SHA-256 token hashes at rest and 90-day rolling expiry.
**Decision:** 90-day rolling applies **only** to verified or anchored sessions. Unverified username-only sessions deliberately keep the 4-hour posture.
**Alternatives considered:** Uniform 90-day expiry (simpler, but hands a squatter three months of access to someone else's board).
**Consequences:** Impersonation window stays small for exactly the sessions that can't prove identity. Consistent with the first-verified-wins and squatter-reset rules from the P1 verified-sessions work.
**Status:** Active.

## D-019 — Prepare the Trade, Never Fabricate the Execute Path
**Date:** 2026-07-25 (`5c29064`, `d6e867d`)
**Context:** Sleeper has a real write API; MFL and the other platforms do not, and FAAB claims have no API at all.
**Decision:** Where a real write API exists, use it (Send in Sleeper). Where it doesn't, FTF **prepares the claim and deep-links out** rather than simulating an execution it can't perform. `POST /api/trades/validate` runs a read-only pre-flight (`league_archived`, `player_moved`, `roster_limit`, `roster_not_found`) so the handoff isn't into a dead end.
**Alternatives considered:** Screen-scraping writes for non-Sleeper platforms (fragile and ToS-adverse); hiding the feature on unsupported platforms (worse UX than a prepared handoff).
**Consequences:** No feature claims to do something it can't. The pre-flight catches the common failure cases before the user leaves the app.
**Status:** Active.

## D-020 — Analytics Omits Untrustworthy Data Rather Than Reporting It
**Date:** 2026-08-06 (`30492ac`)
**Context:** `api_request_failed` latency was corrupted whenever a request spanned the app being backgrounded — wall-clock time included the time the phone was in a pocket.
**Decision:** Use a monotonic clock, stamp `bg:true`, and **omit `ms` entirely** when it can't be trusted.
**Alternatives considered:** Report the wall-clock value (poisons every latency percentile); report a sentinel like -1 (someone will average it).
**Consequences:** Latency analysis must filter on "ms present" — a real constraint on every query, recorded in [`CHANGELOG.md`](CHANGELOG.md) §Outstanding. Related: analytics Segments use a **closed grammar** (did / did_not / platform / min_events) so no user string reaches SQL.
**Status:** Active.

## D-021 — Capture ESPN's HttpOnly Cookie From the Native Store, Not Injected JS
**Date:** 2026-08-08 (ESPN Connect WebView, Phase 1b — flag `espn.webview_capture`)
**Context:** Private ESPN leagues need `espn_s2` + `SWID`. Phase 1 shipped a manual paste; Phase 1b adds an in-app WebView login (modeled on `SleeperConnectScreen`) so users don't have to hand-extract cookies. But `SleeperConnectScreen`'s technique — inject JS and poll `localStorage`/`document.cookie` — cannot work here: `espn_s2` is issued **HttpOnly**, so page JavaScript never sees it.
**Decision:** Read the cookies from the **native cookie store** (WKHTTPCookieStore) via `@react-native-cookies/cookies` (`CookieManager.get`), polling `www.espn.com` + `fantasy.espn.com` and delivering once BOTH are present. Injected JS is limited to a MutationObserver that signals the Disney SSO **one-time-code step** so a native hint can render — it never reads the code, any field value, or any DOM content. The only data that leaves the WebView is the two cookie strings, handed to `POST /api/espn/link` (never to analytics — the events carry `saw_otp`, never a credential). OTP assist is **detect + hint only**.
**Alternatives considered:** Injected-JS cookie poller like the Sleeper screen (blind to HttpOnly — the credential is literally unreadable); scrape the OTP to autofill it (needs reading the code — a credential we deliberately never touch, and iOS already autofills it from Mail/Messages); stay paste-only (the friction Phase 1b exists to remove).
**Consequences:** Adds a native dependency (`@react-native-cookies/cookies`), so the flag can only be validated in a real build — it ships **OFF** and flips after a TestFlight build validates against a real private league (friend's league 493554). Caveat: the package is **deprecated upstream** (6.2.1's npm notice names `@preeternal/react-native-cookie-manager` / `react-native-nitro-cookies` as successors); kept because the used surface is two calls wrapped in one utils module — see [`DEPENDENCIES.md`](DEPENDENCIES.md) §2026-08-08 for the migration path. Manual paste stays as the fallback; flag off ⇒ the sheet is byte-identical. The pure extractor (`mobile/src/utils/espnCookies.ts` `pickEspnCookies`) is unit-tested; the in-WebView login leg is un-automatable and is covered by manual TestFlight QA. Establishes the mobile pattern for any future HttpOnly third-party credential capture (recorded in `LLD.md` §Specific patterns).
**Status:** Active.
**Related ADR:** — (rides the ESPN linking plan `docs/plans/espn-league-linking-plan-2026-07-11.md` §4 + scope `docs/plans/espn-connect-webview/scope.md`)

## D-022 — MFL Draft Room Names Resolve in Four Ordered Tiers, and Never Render a Bare Id
**Date:** 2026-08-10 (feedback #289, `draft.mfl` already ON)
**Context:** MFL Draft Room boards rendered raw ids on both axes. `_render_mfl` set `username = {}` ("MFL has no display-name export here"), so `owner_username` was structurally `null` on every MFL row and the client fell back to the synthetic member id (`mfl:62846.f0001`); and it hard-coded `name: ""`, `position: ""`, `team: None` on every pick, so made picks rendered a bare numeric id with an empty position chip. MFL's export genuinely carries no names — but **ours does**: `league_members` has held the cleaned franchise name for every franchise since link time, and `_mfl_board_binding` was already loading those rows and discarding everything but the ids.
**Decision:** Resolve identity server-side at the single producer (`_render_mfl`), so every board consumer benefits. Franchise names come from the already-loaded `league_members` rows, falling back to `Team <fid>` (matching the sibling `_sync_mfl_owned_picks` convention). Player names resolve in four tiers with **total precedence**: the all-zeros slot sentinel (`player: "0000"`) → `No selection`; our own `players` row for a crosswalked id (the only tier carrying `team`); the DP crosswalk's own `by_mfl_id` name/position map; then the placeholder `Player <mfl_id>`. Total precedence means the two name sources can never disagree about a rendered row.
**Alternatives considered:** Stop at tier 1 and leave `name: ""` on a miss, letting the client's `pick.name || pick.player_id` fallback show the number — **rejected**: rookies are the crosswalk's weakest segment and a rookie draft is exactly where they appear, so that variant leaves the reported defect live on the most likely rows. (Vindicated in the route smoke: against a cold player cache, tier 1 resolved *nothing* and all 30 names came from tier 2 — without it the board would have been 30 rows of `Player 17472`.) Also rejected: a defaulted `members_fn` fetcher to avoid a shared-file edit (a redundant query per render plus a seam whose only purpose is dodging a merge); `Player 0000` for the sentinel (asserts a player exists); dropping the sentinel row (would break a passing test — `_mfl_counts` counts it as made and the suite asserts `len(picks) == man["made"]`).
**Consequences:** The load-bearing guard is **the keying, not the query list.** MFL and Sleeper player ids are numeric strings from different epochs that overlap densely in the rookie band — 255 MFL ids in the committed snapshot are also a *different* player's Sleeper id (`13674` = Dallas Goedert as MFL, Chris Hilton Jr. as Sleeper). A pick may take tier 1 only if its own MFL id crosswalked, and its row must be read by **that pick's crosswalked id**, never by `pick["player_id"]`, which still holds the raw MFL id on a miss. Consuming `load_players_by_ids`' `{player_id: row}` result with the raw id renders one pick's player on another pick — inside a query that is itself entirely legal, and silently. Pinned by `T-289-06`, which was verified to FAIL on the naive keying before being accepted. Zero added queries (names ride objects already fetched); one batched player read per board, none when nothing crosswalked. No schema, route, or flag change — `draft.mfl → false` remains the rollback lever. Known gap, accepted: `original_username` stays `null`, so traded MFL rows still render `from —` (the honest fix is client-side and would escalate the sim gate from Tier 3 to Tier 1).
**Status:** Active.
**Related ADR:** — (feedback item `docs/feedback/items/289-mfl-draft-room-ids/`)

## D-023 — Draft-Pick Value Is Subset- and Filter-Independent, Behind a Kill Switch
**Date:** 2026-08-10 (feedback #293/#294, flag `league.picks_always_counted`, default OFF)
**Context:** The League rankings chart counted a team's draft capital only in the All subset with no position filter. Tapping Starters, Bench, or any position pill silently dropped it, so a rebuilding team holding four 1sts ranked like a team holding none. This was *deliberate* and documented in eight comment sites — "Picks are neither starters nor bench" — and it became visible only after #285 summed picks into team values, which created the expectation that pick value is part of a team's worth everywhere. Operator ruling: *"I'm talking about picks for value."*
**Decision:** Pick value is **subset-independent and filter-independent** — the team total includes the full `picks.value` in All, Starters and Bench, and whenever `PICKS` is in the position filter, with the first position tap auto-adding `PICKS` as a visibly lit pill that one tap removes. Shipped behind `league.picks_always_counted` (default OFF, byte-identical to 1.11.0) at operator direction, overriding the orchestrator's unflagged recommendation: this reverses live behavior on a surface the operator uses daily, and a config flip is a cheaper rollback than a TestFlight round-trip.
**Alternatives considered:** Caption-only ("+X from picks" without counting) — rejected, the operator asked for the value *counted*, and it leaves bars, sort order and rank numerals wrong. Proportional allocation of pick value across positions — rejected as fabrication (`cross-client-invariants.md`). Keeping picks out of position filters on the "a position filter shows one position" reading — rejected: it re-creates the reported defect for the filter half.
**Consequences:** **Starters + Bench no longer partition All** — pick value is counted in both. That is intrinsic to the ruling, not a bug; the UI states it rather than letting the user discover it by arithmetic, and the two are never summed on screen. The flag gates **fourteen** expressions and must switch them **atomically**: bar segment heights are percentages of their own sum while a bar's height comes from the team total, so a partially-gated build grows the bar by the pick value while silently stretching the four position segments to fill it — right-looking and wrong, and invisible to a screenshot diff. Two module-scope consumers therefore take the flag as a **required, undefaulted** binding (`activeTotal`'s 4th param, threaded at BOTH call sites; `BarColumn`'s prop), so `tsc` catches an unthreaded caller. Threading only the bars would leave the #248 other-basis overlay short by exactly the pick value, flipping `boardsDifferInView` true and drawing a fabricated tick and rank-swing chip on every column — #208's reported symptom, reintroduced by the fix for #293. Pulling the switch mid-session needed its own reconciliation (R-0.4): flag ON makes `(subset != all AND PICKS in posFilter)` routine, and that state under OFF strands an invisible, unremovable filter member that renders **no bars at all**. Guarded by a 71-assertion AST check (`mobile/tests/check-picks-subset-invariance.js`) whose assertions 13 and 14 were each verified to fail on a sabotaged build that still compiled clean. Graduating the flag to `true` must add the key to `LAUNCHED_FLAG_DEFAULTS` in the same change.
**Status:** Active (dark — flag OFF pending operator flip).
**Related ADR:** — (feedback item `docs/feedback/items/293-picks-in-subsets/`)

## D-024 — The Mock-Draft "Run" Is Engine-Internal, and Two Constants Are Load-Bearing in Opposite Directions
**Date:** 2026-08-10 (feedback #290, flag `draft.mock` already ON)
**Context:** The CPU pick model scored `rank - need_bonus - noise` where `rank` is *list position*; `row["value"]` was never read. A 3-slot reach therefore cost the same across a 5-Elo gap or a 300-Elo cliff, which is why the operator saw an implausible early pick. Measured on the shipped engine: 45.5% of round-1 CPU picks reach, and at pick 4 the modal consensus rank was only ~19% likely — near-flat across ranks 1-7.
**Decision:** Partition the consensus pool by a **locally-significant value gap** (a "run": adaptive, vs a local median — not a fixed Elo threshold, because the value curve flattens in the tail) and compose it at the existing `reach_cap` seam via `min(round_reach_cap, run_offset)`, so the rule can only ever **tighten** the operator's verbatim W2e round-tiered policy and that policy's literal test stays untouched. "Tight groups of 4-5" is a target the gap rule *produces* (measured median 5.0 on both scoring formats), **not** a hard size clamp — a clamp would manufacture boundaries where the values have none.
**Alternatives considered:** Reuse the 8-tier ladder — **rejected**, its bands are 200-300 Elo wide and it is a governed cross-client enum; #279 set the precedent for refusing exactly this, so this is the second time. A single tuned `m` — **rejected on measurement**: 27 configurations were swept and **none** clears the collapse on both formats while holding a 4-5 median. `m` was doing two unrelated jobs (where the runs are, a property of the data; how tight a wall may be, a behavioral choice), so the fix was to separate them, not to keep tuning.
**Consequences:** `MOCK_RUN_GAP_MULTIPLE = 2.5` sets run tightness; `MOCK_RUN_MIN_OFFSET = 1` stops a singleton run from making the pick deterministic. **At `MIN_OFFSET = 0`, `sf_tep` forces pick 1.01 in 100% of mocks while `1qb_ppr` looks fine** — a parameter validated on one board and catastrophic on the other. `MIN_OFFSET` must also stay strictly below `round_reach_cap(1)` or the rule is inert in round 1 (`= 3` is a silent no-op). Both bounds are pinned by tests that fail on unfixed code. Separately, aggregating positional need with `max()` is **inert**: TE's `(S,B) = (1,0)` makes `severity("TE") == 1.0` for almost every August roster, so `need_pressure` is denominator-weighted. The guarding tests are two-sided by construction — the original one-sided bars (`P(#1 at 1.01) >= 0.43`, `>= 12 distinct orderings`) both **passed on the fully collapsed board** (1.000 and 24), and a collapsed `sf_tep` even scored *higher* variety than a healthy `1qb_ppr`. N is pinned at 1500 because the distinct-orderings statistic scales with N. The calibration tripwire (`test_w2_16` asserts `all_pass is False`) did not fire.
**Status:** Active.
**Related ADR:** — (feedback item `docs/feedback/items/290-mock-draft-engine/`)

## D-025 — The Trade Card Owns Its Disposition, and Absence Is the Card's Odds Design
**Date:** 2026-08-11 (feedback #169 frame decisions, third pass)
**Context:** The operator reviewed the #169 outlook-odds mockups and chose League-Summary frames B+C1+E and card frame C, with two placement corrections. Card frame D (week-6+ odds via a with-trade re-sim) was first selected, then dropped on seeing its backend cost. That left no frame covering week 6+ on the card; the IDP coverage caption's fate had been asked twice without an answer.
**Decision:** Four rulings, all operator-explicit. (1) **The trade card shows no odds block at all, in any week, for now** — week 6+ is *deferred, not designed*; absence is the design year-round. ## D-041 — Unlock Is Per-Method and Reads the Board, Not the Event Stream
**Date:** 2026-08-11 (P1 remediation, P1-7; audit A-16/A-17; operator decision D-P1-10)
**Context:** `get_rankings_progress`'s ladder branches on `ranking_method`. `'anchor'` had **no arm** and fell to the trio rule, which needs 10 swipe interactions per position — and `apply_anchor` writes Elo overrides and never a swipe, so that cohort could **never** unlock. `'manual'` had the opposite defect: `unlocked = True`, unconditionally, which post-P0-1 is reached by one drag on Manual Ranks or one Quick Rank step.

Both bars are 40, matching the trio bar so the product has one number to explain. `_tiers_rule()` is extracted as the shared seam. **`MANUAL_UNLOCK_MIN`'s value is a stated assumption awaiting operator confirmation; its shape is not.**
**Alternatives considered:** *Add `'anchor'` to the tiers/quickset arm* — **inert**: that arm reads `tiers_saved`, which the anchor lane never writes and is forbidden from writing (`_ANCHOR_VIA`'s contract; `save_tiers_position` does not occur in `save_anchor_route`). *Bump the interaction counter in `apply_anchor`* — **non-durable**: `_interactions` is overwritten from persisted swipes at session build, so unlock on Tuesday, re-locked on Wednesday; and it would grant credit to the `via:'draft_room'` path P0-1 deliberately excludes, plus to NULL-method users, while mixing units (a trio *orders* three players, an anchor *prices* one). *An Elo fingerprint* recognising the eight rung values — rejected as a comment waiting to lie.
**Consequences:** A draft-room-only anchorer **stays locked** — designed, not a bug: their method stays NULL so the arm is never entered, and their overrides count later if they ever answer one wizard question, because the predicate reads the board rather than the event stream. `ranking_complete_first_time` begins firing for the anchor cohort, a **step change in a shipped funnel series**. The manual arm is a tightening, made safe by the monotonic floor; a *strong* A-17 gate needs a product decision and a client payload change (the client posts the whole visible list on every drag) and remains P1-8's.
**Status:** Active.

## D-042 — First-Unlock Fan-Out Is Suppressed by a Backfill, Not a Special Case
**Date:** 2026-08-11 (P1 remediation, P1-7 RL-5)
**Context:** Crossing the unlock bar takes a `was_first` branch that emits `ranking_complete_first_time` and pushes "@user just unlocked Trade Finder" to **every joined leaguemate**. Giving `'anchor'` a rule flips a pre-existing cohort locked→unlocked on their first poll after deploy, which would fan out retroactively for work nobody did that day. P0-1 faced the identical question.
**Decision:** Match what P0-1 **did**, read from the merged code rather than from any plan: leave the `was_first` branch untouched and add a boot-time backfill (`database.backfill_anchor_unlocked_formats`) that pre-seeds `users.unlocked_formats` for the qualifying anchor cohort, so `mark_format_unlocked` short-circuits and neither the event nor the push fires. Not done for `'manual'`, which P1-7 only ever tightens.
**Alternatives considered:** Suppressing inside the `was_first` branch for anchor users — rejected: it makes a permanent code special case out of a one-deploy problem, and it would also suppress *genuine* future unlocks. Doing nothing — rejected: the burst is the kind of thing that reads as spam to a whole league at once.
**Consequences:** The backfill's cohort predicate is a deliberate **superset** of the runtime one — it counts stored overrides, while the runtime rule counts pool-resident ones, because the player pool is not a database concept. The direction is generous (grants an unlock a hair early, never locks), which is the right side to err on for a suppression pass. The affected user ids are logged, per the same rule P0-1's backfill set, so a scoped SQL undo stays expressible.
**Status:** Active.

## D-044 — A Position Filter Means That Position: Rules A and B Removed
**Date:** 2026-08-12 (feedback #300; reverses part of #293/#294)
**Context:** `league.picks_always_counted` shipped 2026-08-10 with two toggle rules. **Rule A** auto-added `PICKS` on the first position tap so draft capital never silently vanished under a filter. **Rule B** cleared the filter to All when removing a position left no core position, "instead of stranding the user in a picks-only ranking they never asked for". #300's median divider then found rule A load-bearing in the wrong direction: with it live, tapping WR ranked the league by **WR + capital** while any median measures WR alone, so no honest line could be drawn — and in a pick-carrying league (i.e. all of them) the feature sat one undiscoverable tap from invisible.
**Decision:** Remove both. A position filter means that position; pick value is an explicit opt-in. Operator ruling: *"All leagues have picks. They should not be selected along with a position filter. Only by explicit user action."*
**Alternatives considered:** Keeping rule A and gating the divider on `PICKS` absent — built first, and rejected: it left the natural path (tap WR from All) reaching nothing, which is the #205 tenet failure of requiring the user to know how the app works. Narrowing rule B — impossible: with rule A gone, every `PICKS` is hand-chosen, so rule B's trigger set and the case the ruling protects are the same states.
**Consequences:** Reversibility becomes structural (a plain toggle is its own inverse) and strictly better — `{PICKS}` + RB − RB now returns to `{PICKS}` rather than costing the extra tap #294 accepted. #294's "hidden hand-chosen state axis" objection is obsolete. **What #293 originally complained about can return**: a rebuilding team's capital is no longer counted under a position filter unless the user asks. That is the intended trade, not an oversight. The flag still governs picks in all subsets, the bar segment, legend, pill, drill-in group and hint strings — only the auto-add is gone. Two Maestro flows and one structural suite were re-pinned; the original reasoning is preserved in the code comments and the `features.json` block rather than deleted.
**Status:** Active. Shipped `5139b45`, v1.13.1 build 106.

## D-045 — An Inbox Row Is Written Beside the Push, Never Inside the Dispatcher
**Date:** 2026-08-13 (notif-inbox-growth; operator decisions GD-1…GD-8)
**Context:** Six notification types that push today left no trace in the bell inbox, and `_send_typed_push` has never written one for any kind — 11 of 14 kinds had no inbox row at all. The obvious economy was to add `create_notification` inside the dispatcher and get all 14 at once.
**Decision:** Rows are written **at the call site, beside the push**, via a thin `_write_inbox_row()`. The dispatcher stays push-only. Idempotency is the caller's job and may **not** borrow the push's.
**Alternatives considered:** Writing the row inside `_send_typed_push` — rejected: its five gates (prefs → bucket → frequency cap → quiet hours → Expo) are each a statement about *interrupting* the user, and none is a statement about what belongs in a list the user chose to open. Writing rows in a post-dispatch hook — rejected for the same reason plus a worse one: the hook only runs when a push leaves.
**Consequences:** The inbox is now a surface with its own rules rather than a push mirror, which is what lets phase 1 ship to **every** user while push stays operator-only — nothing here waits on the push rollout. The cost is one extra line per call site and an explicit idempotency decision each time. `_freq_cap_blocks` reads `notification_events_log`, which is only written when a push **actually leaves**, so a suppressed push logs nothing: the 15-minute `match_expiring` cron would have re-written its row ~96×/day per match on a shared gate. It uses `notification_exists_with_meta`, keyed off the inbox's own rows; the other three sites are structurally once-only. Recorded in `living-memory/LLD.md` and `docs/cross-client-invariants.md`.
**Status:** Active.

## D-046 — The Bell Carries Receipts, Not Prompts; the Invite Ask Lives in the Empty State
**Date:** 2026-08-13 (operator decisions GD-1, GD-3)
**Context:** The operator asked to use the notification list for things we want users to *do* — invite leaguemates, re-rank players, learn about new members. The inbox today is an event log: everything in it is news. A prompt list is a different object, and prompts are always available while news is not, so mixing them without a rule converts the log into the prompt list.
**Decision:** v1 ships **six receipt/social rows and zero prompt rows**. The invite ask goes in the bell's **empty state**, gated at the shipped <50%-penetration rule (`MatchesScreen.tsx`, D-P1-13 PR-6) — never a standing row. Ordering stays recency-only; no `priority`/`expires_at` columns until the first prompt row is approved.
**Alternatives considered:** A standing invite row — rejected: it fails the slot test by construction (true for every user every day, therefore not news), and five in-screen invite surfaces already exist. A single-lifetime invite row fired at a moment of demonstrated need — defensible, and left on the table if the operator wants it. A pinned "for you" section — rejected: two lists in one sheet, solving a crowding problem six rows a month do not create.
**Consequences:** What is protected is that **opening the bell is currently always worth it**. The empty state is structurally incapable of burying a receipt — it exists only when there is nothing to bury, and disappears the moment the surface has content. The honest cost of recency-only: unread rows never age out (`get_notifications` returns all unread), so a row can sit for weeks. Fine for receipts, not for prompts — a second, independent reason prompts wait. Phase 3 prompts are gated on `notif_row_tapped` showing the bell is used at all.
**Status:** Active. Reasoning: `docs/business/product/2026-08-12-notification-inbox-growth-surface.md`.

## D-051 — A Co-Owned Sleeper Roster Has One League Identity: its Primary `owner_id`
**Date:** 2026-08-15
**Context:** Sleeper rosters carry an optional `co_owners` array; FTF never read it, matching `owner_id == user_id` everywhere. Confirmed live on the operator's own account: he co-owns roster 3 of league `1338231586314780672`, so the league appeared in the picker (Sleeper counts co-ownership in `/user/{id}/leagues`) and then resolved to nothing — and, because the opponent filter was `owner_id != user_id`, his own roster was posted back as a leaguemate for the engine to trade against.
**Decision:** A roster belongs to a user iff `user_id == owner_id` **or** `user_id ∈ co_owners`, and a co-owner is an **alias** of that roster's primary `owner_id`, never a separate team. **Alternatives considered:** *Widen the client predicate only, keep the caller as the `league_members` key* — rejected, and this is the load-bearing rejection: `league_members` is league-SHARED, so roster 3 gets one row from the co-owner's sync and another from any leaguemate's, giving a 12-team league 13 rows with a duplicated roster — and session_init's DB-member merge then hands the engine a phantom copy of the caller's own team. *Re-key on `roster_id`* — correct but a schema change plus migration to fix an identity bug; `owner_id` already carries the guarantee. *Resolve server-side in session_init* — `_sleeper_get` is uncached, so it adds a live Sleeper round-trip to the launch critical path; trust level is unchanged either way since `user_id`/`opponent_rosters` are already client-asserted. *Re-key `member_rankings` too* — would attribute one person's board to another's Sleeper id in cross-league Trends.
**Consequences:** Both co-managers see the same team (correct — it is one team) with personal boards, so suggestions still differ. Exactly one member row per roster; power rankings stay at 12. The team is labeled with the primary owner's Sleeper name, since that row is what every other member sees; `is_you` marks the caller's. Known limitation: `member_rankings` stays account-keyed, so a co-owned team's board reaches leaguemates only if the primary owner uses FTF (follow-up in NEXT.md). ## D-052 — Compressed Boards Are Fixed by Rescaling the Prune, Not by Rank-Normalising It or Disowning the Board
**Date:** 2026-08-15
**Context:** Three of four boarded opponents in the operator's real league produced zero trade cards. Root cause: `trade_optimizer`'s candidate-pool prune ranks by the raw divergence `_vo(p) - _uv(p)`, and `elo_to_value` is exponential, so an opponent board pinned near the 1200 floor deflates studs by thousands of value points and bench bodies by tens — every tradeable stud sorts below the user's junk. Compounding it, `trade_service`'s boarded/unboarded branch was `if/else` with no fall-through, so a zero-yield boarded member vanished from the deck entirely. Three fixes were on the table (scale-invariant ordering / consensus fallback / treat a thin board as unranked) and they are not mutually exclusive.
**Decision:** Ship the **first two**, each behind its own dark flag. (1) `trade.pool_calibration` rescales the opponent's value space by the **geometric-mean ratio over the assets in play** — the same players priced on both boards — before differencing; equivalent to shifting the opponent's board onto the user board's mean Elo, so the prune **order** is exactly invariant to a board-wide offset. Prune ordering only; surplus, fairness and composite keep each side's own raw space. (2) `trade.divergence_fallback` runs the existing consensus generator when the divergence path returns empty for a boarded member.
**Alternatives considered:** *Rank/percentile-normalised divergence* — rejected: scale-invariant, but it discards magnitude, so on a healthy board a five-slot disagreement about a WR3 would outrank a two-slot disagreement about a stud worth 20× more. That regresses the main path to fix the edge case. Geometric-mean rescaling is scale-invariant **and** magnitude-preserving. *Treating a low-spread board as `has_rankings=False` (option c)* — rejected: needs a spread/coverage threshold nobody can calibrate, and it throws away real board signal; the fallback fixes the same perverse incentive with no magic number and no information loss. *Raising `v3_pool_size` (the deploy-free knob)* — rejected as the fix: measured on real boards it rescues the same pairs at **26–102 s per pair** against ~2 s at 12, and it leaves the ordering defect in place. *Calibrating the surplus math too* — rejected: out of scope and unnecessary; the surplus gate was never what rejected these trades (the field case scored +3,682 against a floor of 60).
**Consequences:** Boarded members can now carry `basis:"consensus"` cards — a new but already-instrumented combination on the existing deck spine. Because boarded members are visited first and generation stops once the deck reaches `global_target`, rescuing them **displaces** consensus cards from unranked members further down the queue (post-deploy: four unranked members returned 0). Note `global_target` is a stop-when-reached threshold checked *after* each opponent's whole batch is appended, **not** a truncation — the deck can overshoot by up to `max_per_opponent - 1` (post-deploy FFV3 read: 34 cards). An earlier draft of this entry claimed the deck size was fixed at 30; that was an artifact of three pre-deploy reads in which every batch happened to be a full 5. A single multiplicative factor cannot undo a *nonlinear* compression, so calibration alone did not rescue MangoPatti or Bcork — quantile-matching is the candidate follow-up ([Q-017](OPEN_QUESTIONS.md)). Both flags are dark; flipping either is deploy-free and each is its own kill switch. Flag off ⇒ engine byte-identical, pinned by paired tests in `backend/tests/test_compressed_board.py`.
**Status:** Active (code merged behind dark flags; not yet enabled in production).

## D-053 — A Narrative Sentence Names a Position and a Player From One Source, or Says Neither
**Date:** 2026-08-15
**Context:** `trade_narrative.build_narrative` paired a position from the roster analysis (`match_context.user_needs` / `opponent_surplus`) with a player from the card (`_top_received_name` — highest dynasty value, no position filter). Nothing linked them, so a QB-thin manager receiving a TE read "Adds Brock Bowers to address your thin QB group." Running the real engine against the operator's four Sleeper leagues on 2026-08-15 produced 23 position-inaccurate sentences out of 32 cards; `build_narrative` runs on both live paths, so it shipped on every card.
**Decision:** Every positional branch resolves the player and the position **together**, through `_top_received(card, players, positions)` — the highest dynasty-value received player whose *own* position is in the candidate set — and prints that player's own position. Among the players that qualify, the highest-value one wins (not the highest-priority need), so the sentence names the card's headline asset. When nothing received fills a need, the builder falls through to the neutral `"<player> comes back in a <fairness> package."` sentence rather than inventing a benefit. The `fit_premium` branch's `needs[0]` fallback is deleted for the same reason: no premium position → fall through.
**Alternatives considered:** *Keep `needs[0]` and only swap the player* — rejected: it inverts the same bug (names the top-priority need even when a different need is the one actually filled). *Prefer the highest-priority need over the highest-value player* — rejected: the card body is dominated by the headline asset, so naming a bench QB while a stud RB carries the trade reads as a different trade than the one shown; both are true, this one is legible. *Drop the positional sentences entirely* — rejected: when the pairing is real it is the most useful line on the card.
**Consequences:** Some cards lose their positional sentence and get the neutral fairness line instead — that is the intended trade (silence over a false claim). Any future branch that wants to name a position must get it from `_top_received`; an invariant test in `test_trade_narrative.py` sweeps every needs × received-position combination and fails if a claimed position isn't on a received player.
**Status:** Active.

**Context:** Testers filed live-behavior bugs: lopsided cards a human would never accept survive even with the fairness toggle off (a 45% gap passes the divergence floor), 2RB-for-2WR packages wreck positional balance, a pick riding the heavier side papers over the gap, a contender is offered a player behind their current starter, and already-liked/matched trades regenerate after 7 days.
**Decision:** Five presentment rules behind `trade.presentment_rules` (ships ON — Q-G6-3), enforced as **construction-time kills with refill** inside every v1 generator (never post-hoc deck filtering; never relaxed by #189). Recorded sub-decisions, per the G6 reconciliation: (1) **filter-not-reorder** — the operator's batch-plan call supersedes the 2026-07-17 "light multiplier" posture *for presentment* (a reorder still serves the horrid card; `need_fit_weight` reordering survives underneath). (2) **R5's targeted/untargeted boundary** (orchestrator arbitration): any targeted job — pinned give/receive, `opponent_user_id`, explicit `acquire_positions` — bypasses R5 via a flag derived server-side in `_run_trade_job`, never client-passable; the operator-visible asymmetry (a card reachable via Offer/targeting but absent from discovery) is intended — "you asked for him" vs "we suggest what you need". R1/R2/R3/R4 apply to every job. (3) **R5 judges on the consensus board** (`seed_value`), not the user's raw board, though #304's verbatim complaint ranks on the user's board — shrunk user boards are noisy at low comparison counts and the corpus baselines are consensus-denominated; the user-board variant is a named follow-up, not an oversight. (4) **Unresolved-window users get no need gate** — the `unresolved → PASS` branch is deliberate fail-open, stated rather than implicit. (5) Q-G6-1: likes-you gets exactly R4 dedup, none of the quality rules (Q21; the D-055 floor stays its quality gate). (6) Q-G6-2: `declined` matches never hard-exclude — "blocked" means currently live in the match pipeline.
**Alternatives considered:** Heavier `need_fit_weight` / demote-to-bottom (Q19 closed: the card still exists); post-hoc deck filter (converts kills into holes, fails the D-055 empty-deck bar); per-rule feature flags (knobs already give per-rule deploy-free disable); widening `since_days` (still a window — the window was the bug); applying R5 to targeted jobs (an R5 refusal of an explicit user ask is an inexplicable dead end; explicit acquire already replaces inferred need).
**Consequences:** Contender decks thin most by design (#304 is a contender complaint) — the `presentment-tripwire` WARNING (runbook) watches rule-explained thinness. R3's defaults are unmeasured (zero pick-carrying candidates in every available corpus) — `pick_gap_frac` is the named tuning lever pending a prod-state divergence replay (NEXT.md). `trade_gen.v2` inherits only R4 (via the shared `past_decision_keys` kwarg); porting R2 into gen-v2 hygiene is on its lighting checklist.

## D-066 — A Pass Only Moves Elo When The User Actually Made A Value Claim

**Date:** 2026-08-17 · **Context:** decline reason capture (`docs/plans/decline-reason-capture/SPEC.md` §4)

Before this, every pass fired `record_trade_signal(winner=give_ids, loser=receive_ids,
decision="pass")` — asserting *"I value my players more than theirs"* for **every** decline.
That is true for exactly one of the reasons a user can now give.

**Decision:** the pass Elo write survives only for `value_giving` ("giving up too much").
It is suppressed for `value_getting` (the user said the **opposite** — writing it would
invert the signal), for every `fit_*` code, for `other*`, and for a layer-1-only answer
where no specific claim was made. Because layer-1-only always suppresses, the `value_giving`
signal lands at the **layer-2 tap**, and `elo_signal_at` claims it once so it can never
double-write. Knob `pass_reason_elo_suppression = 0` restores the old
write-on-every-pass behavior with no deploy.

**Why:** the boards are the product's foundation, and they were being fed a claim the user
never made every time someone passed for a roster-fit reason. This is a correctness fix to
ranking inputs, not a feature preference.

**Known limitation, accepted:** the write is **not retracted** if a user earns
`value_giving` and then switches tiles — there is no negative-K correction path on this
route. Documented in the route, the scope block, and pinned by a test proving it cannot
write twice.

## D-073 — A Replayed Pass Is Suppressed by a Time-Window Guard, Not a Unique Constraint
**Date:** 2026-08-18
**Context:** G-049 — a duplicate pass double-counted `trade_k_pass`. The obvious fix (unique
constraint on `trade_decisions`) is unavailable: `retracted_at` (#318) makes duplicate
`(user, league, trade_id)` rows **deliberate** (the revive path), the constraint cannot be created
against prod (63 pre-existing duplicates reject it), and an `IntegrityError` in the route's persist
block would skip `check_for_match`, killing mutual-match detection on a re-like. **G-049 also named
the wrong table** — `_compute_elo` replays `swipe_decisions`, so a `trade_decisions` constraint would
have fixed nothing measurable.
**Evidence:** prod (933 rows) splits duplicates into **40 double-writes at 0.015–0.200 s** and
**23 genuine re-decisions at 147.7 s+**, with a **738× empty band** between. The gap is what makes a
time window safe rather than a guess.
**Decision:** `save_trade_decision` suppresses a write only on the narrow double-fire signature — a
still-live row (`retracted_at IS NULL`), same `(user, league, trade_id, decision)`, byte-identical
payload, inside `TRADE_DECISION_DEDUPE_SECONDS = 10.0` — and returns `bool`. **Both** route call
sites (`swipe_trade`, `_apply_reasoned_pass`) gate `save_trade_swipes` on that verdict, which is what
actually single-counts the Elo. `check_for_match` is **not** gated: a replayed like must still
surface a match. **`RankingService.record_trade_signal` is not gated either** — it fires before the
DB write and appends to `_trade_swipes`, derived state that `replay_from_db` rebuilds from
`swipe_decisions` at every `session_init`. Gating it would make an in-session board movement depend
on the DB being reachable, when the persist block around it is best-effort by design: that trades a
bounded 2x overcount for an unbounded 0x undercount on a DB blip. The guard fails **open** on an
unparseable timestamp — losing a real decision is worse than keeping a duplicate row. No migration,
no DDL.
**Alternatives considered:** unique/partial index (rejected above); dedupe inside `_compute_elo` or
`save_trade_swipes` (**not implementable** — `swipe_decisions` carries no trade or league identity,
and prod has 661 legitimate repeats of the same `(winner, loser, k)` triple within an hour, so a
blind identity dedupe would delete real signal); a genuine upsert (nothing to update — a replay
should change no state).
**Consequences:** read-then-write in one transaction, not a distributed lock — two simultaneous
requests on separate workers could still both write. All 40 observed prod duplicates were sequential.
The contract test defines its own caller, so **route pins** (`inspect.getsource`) were added after
sabotage showed both call-site gates could be deleted with every test still green; a **route-level
test** now POSTs `/api/trades/swipe` twice against a real DB with the real `save_trade_swipes` and
counts `swipe_decisions` rows, which the source pins alone could not do.
**Accepted residual:** a replay still doubles the *in-memory* signal for the life of that session
(~2 Elo points at `trade_k_pass = 4.0`, on the affected pair only). It clears at the next
`session_init` because the persisted rows — now correct — are what `replay_from_db` reloads. Pinned
by `test_route_replay_leaves_the_in_session_signal_doubled` so that it stays a decision rather than
drifting into a leak.
**Watch (not yet true as of 2026-08-18):** the matchmaking session reports that `feat/tier-bounded-pins`
— in flight, **not landed** — clamps a tier-placed player's Elo to his tier band, which would make this
residual strictly smaller for *pinned* players (a doubled signal could not push value past the band
edge) and leave it unchanged for unpinned ones. Re-check this paragraph once that branch is on `main`;
do not treat the tighter bound as real until then.
**Status:** Active.

## D-071 — `swipe_guard_blocked` Is an INTENT Event, Laddered Not Deduped

times and generate no events, which is why it took a user report to find.

every fronted card — so no new user-day is created. A test pins that premise so it cannot rot
silently. **If the operator disagrees, it is one line.**

## D-070 — Tier-Target Chips Are Direction-Aware; a Repeat Tap Is a No-Op
**Date:** 2026-08-18 (operator: *"when users are ranking players and push a player down a tier, the default should be that the player is at the top of the next tier"*)
**Context:** The "Tier down" button (`moveTierByOne`) already inserted at the top — that path was never broken. The reported behavior came from the **tier-target chips** ("Move to 3rd") and the VoiceOver "Move to \<tier\>" action, which appended to the destination's END regardless of direction. Within-tier order is score-derived, but `apply_tiers` spreads the submitted index monotonically across the tier's Elo band (`ranking_service.py:1419-1427`), so client order round-trips faithfully — persistence was ruled out with a new round-trip test.
**Decision:** Both chip paths are direction-aware — a mover whose source tier is ABOVE the target (moving down) enters at the TOP; from below, at the bottom. Applied to **all** jumps, not only adjacent tiers. **"Move up" is unchanged** (bottom of the higher tier): that asymmetry is the deliberate minimal-displacement rule documented at `TiersScreen.tsx:1552-1555`, and the operator asked only about *down*. A player **already in** the destination is a **no-op** in both handlers.
**Alternatives considered:** Top-insertion only for adjacent tiers, appending for jumps of 2+ (rejected — inconsistent with the Tier-down button for no clear user benefit; revisit if a far jump to FA reads as too strong a value claim). Making "up" symmetric (rejected — minimal-displacement is coherent and out of scope). Routing same-tier movers into the "down" group (rejected — see consequences).
**Consequences:** A multi-select spanning both sides of the target splits into two groups bracketing the existing members; this is intended and preserves global rank order. The same-tier no-op is load-bearing: selection persists after a chip tap, so without it a double-tap sent a player from the top of a tier straight to the bottom — reproducing the very symptom this fixes. Caught in adversarial review, not in build.
**Status:** Active.

## D-068 — A Failed Swipe Re-Arms the Guard and Offers No Retry Button
**Date:** 2026-08-18 (operator bug report: *"he wasn't able to [pass]. It kept the suggestion on the screen without a way to move past"*)
**Context:** `swipeMutation.onError` rewinds the deck to re-front a card whose POST failed, but never cleared `lastDispositionedRef` — so every subsequent ✕/✓/swipe on that card hit a bare `return` and the user was trapped with no error and no escape but a league switch. Six other sites clear that guard; one carries a comment describing this exact hazard. The failure was also effectively invisible: the POST is held `UNDO_HOLD_MS = 5000` before firing, and the warning toast held for the 1500 ms default.
**Decision:** (1) Clear the guard in `onError` on an `ctx.rawId` match — one statement, placed OUTSIDE the `setDeckIdx` updater, because React may re-invoke updaters and a ref mutation there is unsafe. (2) **No Retry action on the toast.** With the guard cleared, the card's own ✕ re-POSTs *and* advances the deck; a Retry button would re-POST while leaving the card fronted, inviting a second pass. That matters because **`save_trade_decision` is a plain `INSERT`** (`backend/database.py:4794`) with no upsert and no unique constraint — a duplicate writes a second `trade_decisions` row, a second `trade_swipes` row, and replays `trade_k_pass` twice. (3) The toast holds 6 s and says "Tap again to retry", which is now literally true; a `verification_required` 403 gets its own copy and points at the banner the same failure raises, since retrying a standing gate can never succeed.
**Alternatives considered:** Retry that also advances the deck on success (rejected — needs deck mutation from a closure that may outlive a fairness re-sort, strictly riskier than the ✕ that already works). A `swipe_guard_blocked` analytics event (deferred at the time — needs an `analytics_taxonomy.py` row, which crosses the bright line. **Built 2026-08-18 on operator instruction — see D-071**; the stall is no longer invisible).
**Consequences:** Re-arming opens a duplicate-record path the stall previously prevented — a swipe that succeeded server-side but lost its response now lets the user re-pass and double-record. Accepted: a permanent trap is strictly worse. Recorded as **G-049**.
**Status:** Active.

## D-067 — A Dismiss Is a Hard 14-Day Exclusion, Not a Score Demotion; Accuracy Over Volume
**Date:** 2026-08-17 (operator: *"Users are reporting that they're getting the exact same suggestions between sessions in the same order… there needs to be a cool down process after a 'pass' decision"*; scope + principle confirmed same day)
**Context:** `deck.fatigue` shipped ON with two tiers, and a dismiss only ever earned the weak one. A **decline** (backing out of a mutual match a league-mate already agreed to) writes a durable 30-day near-duplicate suppression; a **dismiss** (`decision='pass'` — swiping away an engine-invented suggestion) got only a score multiplier floored at `fatigue_floor = 0.25`, which demotes but never removes. The one hard filter, `past_decision_keys`, was windowed at 7 days shared with likes — and 61% of prod decisions (495 of 810) had already aged out of it. `deck_suppressions` had **0 rows in prod**: the hard path had never fired for any user. Measured symptom: one card served across 41 separate deck jobs in 12 days. Dispositions themselves were saving correctly (496 passes, 314 likes) — the bug was never persistence.
**Decision:** (1) A dismiss becomes a **hard exclusion** for `pass_cooldown_days` (default **14.0**), a `model_config` knob — separate from the like window, which stays 7 days. (2) The exclusion **binds immediately** to every service in `sess["trade_svcs"]` at swipe time, not at the next `session_init`; `sess["trade_svc"]` is an alias for the active format's service, so updating it alone leaves other formats stale. (3) Scope stays **exact-pair**, deliberately NOT the decline path's near-duplicate suppression — a dismiss is one cheap swipe at a hypothesis, not a rejection of an agreed deal, and dismisses outnumber declines by orders of magnitude. (4) **Re-showing a card that was served but never acted on is acceptable** and is left alone (98.5% of the reporting user's repetition; 4,003 impressions vs 61 decisions in 14 days).
**Operator principle (governs future tuning):** *"The goal of these revisions is accuracy, not volume. Bad suggestions are worse than limited suggestions."* Deck thinning is an accepted cost of exclusion work — when a cooldown and the D-055 empty-deck bar conflict, report the number and keep the exclusion; do not weaken a correctness rule to protect deck size.
**Alternatives considered:** Reusing `deck_suppressions` near-duplicate semantics for dismisses (rejected — one swipe would silence a player's whole trade space); a new feature flag (rejected — the knob at `7.0` is the deploy-free revert, a flag adds surface with no extra rollback value); windowless dismissal like #336's matched/awaiting (rejected — a genuinely changed market should be able to resurface a name); reading `deck_impressions` back at generation to suppress served-but-unacted cards (out of scope per the operator, and a much larger change).
**Consequences:** Decks thin further for heavy swipers in small leagues, on top of G6's 18.4% presentment kill — accepted per the principle above; `pass_cooldown_days` is the lever. Soft fatigue multipliers are untouched and still apply underneath. Naming hazard recorded: the UI's "dismiss" is the API's `pass`, while `/api/trades/awaiting/dismiss` is a *different* action (#336).
**Status:** Active.

## D-074 — A Zero-Divergence Asset May Not Buy Ranking Score; One Player May Not Own a Deck
> **Renumbered 2026-08-18 (was D-068).** Claimed concurrently with the swipe-guard D-068 below;
> both landed on `main` as duplicates. This is the later of the two by push order and carries
> fewer references, so it moved. Third ID collision in three days — the grep-then-write rule
> cannot see an unpushed sibling session.
**Date:** 2026-08-18 (operator: *"the random insertion of picks when a trade would be fair without them is by far the most nonsensical behavior"*)
**Context:** Live-corpus diagnosis of "the suggestion engine is producing mostly nonsensical trades" (563 impressions / 8h) found two defects. **A — picks are free fairness.** Picks carry zero board divergence by construction (every board is primed with the same bridged Elo), so a pick adds nothing to the mutual gain the composite is meant to score — yet it raises the consensus `fairness` term whenever it closes the give/receive value gap, and nothing penalised package size. 63% of live cards involved a pick; `PICK PICK PICK -> RB WR` appeared 18 times; 25% of multi-asset pick cards ended with a <10% value gap, i.e. the pick was pure fine-tuning on a trade that was already fair. **B — one player floods the deck.** `_dedup_and_sort` did exact-key dedup then sorted by composite, with no notion of a repeated headliner; `mismatch` is largest for whichever asset diverges most, so that asset anchored many distinct high-scoring packages and all of them survived (Colston Loveland 18/18 cards in one deck, 8/8 in another, MarShawn Lloyd 13/33). That makes a single valuation error catastrophic instead of survivable, because mismatch is LARGEST exactly where a valuation is most wrong.
**Decision:** (1) The **ranking** fairness term is priced on the **signal core** — the assets whose two boards actually disagree — so a zero-divergence asset cannot raise it; the **gate** and the card's stamped `fairness_score` keep pricing the real package. (2) At most `deck_headliner_cap` (2) cards per **centerpiece** in one served deck, applied at deck assembly on the same centerpiece definition `deck_impressions.centerpiece_id` uses. (3) Three supporting rules: prefer the minimal package among near-equivalent variants in the pinned ranker; strip matched pick pairs before the churn gate rules; damp the ranking mismatch of thinly-compared assets. (4) **Every change gets its own `model_config` knob whose disable value is byte-identical to prior behaviour**, no group feature flag — proven against `origin/main` goldens.
**Alternatives considered:** *Design (a), a per-asset package-size penalty on composite* — rejected: it mis-names the defect (the problem is a zero-INFORMATION asset buying score, not package size; a 3-for-2 of five genuinely divergent players would be taxed identically), it needs calibration against the composite scale for a guarantee that is still conditional, and it pulls against the `crown_asset` consolidation premium. *Zero-WEIGHTING core assets instead of dropping them* — rejected: `package_value_v2`'s 'heavy' crown premium branches on asset COUNT, so a zero-valued asset still moves the ratio. *`min(full, core)` fairness* — rejected: it fails the required invariance whenever the base package already carries padding. *Core-gating the mismatch term too* — rejected: a pick added to the short side really does move value on the user's own board, so that gain is real. *A shared feature flag for the wave* — rejected on the G6 precedent: it would make the five changes un-revertible independently.
**Consequences:** Pricing ranking fairness on the core also removes the PENALTY padding used to incur, so a padded package now ties its bare sibling instead of scoring below it; the tie-break (fewer pieces wins) and the headliner cap are what keep the bare deal on top, and both ride the same knobs. Decks thin further on top of D-067's cooldown and G6's presentment kills — consistent with D-067's operator principle ("accuracy, not volume"). C3's strip is evaluation-only: a matched pick pair inside a package with real content on both sides still rides on the emitted card; C1 stops it buying score, and killing it outright was deliberately left out of scope. The five defaults are **unmeasured against the live corpus** — they are reasoned from the fixtures, and each knob is the named tuning lever.
**Status:** Active.


## D-069 — A Pin Is the User's Newest Word, Not Their Last Word Forever
**Date:** 2026-08-18
**Context:** [The valuation audit](../docs/reviews/2026-08-18-valuation-age-audit.md) found board overrides ("pins") composing perversely with the trade layer. `_compute_elo` skips every rating update for a pinned player — deliberate, and itself a fix (before it, tier saves became "decorative" when a user had many past swipes). But `trade_service._shrink_user_elo` weights personal Elo by `w = n/(n + shrink_pseudocount)` where `n` is the COMPARISON COUNT, direction-blind. A pinned Elo cannot move, so extra comparisons only raised `w` and dragged effective value further toward the pin: 17 down-votes on a player pinned above consensus raised his trade value **12.5%**. 67.8% of all 4,013 recorded comparisons had both sides pinned. The audit rated F2 "worth an operator decision, not an agent decision" precisely because permanent pinning was itself deliberate.
**Decision:** (1) **F1** — `comparison_counts()` counts only comparisons that actually MOVED a player, so a still-pinned player scores 0 and prices at exactly the consensus seed. (2) **F2** — a **ranking** swipe recorded strictly AFTER a pin releases it; the pin stays as the starting rating and only newer swipes apply on top. (3) The F1 exclusion applies to `_value_uncertainty` as well as `_shrink_user_elo`, sharing one map. (4) Legacy (timestamp-less) pins are **permanent by default** — `pin_legacy_at_epoch=0` — so no existing board moves until the user re-tiers. (5) Every rule gets a `model_config` knob whose kill value is byte-identical to prior behaviour, proven against a golden captured on `origin/main`.
**Alternatives considered:** *Keep raw counts for `_value_uncertainty`, exclude only for shrinkage* — rejected: after F1 a pinned player's value IS the consensus seed, and this codebase already gives any consensus-valued player maximum uncertainty (`n=0 ⇒ range_base`); a narrow range around a value carrying zero personal signal is false precision, and splitting the map means threading a second one through 8 call sites across three files for a "pinned AND compared" population. *Replay ALL history for a released player* — rejected: the placement already superseded everything said before it; replaying resurrects exactly the swipes the user overrode. *Let a trade like/pass unpin* — rejected: an indirect, low-K judgement of a whole package must not destroy a deliberate tier placement (a released player does absorb newer trade swipes). *Bulk-clear or bulk-stamp the 2,735 live pins* — rejected outright as an agent action; the reversible backfill is written up in [scope-phase0 §6](../docs/plans/three-model-bakeoff/scope-phase0.md) and left unexecuted.
**Consequences:** **F1 removes the inversion immediately; on today's data F2 unfreezes nothing.** Every live pin predates the timestamp, so live comparisons stay at 1,292/4,013 (32.2%) until the operator opts in via `pin_legacy_at_epoch=1` (→ 100%) or runs the backfill. What changes now is the confidence map: 6,250 of 8,026 player-sides (77.9%) stop contributing — precisely the votes that could never move an Elo. `users.tier_overrides` gains a sibling key `__override_at__` rather than a value-shape change, so no migration and no existing reader is touched. The pin is still invisible in the ranking UI (audit F3), so a user can still vote against a control that cannot move — that is the durable fix for recurrence and it is NOT in this work.
**Status:** Active.

## D-070 — A Superseded Deck Job Must Finish Silently, Because Nothing Can Stop It
**Date:** 2026-08-18 (operator-approved mid-flow; approval relayed by the coordinating session — see [scope-phase0 §7](../docs/plans/three-model-bakeoff/scope-phase0.md))
**Context:** `POST /api/trades/generate` gated its cache-hit branch on `force` but not its in-flight branch, so a forced regeneration arriving while a job was running returned that job verbatim — same `job_id`, same minted `trade_id`s — and the regeneration never happened. It broke the Quick Set → Trades handoff and would have made D-069's unpinning invisible: a changed board that cannot rebuild the deck is a change the user never sees. The job registry has **no cancellation mechanism** anywhere, so gating the branch alone orphans the old worker, which keeps running and keeps writing `deck_impressions` rows for a deck no user will ever be served.
**Decision:** Gate the in-flight share on `force_fresh`, AND mark the displaced job `superseded`. Every snapshot publish routes through one helper, `_job_live(j) = running AND NOT superseded` (8 sites). The two DURABLE side effects — impression rows and the `trades_generated` event — re-read the marker under the lock at the point of use rather than once up front, so a supersede landing mid-worker still suppresses them. The job still transitions to `complete`, so a client holding the old `job_id` polls to a terminal state exactly as before. Knob `force_supersedes_running` (kill 0.0).
**Alternatives considered:** *A new public `superseded` status* — rejected: an undocumented enum value reaching clients that are still polling the old id. *Marking only, no publish gate* — rejected: the orphaned worker would keep overwriting the very snapshot the user is now reading. *Suppress impressions but keep `trades_generated`* — rejected as inconsistent: both count a deck that was never served, and both overstate supply in every per-deck rate. *Building a real cancellation mechanism* — out of scope; the marker achieves the observable outcome without touching thread lifecycle.
**Consequences:** The "never two concurrent workers for one key" invariant is intentionally gone — a superseded worker runs to completion alongside the new one. Bounded: it does no durable writes and publishes nothing. A narrow race remains where a supersede landing between the check and the write still lets a row through; it fails toward writing, which is the pre-fix behaviour. This is an **API contract change** (a forced request now yields a different `job_id`), so it crossed CLAUDE.md's bright line and was built under full gates, not express.
**Status:** Active.

## D-075 — Arm A Is a Pinned Constant with a Golden, Not a Set of Knobs Someone Remembers
**Date:** 2026-08-18 (three-model bake-off Phase 2; [PLAN.md §1/§3.3/§8](../docs/plans/three-model-bakeoff/PLAN.md), [scope-phase2](../docs/plans/three-model-bakeoff/scope-phase2.md))
**Context:** The bake-off's arm **A** is "the trade engine as it behaved before the 2026-08-16 G6 wave". That engine was modified **in place**, never forked, so arm A has no code to point at — it exists only as nine post-wave knobs at their disable values, plus R4, which has **no knob at all** (`trade.presentment_rules` is its only switch, and that flag is global). Two failure modes follow, both silent: (1) the next knob anyone adds is on by default in arm A, so arm A quietly stops being the baseline and the comparison becomes unfalsifiable with nothing visibly wrong; (2) whoever wires the runner applies the config profile and forgets R4, producing an arm A that is neither pre-wave nor current.
**Decision:** (1) Pin the set as `bakeoff_profiles.MODEL_A_PROFILE` against reference SHA **`92c31d5`** (`20b40db^` on `--first-parent main`), with `MODEL_A_REFERENCE_SHA` in code. (2) Golden-test it: `backend/tests/test_bakeoff_arm_a_golden.py` asserts arm A's deck AND asset-ideas equal output captured by running the same fixture in a worktree at that SHA. (3) The fixture supplies **every generation input as a literal** — player table, consensus board, user board, each opponent's board, confidence counts, roster, outlook, fairness threshold — and calls the generator directly, so it is immune to the board-computation changes (Phase 0's pin fix, tier-bounded voting, premium import) that legitimately moved generation *inputs* since the reference SHA. (4) R4 gets a **thread-local bypass**, `trade_service.r4_bypass()`, in the same style as `_cfg_override`, applied at all three sites that consult the exclusion set — never the global flag. (5) `model_a()` is the only supported entry point and applies both halves, so "forgot the R4 bypass" is not a reachable mistake. (6) **Pin the knob inventory too:** a test carries the full 189-key `_DEFAULT_CFG` key set and fails, naming the key, the moment one is added or removed.
**Alternatives considered:** *An end-to-end golden over a real league fixture* — rejected: it would differ for reasons unrelated to the two waves (Phase 0 alone changes what `comparison_counts` returns), so it would be re-baselined every week until it meant nothing. *Flipping `trade.presentment_rules` off for arm A* — rejected: the flag is process-global, so it would disable R4 for arms B and C and for every other user of that process. *Relying on the golden alone to catch new knobs* — rejected: the golden only fires if the new knob happens to move THIS fixture, which is exactly the case where drift is hardest to notice; hence the inventory test. *Contorting the fixture until `pick_pair_strip_frac` (C3) bites on the deck* — rejected: no matched-pick-pair shape survives the other gates on a realistic league, and manufacturing one would make the golden brittle; C3 is asserted at its own gate instead and recorded as a known gap.
**Consequences:** Adding any `trade_service._DEFAULT_CFG` knob now fails CI until someone decides in writing whether arm A must disable it — deliberate friction, and the point. Changing the fixture invalidates the pin and forces a re-capture; the procedure is in the test's module docstring, and the failure message says explicitly not to re-capture the golden to make a failure go away. Excluded from the profile with reasons in the scope block: the three inert companion knobs, `pass_cooldown_*` (a shared per-job exclusion set built upstream of every arm — differing there would re-serve trades the user dismissed), `force_supersedes_running` (route semantics), and the `pin_*` knobs (PLAN.md §3.4 requires Phase 0's unpinning to stay live for all three arms). Nothing user-visible ships: outside `model_a()` every path is byte-identical, and the only caller today is the test suite.
**Status:** Active.

## D-076 — A Pin Names a Tier, Not a Value: Voting Re-Ranks Inside the Band
**Date:** 2026-08-18 (operator design decision, relayed in-session)
**Context:** [D-069](#d-069--a-pin-is-the-users-newest-word-not-their-last-word-forever) shipped that morning and stopped the audited inversion, but at a price: a still-pinned player scored `n = 0` and priced at *exactly* the consensus seed, so the user's deliberate tier placement counted for nothing, and the release mechanism (F2) needed a pin write-time that none of the 2,735 live pins carried — leaving an unexecuted operator decision about a backfill ([scope-phase0 §6](../docs/plans/three-model-bakeoff/scope-phase0.md)) and 67.8% of all 4,013 comparisons still inert. The operator's call: *"for deliberately placed players in tiers, the voting can just rerank a player within his current set tier. So some adjustment is expected, but nothing massive across a tier."*
**Decision:** `pin_tier_bounded` (default 1.0). A pinned Elo is read as a **tier label** (`tier_for_elo`) and every rating update is clamped to that tier's band (`tier_bands_for` → `tier_config.json`, 165–205 Elo wide). Consequences taken deliberately: (1) **no data is written** — the band is derived at Elo-compute time from the pinned value the board already stores, so all 2,735 pins are covered with no migration, no backfill, and the §6 operator decision is **moot**; (2) `pin_exclude_comparisons` is **narrowed, not reverted** — comparisons still count only when they actually *moved* the player, which now admits every in-band vote as evidence and excludes only the residue the clamp swallowed at a band edge; (3) `pin_unpin_on_newer_swipe` and `pin_legacy_at_epoch` are **superseded and default OFF**, kept and still functional as the Phase 0 revert path; (4) a pin **below the lowest band** (`tier_for_elo → None`: `DEMOTED_ELO`/anchor "no value" = 1100) has no tier and stays frozen; (5) a pin in a band **gap** or above the top band widens its own clamp to `min(lo,pin)`/`max(hi,pin)`, so the clamp can never move an un-voted player.
**Alternatives considered:** *Revert `pin_exclude_comparisons`* — rejected: the direction-blind weight does not disappear under tier-bounding, it relocates to the band edges, and a user who keeps down-voting is exactly the user who ends up there; reverting reinstates the audited inversion for the population most likely to hit it. *Leave F1 as Phase 0 wrote it* — rejected as the larger error: it zeroes confidence for every pinned player, discarding both the placement and the votes now that the votes are real. *Delete the superseded F2 code* — rejected: it shipped hours earlier, other sessions may reference it, and it is the documented revert path. *Let an unranked pin float free* — rejected: 1100 is where a Quick Set pass-over (#161) and the anchor "no value" answer put people, and a stray comparison must not undo an explicit user action. *Clamp a F2-released pin too* — rejected: release means the pin is gone, so half-reverting would make the Phase 0 path not a revert.
**Consequences:** Measured on prod (read-only replay through the real `_compute_elo`): effective comparisons **1,292 → 3,938 of 4,013 (32.2% → 98.1%)**, and **667 of 2,735 pins (24.4%) now move** — 90.3% of the 739 pins that were ever voted on. Expect deck churn on the next generation. A **residual is disclosed rather than hidden**: the step from zero votes to one vote *raises* effective value ~2%, because at `n = 0` the placement carries no weight and the first vote that moves a player gives his board weight 0.2 — every subsequent down-vote reverses it, monotonically, ending below consensus, and direction is respected at equal vote counts. The clean fix is to let a tier placement itself carry confidence, which is a change to what `confidence` means and is out of scope. The band edge is still invisible in the UI — a user can still vote against a wall — and the recommended affordance ("he's at the bottom of *worth a 2nd*, re-tier him to go lower") is a client change, deliberately not built here. **Correction to the audit:** the operator's 18 Adams comparisons are `decision_type = 'trade'`, and trade decisions have never entered `comparison_counts` for any player, so his Elo now moves (1565.28 → 1530.15) while his price does not; the audit's `n = 6` was reconstructed from unfiltered SQL. The mechanism is real, the specific +12.5% attributed to that player is not.
**Status:** Active. Supersedes D-069 items (2) and (4).

## D-077 — A Bake-Off Deck's Order Belongs to the Interleaver; Every Re-Ranker Is Bypassed, Not Re-Applied
**Date:** 2026-08-18
**Context:** Phase 3 of the [three-model bake-off](../docs/plans/three-model-bakeoff/PLAN.md) merges three generators' ranked lists by team-draft interleaving, whose whole purpose is to give every arm the same distribution of deck positions. Five-plus layers currently reorder the deck AFTER generation — `deck.thompson_v2`, A6 diversity + `_cap_per_target`, `deck.fatigue` multipliers, `deck.taste_vectors`, `deck.value_model`, `deck.exploration`'s wildcard insert, `deck.first_session` shaping — and the likes-you injector returns the deck **re-sorted by `composite_score`**. Any one of them running on the merged deck destroys the position balance and converts the bake-off into a measurement of deck position, with no visible symptom: the numbers still look like numbers. PLAN.md §3.4 allows two treatments — bypass for bake-off decks, or apply per-arm BEFORE interleaving.
**Decision:** **Bypass**, gated by one predicate (`bakeoff_runner.bypass_rerankers()`), active only when `trade.bakeoff` is on AND `bakeoff_serve_interleaved = 1`. Layers that only REMOVE cards stay live — F3 decline suppression, because removal shifts every arm equally and dropping it would re-serve durably declined trades. The likes-you injection also stays, with `restore_order()` pinning injected cards to the top (a constant shift, identical for every arm) and returning every arm card to its interleaved index; injected cards carry `model_arm = NULL`. Phase-4 dark validation bypasses **nothing** — it serves arm B through the untouched stack, which is what makes it zero-risk. Also decided here: `elo_freeze_mult()` zeroes the trade-swipe K factors for the run (§3.4 Channel 1), and arm C invokes `trade_gen_v2` directly with `trade_gen.v2` FALSE, because that flag gates the normal serving path rather than the module.
**Alternatives considered:** *Apply the layers per-arm before interleaving* — rejected on three counts: (1) `arm_rank` would then record the presentation stack's opinion rather than the generator's, and `arm_rank` is the field that distinguishes "this model ranks badly" from "this card sat low in the deck"; (2) `deck.fatigue` and `deck.thompson_v2` LEARN from what they serve, so left live they start steering which shapes get served — a contamination channel independent of Elo, and one that differs per arm; (3) it needs a correctness proof per layer, where bypass needs one test. *Leave the layers on and caveat the result* — rejected by PLAN.md §3.4 itself: such a run must be discarded, not caveated. *Skip likes-you injection entirely on bake-off decks* — rejected: a week of Phase 5 without it is a real product regression, and `restore_order` costs six lines. *Freeze `elo_k` too* — rejected: Phase 0 exists to unfreeze boards; re-freezing them would measure models against stale values again, which is the confound Phase 0 was built to remove.
**Amendment (2026-08-18, same session):** a third contamination channel was found by [the trade-logic archaeology review](../docs/reviews/2026-08-18-trade-logic-archaeology.md) and closed the same way — `fairness_threshold` arrives per-request from the client and was persisted **nowhere**, so a per-arm comparison spanning sessions with different client settings would compare arms AND thresholds at once. It is now a `deck_impressions` column (a scalar the analysis groups by, not a `features_json` key), written per CARD because the effective bar is card-dependent (consensus keeps the full bar, divergence rides `fairness_floor_divergence`, a relaxed card rides `relaxed_fairness_threshold`, an arm-C card has none), and per ARM in `bakeoff_runs` because arm A runs under `MODEL_A_PROFILE` and agreement is recorded rather than assumed. `bakeoff_runs.config_json` additionally snapshots the effective config each arm ran under, since `model_config` has no `updated_at` and those knobs are exactly what decides what a recorded threshold means — whole values, not a fingerprint, because a hash says the config changed without saying to what. Recording rather than inferring is not theoretical here: the mobile default flipped 0.75 → 0.50 on 2026-08-17, yet prod shows ≈0.50 back in July.

**Consequences:** During Phase 5 an interleaved deck is served in raw team-draft order — no Thompson exploration, no fatigue discount, no taste, no wildcard, no first-session shaping — so deck quality for participating users is deliberately traded for measurement validity, and the revert is a knob, not a deploy. Impressions on such a deck honestly record `propensity = 1.0` (a deterministic serve). The G6 presentment tripwire's per-job kill counters reflect the last arm to run (arm A, all rules zeroed) rather than the served deck; it is a log line only, and left alone rather than grown into per-arm counters. Arm A's fidelity rests on Phase 2's golden ([D-075](#d-075--arm-a-is-a-pinned-constant-with-a-golden-not-a-set-of-knobs-someone-remembers)): this branch was built against a temporary stub of `bakeoff_profiles.py` and rebased onto Phase 2's real module, so the runner consumes `model_a()` rather than assembling the profile itself.
**Status:** Active.

## D-078 — A Bake-Off Deck Is Composed of Groups, and an Unfilled Quota Is the Finding
**Date:** 2026-08-18 (operator decision, relayed in-session; [scope-composition](../docs/plans/three-model-bakeoff/scope-composition.md))
**Context:** Phase 3 served a bake-off deck as a plain per-ARM team draft over three arms. The operator restructured it: 30 cards from **three groups of ten** — group 1 arm `current`/`divergence`, group 2 arm `current`/`consensus`, group 3 arm `gen_v2` — each split five *value* / five *outlook*, with arm A removed from serving. Four things had to be decided rather than assumed. (1) Arm `current` holds two of the three groups, so a per-arm rotation would give it two of every three slots and leave arm `gen_v2`'s ten cards behind twenty of arm B's — the deck-position confound team-draft exists to remove (~27% acceptance decay across a session from position alone). (2) `window` is only ~19% of live divergence supply (798 value / 193 window over 3,163 recent cards), so the divergence groups cannot reliably fill five outlook slots, and arm `gen_v2` has never served so its lane mix is entirely unmeasured. (3) 132 of 3,163 cards carry **no** lane at all. (4) The operator also decided the user-facing trade settings stay visible during the bake-off (testers briefed verbally), so a tester can move the #172 intent chip mid-test — and `trade_intent` was persisted nowhere.
**Decision:** (1) The **groups**, not the arms, are the team-draft participants, on the unchanged per-deck seed (`sha256("<league_id>|<ISO-week>")`), keeping first-picker credit and `also_proposed_by`. Measured on identical inputs: composing groups then concatenating per arm puts arm C at mean deck position **24.5 of 30**; interleaving the groups puts it at **14.5**. (2) **Fill policy `leave short` by default.** A lane quota the group cannot fill stays empty and the shortfall is recorded per (group, lane) in the new `bakeoff_runs.groups_json[key].short`, alongside the supply it had and what it managed. `bakeoff_fill_policy` = 1 backfills from the same group's own other lane, stamping every substitute `deck_impressions.lane_slot = 'fill'` and **still** recording `short`. (3) **Absent `lane` is its own bucket** — never value, never outlook, reachable only as flagged fill; and when *nothing* in a group's pool carries a lane the axis is undefined for that deck, so the split goes inert (top-N by arm rank, `lane_split_active: false`) rather than serving an empty deck. (4) **Arm A leaves by configuration** (`bakeoff_include_baseline` = 0), never deletion: `MODEL_A_PROFILE`, `model_a()`, the arm-A golden and the knob-inventory guard all stay and keep passing. (5) `trade_intent` is captured per card and per arm as the **effective** value, extending D-077's amendment rule; and arm C now runs the same `_filter_by_trade_intent` and the same `classify_lane` the engine arms already get.
**Alternatives considered:** *Round-robin by arm* — rejected by the 24.5-vs-14.5 measurement; it is the exact confound the design exists to remove, and it fails silently. *Backfill the outlook shortfall from the value lane by default* — rejected: whether an arm can produce outlook-basis divergence ideas **at all** is one of the more interesting things this test can reveal, and a quiet backfill erases the evidence while leaving the deck looking full. *Fail the deck when a quota cannot be met* — rejected: an under-producing arm is data, not an error (PLAN.md §3.2), and it would break decks for real users in Phase 5. *Count an absent lane as `value`* — rejected: `classify_lane` returns None when the outlook axis is **undefined** (no window direction, or `trade.lanes` off), not when the card is value-shaped, so it would inflate the value lane with cards nobody classified and make the comparison depend on how many users declared a window. *Drop unlabelled cards* — rejected: 4% of consensus supply, and it empties the deck entirely for every `not_sure`-outlook user. *Delete arm A / `MODEL_A_PROFILE`* — rejected by the operator: it costs nothing dark and the baseline may be wanted later. *Leave arm C without the intent filter and the lane label and just record the difference* — rejected: those are post-generation **presentment** steps that arms A/B already receive, so omitting them would compare plumbing rather than generators; specifically, an unlabelled arm C would under-fill group 3's outlook quota 100% of the time and read as "arm C cannot produce outlook ideas", a false finding of exactly the kind this composition exists to test for.
**Consequences:** New knobs, all in `trade_service._DEFAULT_CFG` so `bakeoff_runs.config_json` records them by construction: `bakeoff_group_size` 10, `bakeoff_group_value_slots` 5, `bakeoff_fill_policy` 0, `bakeoff_include_baseline` 0; `bakeoff_deck_limit` default changes 0 → 30. Kill values (`bakeoff_group_size` 0 + `bakeoff_deck_limit` 0 + `bakeoff_include_baseline` 1) restore Phase 3 exactly, asserted. New columns `deck_impressions.group_key` / `.group_rank` / `.lane_slot` / `.trade_intent` and `bakeoff_runs.groups_json`, all additive/nullable, no backfill. **The analysis shape is now asymmetric and the report surface must say so:** groups 1 vs 3 is the clean head-to-head (both divergence, both ten, interleaved together), while group 2 is a **consensus reference slice with no arm-C counterpart** — arm `gen_v2` is divergence-only by construction — so reading `current` vs `gen_v2` across all three groups compares arm B's consensus cards to arm C's divergence cards and blames the model; the documented query therefore groups by `(model_arm, group_key)`. Dropping arm A roughly halves the fan-out cost `scope-phase3` §6.2 told Phase 4 to watch (arm A was 4.19 s of 7.36 s — its profile zeroes every gate, so more candidates survive). **`trade.lanes` becomes load-bearing:** with it off no card carries a lane, every split goes inert, and the value/outlook comparison quietly answers nothing.
**Status:** Active. Extends D-077.

## D-079 — Draft-Pick Year Decay Is Per Round, and a First Does Not Decay
**Date:** 2026-08-19 (operator direction, relayed in-session; [review](../docs/reviews/2026-08-19-pick-year-valuation.md), [scope](../docs/plans/pick-year-decay/scope.md))
**Context:** One constant — `pick_values.YEAR_DISCOUNT = 0.85` — discounted every draft pick 15 % per season it sat in the future, regardless of round, on all four pricing paths (`pick_pool_value`, `discount_pick_value`, `database.compute_pick_value`, and the past-horizon tail of `market_pick_pool_value`). A 2029 1st therefore priced at 1300.1 against a 2026 1st's 2117.0 — 61.4 %. The operator reported the consequences three times across two sessions: "1st round picks seem undervalued" and "Another example of a random 1st swap. Shouldn't happen" (2026-08-17), then "I think 2029 1st values are the issue. Adams is rated as a 3rd for me. Offering him for a 1st is nonsense" (2026-08-19). Both symptoms trace to the one constant. (1) At 1300.1 a far-out 1st sat inside a mid-tier veteran's consensus value (Davante Adams, 1138.8), so `overpay_ok` saw a 161.3 gap — under its 500 floor — and served "Adams for a 2029 1st" straight up (impression `c67c2fd1e97cb6bf`). (2) Two 1sts of different years became *different-priced instances of the same asset*, which is free value to a search that maximises delta: **99 of 2048 served cards** moved a 1st one way and a different-year 1st the other. Picks are not a corner of the deck — **58.5 %** of served cards contain one, and firsts are **84 %** of all pick mentions.
**Decision:** The per-year decay is a function of the pick's **round**, read live from `model_config` via `pick_values.year_decay(round)` → `trade_service._c`. **Round 1 is flat (1.0)** — a 2029 1st prices exactly like a 2026 1st — per the operator's direction: "firsts should hold similar value YOY. Other picks can degrade the longer away they are." Rounds 2–4 keep the shipped 0.85; deep rounds clamp onto `_r4`. Four keys (`pick_year_decay_r1..r4`) live in both `trade_service._DEFAULT_CFG` and `_MODEL_CONFIG_DEFAULTS`, so all four at 0.85 restores the old ladder with no deploy. `GENERIC_PICK_SEEDS`, the tier bands and the twelve rungs' Elo are **untouched** — the rungs are current-year assets and were never year-discounted. Inside DynastyProcess's published window the market path is also untouched: DP's own year-over-year price *is* the market's discount and is not re-discounted.
**Alternatives considered:** *Keep one rate for every round but set it to the market's 0.80* — rejected: it prices firsts closer to the outside market but leaves symptom (2) fully intact, because any rate below 1.0 keeps a value gradient between two 1sts and therefore keeps the arbitrage. Flat is the **only** rate that makes first-for-first year swaps structurally impossible rather than filtered. *Add a rule that bans a 1st on both sides of a card* (the operator's own first suggestion on 2026-08-17) — rejected as treating the symptom: the generator would still believe the two picks are worth different amounts and would route the same arbitrage through other shapes (a 1st for a 1st **plus** a player). *Steepen rounds 3–4 relative to round 2* — rejected: no source supports a gradient among later rounds, and the only source that shows one (FantasyCalc) runs the opposite way, its far-out 4ths decaying least. *Ship it behind a feature flag* — rejected: the risk is entirely in the number, not in whether the code path runs, so a config knob at its old value is both a more precise and a more reversible kill switch. *Pin bake-off arm A to the old rate* — rejected and recorded in `docs/plans/three-model-bakeoff/scope-phase2.md`: these knobs price an **asset**, they do not decide which package to build from priced assets, so pinning arm A would confound generation policy with a repricing.
**Consequences:** A 2029 1st moves 1300.1 → 2117.0 (+62.8 %); 2027 and 2028 firsts move +17.6 % and +38.4 %. Rounds 2–4 are numerically unchanged at every horizon. `overpay_ok` flips from pass to kill on the operator's card (gap 161.3 → 978.2, ratio 0.124 → 0.462, against floors of 500 and 0.25). Two deliberate second-order effects: a far-out 1st now badges **`first_1`** instead of `second` on `GET /api/league/picks` (D-320-2's *rule* is unchanged — the badge still reflects today's value, not the pick's name; the value it reflects moved, and the old badge was itself a symptom the operator was reporting), and seven existing test files asserting the old round-1 discount were retargeted. **We are now deliberately pricing firsts above the outside market**, and that divergence is real, not incidental: DynastyProcess publishes an explicit flat 20 %/yr rule, FantasyCalc's 2027→2029 CAGR for firsts is 0.80, KTC's is 0.83, and **three of the four sources discount firsts *harder* than later rounds** — the opposite of the model shipped here. The operator's direction stands as a product call about what this app should recommend; the disagreement is logged as **Q-018** and is one config write to walk back.

## D-080 — Player Preference Is Two Decline Codes, Not One, Because the Two Directions Have Different Engine Fixes
**Date:** 2026-08-19 (operator decision — *"Add it as an option to the 3rd tile. Do the backend DB work to capture it."*; [scope-player-preference](../docs/plans/decline-reason-capture/scope-player-preference.md), [SPEC §2a](../docs/plans/decline-reason-capture/SPEC.md))
**Context:** Decline-reason capture went live 2026-08-17 with a three-tile taxonomy — **Value** (the price) · **Fit** (my roster) · **Neither** (free text only). The first production burst was 19 pass reasons in 9 minutes, and **"Neither" took 9 of them — 47%**, the single largest bucket and the only one with no codes behind it. Reading its free text showed one reason dominating: *"Don't like Troy"*, *"No need to move kelce"* (which arrived with `switched_from = fit`), *"Just not players worth my time"*, *"I just traded marshawn Lloyd away. It doesn't make sense to try and trade back for him."* None of those is a price judgement and none is a roster-construction judgement. The shared `other_player_` stem keeps the axis selectable as one prefix (`detail LIKE 'other_player_%'`) while the suffix keeps the direction. Naming follows the established rule that a layer-2 code is prefixed by its layer-1 code.
**Alternatives considered:** *One code (`other_player`)* — rejected on the argument above; the only thing it buys is one fewer option, and conversion is explicitly not a driver here. *A fourth layer-1 tile ("Players")* — rejected: the operator asked for an option on the third tile, four tiles break the one-row three-tile layout the approved prototype is built on, and it would orphan every historical `other` row against a new sibling. *Parenting `other_player_keep` under **Value*** — rejected, and it is the tempting mistake: "won't give up my guy" *looks* like `value_giving`, but it is attachment, not a market-value assertion — "not this player at any price" is the opposite of a claim about price. Parenting it under Value would also have dragged it into the Elo-keep set. *Capturing the player id* — rejected for this pass: it is a materially larger surface (a picker, PII-adjacent joins, a new column) and the direction alone already routes the fix; revisit once the split shows which direction dominates.
**Consequences:** No schema change and no backfill — `trade_pass_reasons.detail` is a free-form `String`, so the vocabulary lives in `database.PASS_REASON_LAYER2` and `PASS_REASON_PARENT` derives from it; the route's two 400s (`invalid_detail`, `detail_reason_mismatch`) pick the codes up automatically. **No new analytics event and no new property** — `trade_pass_layer2.detail` widens from 8 values to 10, so the emitter is untouched and `NON_INTENT_EVENTS` needs no change. **Elo is unchanged and both codes suppress**, structurally: `PASS_REASON_ELO_KEEP` is an allow-list of `{value_giving}`, so a new code suppresses unless somebody deliberately adds it. **`other_text` keeps its meaning but not its population** — before 2026-08-19 it was *every* "Neither" answer, after it is only what the two player codes did not absorb, so any before/after comparison of `other_text` must be cohorted on that date. Two side effects worth naming: the "Neither" tile now **banks `other_text` before opening the composer** (it previously rendered the box straight from the tile tap and banked nothing, so a tester who bailed left `detail = NULL`) — strictly better SPEC §3.3 compliance; and **SPEC.md was untracked** until this change, so its cross-check in `mobile/tests/check-decline-reasons.js` had never once executed. It is committed and the cross-check runs.
**Status:** Active. Extends D-066 (the decline-reason taxonomy and its Elo rule); the SPEC §2 amendment itself is recorded in [SPEC §2a](../docs/plans/decline-reason-capture/SPEC.md).

## D-081 — The Confidence Band Is Derived from Provenance, Because No Confidence Field Exists
**Date:** 2026-08-18 ([docs/plans/trade-presentation-v2/scope.md](../docs/plans/trade-presentation-v2/scope.md) §2; approved lab `mockups/trade-suggestion-redesign/04-confidence.html`)
**Context:** The approved presentation redesign shows three labeled fit bands — *Strong fit* / *Moderate fit* / *Early signal* — and is explicit that a two-digit percentage must never appear (the OkCupid lower-bound rule: displayed confidence is capped by data volume). Building it revealed that **`TradeCard` carries no confidence field at all.** The nearest analogs are `match_score` (0–100), `fairness` (0–1) and `partner_fit` (0–1) — every one of them a score, and two of them winner-shaped. The build brief was equally explicit that a missing field should be recorded, not approximated. The obvious shortcut — bucket `match_score` into three bands — would have been an approximation of exactly the kind the surface exists to prevent: `match_score` is deal *compellingness*, not our confidence in it, so a thin-data card with one wild valuation scores high and would have been endorsed.
**Decision:** Derive the band from the two **data-provenance** fields the backend already ships, and nothing else: `basis` (`divergence` = the card came from a real disagreement between two saved boards; `consensus` = the counterparty has not ranked and was priced off the consensus seed) and `real_opponent` (their Elos are their actual saved rankings vs noise-randomized). Both real ⇒ *Strong*; exactly one ⇒ *Moderate*; neither ⇒ *Early signal*. A reciprocated `likesYou` promotes to *Strong* — the counterparty liking the mirror is stronger acceptance evidence than any inference from their board. Only a *Strong* card may wear the endorsement, and the badge is binary. Separately, the data-volume **cap** reports the user's real overall board coverage from the existing `GET /api/rankings/progress`; the lab's per-deal denominator ("34 of the 60 players this deal touches") is **not shipped**, because per-deal coverage exists nowhere.
**Alternatives considered:** *Bucket `match_score`* — rejected above; it measures the wrong thing and fails silently on exactly the thin-data cards the bands exist to demote. *Bucket `fairness`* — rejected: fairness is package balance, orthogonal to how much we know about either board; a perfectly balanced trade between two empty boards is not a strong fit. *Use `partner_fit`* — rejected twice over: it is serialized only under `trade.finder_targeting` with user-stated targets, so it is absent on most cards, and rendering a counterparty fit **number** is precisely what the asymmetric confidence *statement* replaces. *Add a server-side `confidence_band`* — the right long-term answer, but out of scope for a client-only, flag-off branch, and the brief forbade adding backend surface.
**Consequences:** The derivation lives in one pure function, `confidenceBand()` in `mobile/src/utils/tradePresentation.ts`, is executed (not grepped) by `mobile/tests/check-presentation-v2.js` across all four provenance combinations plus the `likesYou` promotion, and carries a header comment saying **"if a server-side `confidence_band` ever lands, delete this and read the field."** Two honest limitations follow and are documented rather than hidden: the band cannot distinguish *how much* either board holds (only whether it is real), and a league of active FTF rankers will see mostly *Strong* while a cold league sees mostly *Early* — which is the truth, and is why the cap sentence and the ranking prompt sit on the card. Endorsement is genuinely refusable: when no card is *Strong*, `partitionDeck` returns **no hero** and the surface renders the honest empty state rather than promoting a *Moderate* card.
**Status:** Active.

## D-085 — A Deliberate Tier Placement Bounds How the Engine PRICES a Player, Not Just How Voting Moves Him
**Date:** 2026-08-19 (operator decision — chosen from three presented options; [scope](../docs/plans/placement-tier-clamp/scope.md), [code-walk](../docs/plans/placement-tier-clamp/code-walk.md))
**Context:** The trade engine never prices a player at the user's own Elo. `trade_service._shrink_user_elo` blends toward the consensus seed with `w = n/(n + shrink_pseudocount)` (n0 = 4), where `n` is `RankingService.comparison_counts()` — distinct opponents whose comparison actually MOVED that player's Elo. Shrinkage exists for a good reason and must be preserved: a player the user never compared has a *default*, not an opinion, and trusting it manufactures fake divergence. The gap is that `w` counts **samples** and cannot see **assertions**. A manual tier placement (an Elo override, `_elo_overrides`, written by a tier save or drag-reorder) is the strongest statement of value the product accepts, and it contributed nothing to `w`. The operator's live case, confirmed by replaying his board out of read-only prod: **Davante Adams placed in `third` [1280, 1365], consensus 1526 (`second`), priced at 1490.8 — `second`, a full tier above where he was put.** The mechanism is sharper than "he was barely compared": Adams has **36 distinct comparison opponents** and is one of the most-voted players on that board, but his live `comparison_counts` is **1**, because `pin_exclude_comparisons` (F1) correctly discards votes that a tier-bounded player's band edge swallowed. So `w = 0.2` and the engine priced him **80 % consensus** *despite* 36 votes and an explicit placement. F1 narrowing which comparisons count and this defect are the same phenomenon seen from two ends.
**Decision:** Clamp the shrunk personal Elo of a **placed** player to the Elo band of the tier he was placed in — `RankingService.placement_bands()` → `tier_config.json`. Consensus may still re-price him *inside* that band; it may never carry him out of it. This is the operator's own already-shipped voting rule (`pin_tier_bounded` — *"the voting can just rerank a player within his current set tier ... nothing massive across a tier"*) applied one layer further out, to how the engine PRICES the result; the two were inconsistent and now agree. Knob **`placement_tier_clamp`** (default **1.0**, kill **0.0**). The band derivation is factored into one function, `ranking_service._placement_bands`, that both `_pin_bounds` (voting) and `placement_bands` (pricing) call, so the two definitions of "the tier the user placed him in" cannot drift. `MODEL_A_PROFILE` pins the knob to 0.
**Alternatives considered:** *Pseudo-count bonus* (`n += bonus` for placed players) — rejected by the operator: it only slows the drift, still lets a placement cross a tier, and buries the rule in an arbitrary constant. *`w = 1` for placed players* — rejected: it makes a **mis-placement uncorrectable**, since no amount of later voting could move the priced value. The clamp is applied **after** the blend precisely to preserve correction: a user who keeps voting a placed player down still moves him inside the band, and the clamp's displacement decays to exactly zero once `n` is large enough to carry the blend back inside on its own. *Make `_value_uncertainty` placement-aware* — rejected deliberately, not by omission: that half-width feeds a **GATE** (range-overlap fairness), and gates price the real package on real consensus values; narrowing it for placed players would silently change what the gate lets through. Also wrong on the merits — a placement bounds *where* the point estimate sits, it asserts nothing about precision *inside* a band 45–205 Elo wide. Pinned by an `inspect.signature` assertion so a future edit is a decision, not a drive-by. *Clamp unplaced players too* — rejected: it would freeze the entire board at consensus.
**Consequences:** Measured by rebuilding the operator's real `RankingService` from read-only prod (625-player pool, 624 pins, 1,679 swipes replayed) under the live configuration: Adams moves **1490.8 → 1365.0**, back into the tier he was placed in. Across that whole board, **162 of 615 banded placements (26 %) move**, median 32 Elo, max 343. Placements are **not** rare — 5 of 18 users have them and the three active boards carry 547–737 each. The largest movers are `n = 0` players, placed but never compared, whose blend was **pure consensus** with the placement contributing literally nothing. **Two populations are deliberately never clamped:** unplaced players (see above), and pins **below the lowest band** — `tier_for_elo` returns `None` under 1150, which is the #161 `DEMOTED_ELO` and the anchor "no value" answer at 1100. Those are "unranked, pending placement" markers, not valuations; clamping into a sub-1150 non-band would price a player at ~nothing on the strength of a marker the user never meant as a value. **Known and intended:** while consensus sits outside the band the priced value rests on the near edge, so further voting inside the band does not move it — correction is re-placement, or enough votes to carry the blend back inside. **No gate changes, verified by what the gate reads:** the range-overlap fairness gate prices `gvals`/`rvals` from `seed_value` (consensus), never `user_value`, so the clamp is structurally invisible to it. **`tier_config.json` is untouched**, so the five-client band mirror needs no work and no client release. **The bake-off cannot currently measure this:** `bakeoff_runner.gen_v2_cards` never passes `placements`, so the clamp is inert on every arm; that file was left alone on purpose because two sibling agents were editing it concurrently. Follow-up, not a defect.
**Status:** Active. Extends `pin_tier_bounded` (2026-08-18 operator design call) from the voting path to the pricing path. **Committed to `feat/placement-tier-clamp`, not pushed and not merged.**

**Does this explain the `basis: consensus` finding? No — and the framing was wrong.** The work was motivated by "every one of the 40 most recently served cards came back `basis: consensus`". Read-only prod on 2026-08-19 shows the last 40 impressions at **30 consensus / 10 divergence (25 %)**, the last 400 at 7.8 %, and all time at 12 % — divergence is being found. More importantly, `basis` is decided by `trade_service.py:4105` (`member.has_rankings and member.elo_ratings`) — a property of the **OPPONENT's** board, evaluated before any user value is consulted — or by the zero-divergence fallback at `:4175`. The clamp can only influence the second. Whether it does is **not determinable from the impressions table**, because the table does not record *why* a consensus card was consensus. Recommended follow-up: instrument the fallback to distinguish "opponent unboarded" from "divergence path came back empty". Until then, this clamp must not be reported as the cause of the consensus share.

**Date:** 2026-08-19 (agent session `fix/bakeoff-outlook-lane`; [scope](../docs/plans/three-model-bakeoff/scope-outlook-lane.md))
**Context:** The operator reported the bake-off's outlook lane filling **0 of 5 slots**, and 10-card decks arriving from an arm that had generated 37–40 candidates — the pair of symptoms that put `bakeoff_serve_interleaved` back to 0.0 (dark) on 2026-08-19. Read-only prod, all 18 `bakeoff_runs` rows of that day (54 group-runs, 527 pooled cards), settles which of three hypotheses was true. **Not plumbing:** the `(none)` bucket is 0 in *all 54* group-runs — every pooled card carried a `lane`, so `classify_lane` ran everywhere and `window` is **24.7%** of live supply, not ~0% (`current_consensus` 28.1%, `gen_v2` 16.2%, `current_divergence` **0/23**). The one plumbing instance of this class, gen-v2 cards carrying no lane at all, had already been found and fixed. **Partly supply:** `current_divergence` averages **1.3 cards of any lane** against a 10-card group size — its group is empty, not just its outlook lane. **Mostly quota:** a 5/5 split asks every group for 50% outlook from a 24.7%-outlook supply, so it is unfillable by arithmetic — but the loss was not the empty outlook slots, it was that **the value lane was capped at 5 and forbidden to use them**. Decomposed per run: target 30, supply generated 29.3, within-group capacity `Σ min(pool, 10)` **16.0**, actually served **13.8**. The 16.0→13.8 step is **40 of 288 fillable slots destroyed by the lane split alone**; the two 10:33 runs held a group of ten value cards for ten slots and served five. (The 30→16.0 step is a different defect — the group partition strands surplus, e.g. 37 cards in one group and zero in the other two — owned by the concurrent arm-C forfeit work, untouched here.)
**Decision:** **Lane reallocation**, new knob `bakeoff_lane_reallocate`, default **1 (on)**. After the nominal quota is taken, each lane extends into the slots the other lane provably could not fill, **drawing only from its own bucket**. No card ever occupies the other lane's slot, so `deck_impressions.lane_slot` stays literally true — that is the whole distinction from `bakeoff_fill_policy` = 1, which substitutes *across* lanes and flags the substitute `fill` precisely so analysis discounts it. `short` is computed against the nominal 5/5 ask **before** reallocation and is never touched; the spill is recorded explicitly in `groups_json[key].realloc`, so a lane's `filled` exceeding its `quota` is readable rather than inferred. Priority between the two extensions is provably irrelevant: a spare slot exists only because some lane's bucket was exhausted, so at most one lane can have a tail.
**Alternatives considered:** *Re-tune `bakeoff_group_value_slots` to match measured supply* — the option the brief explicitly sanctioned, and rejected on its own arithmetic: replaying the 54 real group pools, a fixed 7/3 (the closest match to 24.7%) reaches 15.6 cards/run while reallocation reaches **16.0 at every split from 5/5 to 10/0**. A magic number buys less and has to be re-tuned whenever supply drifts. *Flip `bakeoff_fill_policy` to 1* — rejected: it serves the same cards but mislabels them, stamping `lane_slot = 'fill'` on cards that never left their lane, and it overturns D-078's default rather than refining it. *Lower the outlook quota to 0 for the divergence groups* — rejected: it hides the 0%-window finding, which is the thing the test exists to surface. *Do nothing and report* — rejected: the deck-size loss is the stated precondition for taking the bake-off out of dark.
**Consequences:** Deck size on the measured pools goes **13.8 → 16.0 cards/run**, and the 10:33 shape 18 → 27 (pinned as a regression test against the real numbers). The remaining 16.0 → 30 gap is supply distribution across groups, not lanes, and is named as such rather than absorbed. **Nothing D-078 protects is weakened:** `short`, `pool` and `lane_split_active` are bit-identical, asserted directly (`on[G1]["short"] == off[G1]["short"]`). `bakeoff_fill_policy` still works and still means what it meant, but with reallocation on it can only draw from the unlabelled `(none)` bucket — both lane buckets are already drained — so a `fill` is now unambiguously "a card with no lane at all", which is a cleaner definition than the one it replaces. One new `_DEFAULT_CFG` key, so `bakeoff_runs.config_json` records it by construction and the knob-inventory guard gets a row in `scope-phase2.md` (composition, not generation — no arm can observe it). Revert lever: `bakeoff_lane_reallocate` = 0 restores the pre-D-086 composition byte-for-byte with no deploy, asserted end to end. **`bakeoff_serve_interleaved` is NOT touched** — it stays 0.0 (dark); re-lighting it is the operator's call. Open follow-up: `current_divergence`'s 0/23 window rate is a genuine signal against `gen_v2`'s 16.2% on the same user and week, but n=23 is too small to call — logged as [Q-020](OPEN_QUESTIONS.md).
**Status:** Active. Refines [D-078](#d-078--a-bake-off-deck-is-composed-of-groups-and-an-unfilled-quota-is-the-finding) — the leave-short *measurement* is kept in full; only the deck-size penalty that used to accompany it is dropped. **Committed to `fix/bakeoff-outlook-lane`, not pushed and not merged.**

## D-087 — A Bake-Off Arm That Produced Nothing Records the STAGE It Died At, Because "Starved" and "Gated" Are Different Findings
**Date:** 2026-08-19 (investigation of arm C's `cards=0, forfeits=9`; [scope](../docs/plans/three-model-bakeoff/scope-arm-c-diagnostics.md))
**Context:** Arm C (`gen_v2`) had never served a card, and its production signature — `cards=0, forfeits=9` against arm `current`'s `cards=40` — read as a broken generator. It is not. Read-only against prod, the pattern is **per-league, not per-time**: across all 18 `bakeoff_runs` rows, `cards=0` occurs only in leagues `62846` and `11896`, while league `1312140920132497408` returned 6–16 cards in every one of its 11 runs. `member_rankings` explains it exactly — `62846` has **zero** rows, `11896` has rows for one user (the requester himself), `1312…` has 4,416 across 6 users. Arm C is divergence-only by construction, so a league with no boarded *opponent* gives it nothing to diverge from; the 3 ms generation time in `62846` against 221 ms in `1312…` is the pipeline returning at the `boarded` loop before enumerating anything. The apparent "improvement over the night" (9 forfeits → 2) was two different leagues being compared, not one league improving. The reason no impression carries `model_arm='gen_v2'` is separate and also not a generation fault: `served_arm` is `'current'` on every run because `bakeoff_serve_interleaved` is `0.0` (dark), so `server.py:3950` can only ever stamp `current` or NULL — arm C already contributed 6 of 6 composed cards to the *interleaved* deck it just does not serve. The tempting counter-reading — *divergence supply is 15.2 % all-time, so arm C had input and must be defective* — does not survive a per-league split: **96.8 % of all divergence impressions (1,196/1,235) come from the single league with ≥3 boards**, and `62846`/`11896` have **zero divergence impressions ever**. The control settles it: in those leagues arm `current`'s own `current_divergence` group pool is **0 in all six runs**, exactly like arm C — while in the boarded league arm C's pool runs 6–16 (median 7) against arm `current`'s 0–7 (median 1), with arm `current` producing no divergence at all in 8 of 11 runs. **Arm C out-produces arm `current` on the divergence axis in 11 of 11 runs where input exists.** It is the strongest divergence generator in the bake-off, and its zeros are the leagues where nobody can produce divergence. **The defect was that none of this was visible.** `GenerationReport` already counted every gate, `gen_v2_cards` threw it away, and the three distinct starvation causes produced byte-identical all-zero reports.
**Decision:** Record the **stage**, not just the count. `GenerationReport` gains three supply counters (`boarded_opponents`, `pairs_no_board_overlap`, `pairs_no_centerpiece`) and a `kill_counts()` method — modelled on `TradeService.presentment_kill_counts()`'s flat per-rule dict — that emits the whole pipeline in order, `S0` supply → `S1` selection → `S2` enumeration → `S3a-d` the hard gates → `S4`/`S6`, plus a derived `starvation_reason` that is **non-null only when nothing was ever enumerated** (`no_boarded_opponents` / `no_board_overlap` / `no_divergence`). `bakeoff_runner.gen_v2_cards` keeps the report it used to discard, adds its own two post-generation kills (`S7_intent_filter`, `S7_headliner_cap`), and hands the dict to the fan-out through a thread-local drained on read; it lands on `bakeoff_runs.arms_json[arm].diagnostics`. **No generation behaviour changes** — no gate, knob, pool or ordering rule is touched, and the two starvation exits now counted were already bare `return []`.
**Alternatives considered:** *Loosen `gen2_min_divergence` or add a consensus fallback to arm C so it always produces something* — rejected, and this is the load-bearing rejection: arm C exists to test the divergence-driven hypothesis, and a consensus fallback would make it a second copy of arm `current` wearing arm C's name, destroying the only comparison the bake-off is for. Silence in a boardless league is the correct output. *Widen the `gen_v2` callable's signature to return the report* — rejected: `gen_v2` reaches `run_bakeoff` as an opaque `Callable[..., list]` bound by the caller, so widening it would touch every arm; a thread-local mirrors the existing `presentment_kill_counts` stash and stays inside the arm-C path. *Gate the diagnostics behind a knob* — rejected: a diagnostic that can be switched off will be off when it is needed, and the whole surface already sits inside the default-OFF `trade.bakeoff` flag. *Fill `diagnostics` for the engine arms too* — deferred, not rejected: `presentment_kill_counts()` accumulates across a job and needs a per-arm reset inside the fan-out, which is in a file a concurrent session is editing.
**Consequences:** A zero-card arm is now self-diagnosing: `starvation_reason` distinguishes "the league has no boards" from "the boards agree" from "a gate killed everything", which are three different fixes and were one indistinguishable symptom. A real accounting bug went with it — `run_row` looked forfeits up by ARM name against a dict keyed by GROUP, so arm `current` (groups `current_divergence` + `current_consensus`) recorded a flat `0` in **all 18 rows ever written**, while arm C's single-group key happened to match; `BakeoffRun.forfeits_for_arm` now sums over an arm's groups, so the published "current 0 / gen_v2 9" contrast was partly an artefact of key spelling and prior runs' `current` forfeits are unrecoverable. Two limits are the operator's, not the code's: **arm C still cannot reach a user** while `bakeoff_serve_interleaved` stays `0.0` (deliberately untouched), and **arm C can only be evaluated in league `1312140920132497408`** — board supply, not model quality, is the binding constraint on this experiment. `pytest backend/tests` 3441 → **3449 passed, 1 skipped** (+8 tests).
**Status:** Active. Committed to `fix/armc-gen-v2-forfeits`, **not pushed and not merged**. Extends [D-078](#d-078--a-bake-off-deck-is-composed-of-groups-and-an-unfilled-quota-is-the-finding)'s "an unfilled quota is the finding" rule from group under-fill to arm attrition.

## D-088 — The Pick Badge Inverts With `value_to_elo`; the Round-3 "Overprice" Was a Wrong Inverse, Not a Price
**Date:** 2026-08-19 ([memo](../docs/reviews/2026-08-19-pick-badge-scale.md), [scope](../docs/plans/pick-badge-scale/scope.md)); closes [Q-019](OPEN_QUESTIONS.md), opens [Q-020](OPEN_QUESTIONS.md)
**Context:** After [D-084](#d-084--round-2-of-the-pick-ladder-is-repriced-to-market-rank-and-the-tier-floor-moves-with-it-in-the-same-commit) lowered `second.min` to 1370, a **current-year 3rd-round pick began badging `second`** on `GET /api/league/picks`, at Elo 1383.5. D-084 recorded this as the pre-existing round-3 overprice becoming visible and logged it as Q-019, on the reasoning that `seed_elo_for_value`'s floor compression made rounds 3–4 unfixable from `GENERIC_PICK_SEEDS`. **The compression claim is true — I re-derived it: on the checked-in `dp_values_snapshot_2026-07-10.json`, ranks 200→300 span Elo 1262.9 → 1208.0, i.e. 100 ranks inside 54.9 Elo points, one EIGHTH the per-rank resolution of ranks 50–100 — and it does make market-rank alignment for 3rds/4ths unreachable via seeds.** It is also not what caused the badge. `draft_picks.pool_value` is stored in **`elo_to_value` units** (`database.py:1040` says so), whose exact inverse is `trade_service.value_to_elo`; `seed_elo_for_value` inverts a *different* map, DynastyProcess's raw 0–10000 consensus scale. The two agree at **exactly one point, Elo 1548.0** (solve `223.130 + 0.824487·v = v`), and diverge either side, so the badge inflated everything cheaper than a mid-1st by a growing amount: Mid 3rd **1320 → 1383.5 (+63.4)**, Mid 4th **1240 → 1339.3 (+99.3)**, Late 4th 1220 → 1329.5 (+109.5). The pick's real price was never 1383.5 — it is Elo 1320, **45 points inside the `third` band**. The map error alone was 4.7× the 13.5-point margin that flipped the badge. #320's own comment shows the hazard was known (*"never `pool_value` passed straight in… the exact #263 bug"*) — it reached for an inversion and reached for the wrong one.
**Decision:** `server._pick_tier` inverts with **`trade_service.value_to_elo`**. `seed_elo_for_value` is removed from `server.py`'s imports with a comment saying why, so the wrong tool is not within reach in the file that handles value-scale numbers. The rule generalises into `docs/cross-client-invariants.md` as a two-row table — engine values invert with `value_to_elo`, DP values with `seed_elo_for_value` — and the invariant is pinned as a *property*, not a literal: a current-year pick of round R must badge exactly where `GENERIC_PICK_SEEDS[(R, "Mid")]` sits, because `tier_config.json`'s `_calibration` **defines** the band floors as those rungs. `GENERIC_PICK_SEEDS`, `tier_config.json`, all five client mirrors and every stored `pool_value` are byte-unchanged.
**Alternatives considered:** *Move the round-3/4 seeds* — rejected: Elo 1320 is not the defect, and D-084 already measured that path breaking `test_tier_occupancy.py` in three places. *Move the `third`/`second` band edges* — rejected: nothing about the bands is wrong, and it would drag all five mirrors ([G-051](GOTCHAS.md)) to work around an arithmetic error. *Re-anchor `seed_elo_for_value` to decompress the floor* — the change Q-019 and the D-084 memo pointed at, and genuinely open, but it moves **every player's seed Elo in the app** (occupancy, decks, matchups, every user's board) and would not have fixed the badge, which was wrong on ten of twelve rungs regardless of where players sit. Re-logged as Q-020. *Clamp or special-case round 3* — rejected as papering over a defect present across the ladder.
**Consequences:** **Display-only, and larger than the reported symptom: 600 of 1,104 live pick rows (54.3 %) change badge**, measured by recomputing both inverses over the actual stored `pool_value`s in prod (7 leagues, read-only). 538 move down, 62 up (stale pre-D-079 2028 1sts at value 1529.5 → Elo 1585, above the Late 1st rung, `second` → `first_1`). The two rungs the report named are both fixed and now land on their own round's name: a current-year 3rd `second` → **`third`**, a current-year 4th `third` → **`fourth`** (that one had been wrong since #320 shipped and nobody noticed, because `third`'s old max of 1395 covered the inflated 1339.3). **One badge disappears rather than dropping**: a 2029 4th prices at Elo 1142.5, below the `waivers` floor of 1150, so `tier_for_elo` returns `null` and the client falls back to the numeric — the documented null-tier contract, and more honest than claiming a 2029 4th is worth a 3rd-round pick. **Nothing about pricing moves**: `pool_value` is never written, the trade engine, deck, calculator and `test_tier_occupancy.py` (47 passed, unchanged) are untouched, and no tier band moved — so the five-mirror bright line is not triggered, as a consequence of choosing the display-path fix rather than by omission. **The blast radius argues against ever repricing rounds 3–4:** read-only prod shows 3rd-round picks in **27 of 2,376 served cards (1.1 %)** and 4th-round picks in **zero**; picks overall are in 55.9 % of cards, of which firsts are 80.9 % of mentions. Deep picks barely touch real decks — which is exactly why the correct answer here was a badge fix, not a ladder move.
**Status:** Active. Third correction of the #263 value-vs-Elo scale-confusion class (#263 → #320 → this); the cross-client table exists so there is not a fourth. **Committed to `fix/pick-round3-value`, not pushed and not merged.**
## D-089 — Settings Is a Pushed Page, Not a Modal; #130's ✕ Is Removed Rather Than Reverted
**Date:** 2026-08-19 (settings-IA build, branch `feat/settings-ia-hub` — [plan §5](../docs/plans/settings-ia-hub/plan.md), [scope §2](../docs/plans/settings-ia-hub/scope.md))
**Context:** Settings shipped as a native-stack `presentation: 'modal'` page sheet. That presentation caused two live defects, both of which the settings-IA review found independently of each other. **F5:** a page sheet cannot push, so `navigateFromSettings` had to `goBack()` and *then* `navigate()` for every outbound link — which is why Back from SleeperConnect lands on the tabs instead of on Settings. **F6:** #188 exempts modals and sheets from the `FeedbackFAB`, so the one screen where a user is most likely to have an opinion about the app had no way to report it. Separately, feedback **#130** had already found the presentation's other cost — swipe-down-to-dismiss is undiscoverable — and fixed it by adding a header ✕ (`HeaderClose`, testID `settings.close-btn`) in `headerRight`.
**Decision:** Drop `presentation: 'modal'` from the `Settings` route. It becomes a plain push wearing the #151 explicit `HeaderBack` (native back is dead on iOS 26 over a `headerShown: false` previous screen — RNS#3294), `navigateFromSettings` collapses to a plain `navigate`, and every settings page mounts a `FeedbackFAB`. **#130's ✕ is REMOVED, not reverted:** the complaint was real and the fix was correct for a modal, but a pushed page's back chevron is the discoverable control #130 was reaching for, in the position users already look for it. `HeaderClose` and `settings.close-btn` are deleted, and `check-settings-testids.js` asserts the id is gone from `mobile/src` and from the two Maestro capture flows that anchored on it. **A future session must not re-add `presentation: 'modal'` citing #130** — doing so restores the `navigateFromSettings` hack (F5) and re-exempts Settings from the feedback surface (F6). The presentation flip is deliberately registered on the ROUTE, **outside** `account.settings_hub`, so it applies in both flag states.
**Alternatives considered:** *Keep the modal and just reorganize the content* — rejected: it leaves F5 and F6 in place, and F5 is a navigation bug users have reported. *Make the presentation flag-conditional* — rejected, and this is the load-bearing rejection: two navigation topologies means `navigateFromSettings` needs two escape paths and `settings.close-btn` has to exist on one arm and not the other, which no structural check can then assert; it also leaves the flag-off (shipped) surface carrying both bugs, i.e. broken for exactly the users a rollback is meant to protect. *Restyle the tree as a native iOS inset-grouped list while we are in here* — rejected: [ADR-008](../docs/adr/adr-008-teardown-remediation-wave.md) already weighed and rejected native settings-list styling in favour of one design language wholesale, and nothing here changes that argument. The hub and all seven pages are Chalkline throughout — hairline rows on `--ink-0`, `TickLabel` group banners, no inset cards, no grouped-table chrome.
**Consequences:** Swipe-**down**-to-dismiss is gone in both flag states and cannot be restored by a flag — only by a code change and a new build. The operator accepted this on 2026-08-19; swipe-**right** still dismisses, and the back chevron is now always visible. `account.settings_hub` therefore covers the *content* (hub vs flat list) and not the *presentation*, which means the flag is a narrower rollback lever than [scope §2](../docs/plans/settings-ia-hub/scope.md) originally claimed; that section is corrected in place. Plan §9's TestFlight checklist item 1 is the only runtime evidence this change will get under [D-056](#d-056--maestro--simulator-retired-entirely-not-just-as-a-gate), and it is **unrun**.
**Status:** Active.
