Fleeced API Audit

Every HTTP call in the app, read statically across all four layers and re-verified by hand. Nothing was changed. Counts are per code path, not measured traffic. The scarce resource is Sleeper calls: they are rate-limited and most of them run inside the session-init daemon the user is waiting on.

Deploy context: render.yaml:16 runs one gunicorn worker, so in-process caches do share across requests. The gap is that the base Sleeper fetcher (server.py:564) has no cache at all, and the single league-meta cache that exists (26472) is consulted by 2 of its 9 callers.

Ranked findings

Severity weighs wasted calls × how often the path runs × upstream cost. High means it burns Sleeper budget or user-visible latency on every launch.

01

Trades sync walks all 18 weeks on every app open

backend → sleeperhigh
sleeper_trades_service.py:128-143 · :40 WEEKS = range(1, 19) · called from server.py:19591

One transactions fetch per week, every session init, year-round. Only the live week can change and the insert is idempotent, so ~17 calls are wasted per init. A Sleeper outage costs up to 18 × 15 s of daemon time.

Fetch only the current week, with a one-time per-league backfill flag; or move the sweep to the daily tick.

02

Session-init daemon re-fetches rosters and league meta per consumer

backend → sleeperhigh
server.py:19497-19520 trade block · 11693-11694 owned picks · 15872-15884 draft status · 19424-19427 auto-detect · suggestion_telemetry.py:377

The comment at 19497 says "fetch ONCE here, hand it to both consumers." The trade block gets the shared rosters; the owned-picks sync fetches rosters and meta again on its own, and draft-status fetches meta, drafts and rosters a third time when its TTL lapses. Scoring auto-detect reads the stored format into existing_fmt and then calls Sleeper regardless, despite the comment above it saying the call is skipped once stored. Three identical is_linked_platform_league reads (19504, 19549, 19623) and a duplicate get_league_scoring (19185, 19424) ride along.

Thread the shared rosters and one meta read into the owned-picks and draft-status calls; gate auto-detect on existing_fmt; hoist the repeated SELECTs.

03

Mobile rebuilds the whole session on every launch and resume, never pinging first

mobilehigh
useSession.ts:363-383 · auth.ts:377, 416-418, 239 · App.tsx:117, 210 · dead: auth.ts:320 sessionPing

Revalidate means GET rosters + GET users + POST session init, plus GET and POST on the Sleeper link when unverified. It runs at boot and on every foreground older than 60 s. Each run pays findings 1 and 2 server-side and kicks a trade pregen. The cheap liveness probe exists and has zero callers.

Ping first; re-init only on a 401. That fully covers the FB-45 concern that a deploy kills in-memory sessions.

04

Web downloads the 4.8 MB players blob three ways and never reads it

webhigh
app.js:625, 771, 2387 · parser app.js:121-139 · warm route server.py:18754

Each call site checks only pr.ok. The shared fetch wrapper then clones, reads and JSON-parses every response to build a summary string that nothing reads, so the full blob is parsed on the main thread for no output. The warm endpoint already returns a few hundred bytes; its comment claiming the web client consumes the body is wrong.

Point web at the warm route, delete the summary block, then retire the raw players route (positional-tiers uses the DB-backed players endpoint, not this one).

05

Mobile fetches rosters and users for the init body, discards them, then re-fetches per screen

mobilehigh
auth.ts:416-430 · re-fetched at TradesScreen:2762, 2772 · InLeagueCalculator:423 · TradeDnaSheet:353 · TradeFinderHub:284

No query-cache seed follows the init fetch, so four screens request the same two proxy endpoints again. Combined with finding 3, that is four proxy calls per launch for data the server just rebuilt into league members.

Seed the roster and users query keys from the init path; or let session init accept a league id and pull rosters server-side, collapsing three requests into one and removing the client-side Sleeper proxy hop.

06

Web fires five requests per ranking swipe; three are redundant

webhigh
app.js:1445, 1485, 1493, 1779, 1797, 2635 · rank3 already returns the counts: server.py:7631-7634

The swipe response carries the progress fields, then the client fetches rankings progress, waits 350 ms, loads the next trio, fetches progress again, and fetches rankings progress a second time. Roughly 120 wasted requests per user reaching the unlock threshold.

07

Web polls notifications every 30 s and never pauses

webhigh
app.js:4802 · cleared only at :275 logout · no visibilitychange handler in app.js

A backgrounded tab issues 120 requests an hour indefinitely. Mobile, by contrast, does not poll at all and relies on push, which is the right shape.

08

Web league switch runs the full boot twice

webmedium
app.js:2372-2461 · location.reload() at 2461 · dead code after the return at 2462

The switch fetches players, rosters and users and posts session init, then reloads the page, and boot repeats every one of those calls including the 4.8 MB one.

09

Hourly draft-status sweep has no season gate and no active-user filter

backend cronmedium
server.py:21135-21141 · TTLs 15797-15801 · database.py:9653, 11529 · daily rosters server.py:20763

Up to 50 leagues × 3 Sleeper calls per tick, over every league row ever synced. An undrafted league is re-probed every 3 hours, which is 24 calls a day per league for the nine months no draft can happen. The daily roster sweep fetches the same rosters on its own and also sweeps every league ever synced.

Gate the draft sweep on the rookie-draft window; filter both sweeps to leagues with a session in the last N days.

10

Trade job loads preferences and picks two to three times

backend cpumedium
server.py:12067-12070 request · 5936, 5972, 5758, 6009 worker · N+1 at 6003 · bulk loader database.py:9132

The request thread reads preference and outlook for the cache key; the worker re-reads both, and the outlook path loads draft picks which the worker loads again. Inside the members loop each opponent's preference is a separate query although a bulk loader exists and is already used by the trade breaker. This runs on every session init through pregen.

11

Mobile trade pregen fires on every launch, not just the first session

mobilemedium
tradePregen.ts:64-78 · useSession.ts:376 · races TradesScreen:2213-2220

Gated only on the two onboarding flags (both true) and a per-launch dedupe. It races the Trades screen's own auto-generate; the server dedupes a fresh job, so usually one wasted POST. Unproven whether a POST landing mid-init produces a second job.

12

Trades landing mounts five ungated calculator queries

mobilemedium
TradesScreen:7596 · InLeagueCalculator.tsx:412-450

With the inline-calculator flag on, trade values, rosters, picks, power rankings and coverage all fire on the Trades tab whether or not the canvas is opened. Power rankings is not a cheap route.

13

Format-default applier writes on every boot, then invalidates what just resolved

mobile + webmedium
useScoringFormat.ts:60-73, 89-116 · web positional-tiers.html:2659, 2866, 2884, 2678

Mobile posts a scoring switch even when it equals the active format, then invalidates progress, rankings, streak, trio, tiers status and trends. The web tiers page posts the same switch on every page view, twice on toggle, then awaits four rankings fetches in series.

14

ESPN link reads the same league three to six times

backend → espnmedium
server.py:24372, 24436-24452, 24249, 24800, 24810

Oracle read, then every linked league, then the target again, then an anonymous probe, then a second verify when the league is public. Low volume, high cost per link.

15

Invite-meta is a public, unauthenticated, uncached Sleeper proxy

backend → sleepermedium
server.py:22984-23012

One upstream call per hit, no rate limit by design. Trivially abusable to burn the Sleeper budget.

16

Extension background refresh fetches rankings the page then ignores

extensionlow
background.js:82-99 · content.js:127 early return · popup.js:82 vs background.js:41

The 15-minute alarm fetches and broadcasts, but the content script returns early when the league id has not changed, so badges stay stale until the user navigates away and back. The popup and background hold two implementations of the same fetch with different staleness rules.

Smaller items

  • Mobile record-picks screen polls the draft board every 15 s unconditionally (RecordPicksScreen.tsx:111); the draft room (DraftRoomScreen:221) has the correct focus and state guard.
  • Rank menu prefetches under query keys the target screens never read (TabNav.tsx:879-923), a full rankings payload per menu tap.
  • The sign-in response already carries a leagues list (server.py:22409) but the client immediately calls get-leagues, a second Sleeper round-trip. Check the compact shape suffices.
  • Progress and tiers status fetched outside the query cache alongside cached copies (usePresentationDeck.ts:98, quicksetProgress.ts:62); entitlements refetch on every foreground with no throttle; the bell always posts read-all even at zero unread.
  • Web fetches full liked-trade cards after every swipe and load just to count a badge (app.js:3185, 3262, 4011); the trades tab fires five to six uncached requests per visit; session ping at :211 is dead weight since init always follows.
  • Web market pulse (app.js:4929) is unreachable from normal navigation, so that section never loads. A bug, not a redundancy.
  • Backend fetches the DynastyProcess CSV twice per boot (server.py:341, 1662); Expo push goes out one POST per user (20129-20139) where the API accepts 100 per batch; the Sleeper fetcher permanently downgrades SSL verification for the process after one cert failure (598-611).
  • Anthropic is called once per trio when the rotation lands on the tightest lane; the result is not cached; generate_next_matchup in the smart-matchup module is dead code.

Found in passing

  • TestStagesScreen.tsx:118, 141 call /api/test-users/templates, which does not exist. Flask matches the delete-only user route and returns 405. Latent behind the stage-users flag.
  • Four cron levers (value-snapshot, players-refresh, roster-snapshot, receipts-grade) are not scheduled in render.yaml; each is duplicated by a fallback guard inside a tick. Operator tools, not waste, but the docs should say the guard is what fires.

Suggested order

  1. Server only, no client change.Thread rosters and meta into the init daemon and gate auto-detect (2); current-week-only trades sync (1); bulk prefs and pass the request-time outlook into the job (10). Cuts roughly 25 Sleeper calls and several reads per login with zero contract change.
  2. Web, small diffs.Warm route plus delete the summary block (4); pause polling on visibility change (7); drop the redundant progress calls (6); delete the dead post-reload block and skip the pre-reload fetches (8).
  3. Mobile, one PR.Ping then init (3), seed the roster and users cache (5), gate pregen on first session or on Trades being the landing tab (11). This changes session-init frequency, which is the FB-45 contract, so walk it through the gates.
  4. Route hygiene.Delete the four no-caller routes and ten dead wrappers, alias skip and dismiss, fold progress and matches, fix the templates call. Update the API reference row by row.
  5. Cron.Season-gate the draft sweep and filter both sweeps to recently active leagues (9).

Not recommended: merging the three propose routes (decided against at 28145), or a bootstrap bundle replacing flags, entitlements and session init. Session init embeds none of those payloads today (19700-19715), so that would be a design change, not a de-dup.

Uncertainties

  • Volumes are per code path. The 200 inits a day and 240 leagues used for estimates are illustrative; the api-events table would give real counts.
  • Whether the server-side job dedupe fully absorbs the double trade-generate when the second POST lands mid-init.
  • Whether the Anthropic key is set in Render; it is not in render.yaml.
  • Whether the compact leagues list in the sign-in response has every field the league picker needs.
  • Admin routes may be hit by operator curl not visible in the repo.
