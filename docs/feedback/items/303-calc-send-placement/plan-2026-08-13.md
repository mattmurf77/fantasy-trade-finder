## 0. Shared context — the no-raw-numerics ruling and its two precedents

The standing operator policy (2026-08-12, #300 round): **value is presented in
pick tiers, never raw numbers.** Two enforcement mechanisms exist today, and
they are gated differently:

1. **Per-asset tier** (`Tier` enum, 8-rung pick ladder): server-computed via
   `RankingService.tier_for_elo` over the RAW seed/board Elo — never derived
   client-side from a display value (`elo_to_value` scale ≠ tier-band Elo
   scale; #263/#277/#278). Ungated; shipped on rank surfaces, FA, calculator
   player rows.
2. **Aggregate pick-equivalent label** (`"≈N firsts"` strings):
   `_aggregate_pick_label` (`backend/server.py:837`), pure function of a
   value. Per-team/per-position emission on `/api/league/power-rankings` is
   gated by the **operator-only `aggregate_tier_labels` experiment** (#279,
   `backend/server.py:20100-20107`; targeting `is_tester_allowlist`,
   weighted 0/10000). But the #300 medians work **deliberately bypassed the
   gate** for the divider (`server.py:19965-19970`, `_position_medians` at
   19993): *"a divider that rendered a label for the operator and a blank for
   everyone else would be worse than no divider."*

#306 and #320 are both instances of surfaces that predate or missed that
policy. #306 additionally forces the gating question into the open — answered
explicitly in §2.3.

## 2. Item #306 — team selector shows raw per-position numbers

### 2.1 Current behaviour

The "team selector section" is the **Trade partner chip list** in
`InLeagueCalculator.tsx`:

- `partnerSummaries` (161-178) reads the consensus power-rankings payload
  (`powerQ`, same queryKey as LeagueSummaryScreen) and keeps only the raw
  numbers: `t.positions[pos].value` and `t.picks.value`.
- The chip's summary line (620-641) renders
  `QB 3,200 · RB 2,100 · WR 4,800 · TE 900 · Picks 5,400` —
  `Math.round(...).toLocaleString()` per position, 11px Plex Mono.
- The a11y label (592-599) speaks the same raw numbers.

The wire already *has* the fix for the operator only: under the
`aggregate_tier_labels` treatment, each team carries `positions[P].value_label`
("≈N firsts") and `total_value_label` (`server.py:20100-20107`); the mobile
types already model both as optional (`api/league.ts:549-566`). Everyone else
gets no label keys at all — so the client renders numbers, for everybody
including (apparently, on this build/session) the reporter.

### 2.2 Fix

**Server** (`backend/server.py`, power-rankings route):

- Emit the per-position `value_label` (and `total_value_label`, with its #285
  pick-firsts fold) **unconditionally** — i.e. lift lines 20101-20107 out of
  the `variant_for(g_user_id, "aggregate_tier_labels") == "treatment"` guard.
  Mechanically this is the #300 medians move (`_aggregate_pick_label` is a
  pure function; `server.py:19965-19970` is the recorded argument), applied to
  the per-team keys. **This is contingent on the gating decision in §2.3.**
- **Proposed (scope extension, operator may decline — D-306-2):** additive
  `picks.value_label` per team, computed as
  `_aggregate_pick_label(0.0, pick_firsts=_pick_firsts_equivalent(items))` —
  the #285 literal-count rule (1st = 1.0, 2nd = 1/3.5, 3rd+ = 0), never the
  dollar-priced `picks.value` (double-count rule, `server.py:20085-20098`).
  Without it the chip's "Picks 5,400" segment stays numeric — the same policy
  violation one word to the right. Fallback if declined: render `Picks ×4`
  (count — not a value numeric, policy-clean).

**Client** (`InLeagueCalculator.tsx`):

- `partnerSummaries` additionally captures `value_label` per position and
  `picks.value_label`/`picks.count`.
- Summary line renders the label when present, numeric fallback when absent
  (old servers) — e.g. `QB ≈3 firsts · RB ≈2.5 firsts · …`. The labels are
  longer than the numbers: change `numberOfLines` 1 → 2 on `summaryLine`
  (623-626) so the tail segments aren't ellipsized away; font stays 11px
  (Chalkline floor holds), chips already flex-wrap.
- `a11ySummary` (592-599) speaks the same labels
  (`QB about 3 firsts, …`) from the same source, numeric fallback identical.
- `TradeCalculatorScreen.tsx`: no change expected (the partner chips exist
  only in the in-league component); kept in footprint for the mode-tab
  Maestro touchpoints only.

## 3. Item #320 — picker misalignment + numeric pick values

The surface is the **"Send from your roster" picker** — `PlayerPickerModal`
mounted by `InLeagueCalculator.tsx:829-843` with exactly that title. Both
defects also exist, from the same root causes, in the `TradeSide` rows one
card above (the "You send" / "You receive" lists); the fix covers both, since
shipping the picker alone leaves the identical defect visible on the same
screen and it would bounce straight back as a new item.

### 3.1 Defect A — left-alignment

**Current behaviour:** the row layout in both lists is
`[PositionChip][name/info flex:1][value]`. `PositionChip` self-sizes to its
text (`alignSelf:'flex-start'`, `paddingHorizontal` 6/4 —
`PositionChip.tsx:40-48`), so a `PICK` chip (4 characters) is wider than
`QB`/`RB`/`WR`/`TE` (2), pushing the pick row's name column right.
Sites: `PlayerPickerModal.tsx:156` (chip) + `:326-333` (row);
`TradeSide.tsx:50` + `:110-117`.

**Fix:** wrap the chip in a fixed-width slot in both rows —
`chipCol: { width: 44, alignItems: 'flex-start' }` (width verified on-sim at
build against `PICK` at `size="sm"`; adjust once, keep both files on the same
constant). Names then start at one x for every row. `PositionChip` itself is
**not** touched — it is shared with Tiers/Trades/Matches and a default-width
change there would be a drive-by (guideline 3).

### 3.2 Defect B — pick values numeric

**Current behaviour:** every calculator `tierOf` callback special-cases picks
to null — `InLeagueCalculator.tsx:679, 701, 836, 851`
(`p.pos === 'PICK' ? null : tierById[p.id] ?? null`) — so
`PlayerPickerModal.tsx:181-189` and `TradeSide.tsx:69-82` fall back to the
numeric `pool_value` (e.g. `1,240`). This was a deliberate #263 choice ("a
pick already IS a tier rung", comment at `InLeagueCalculator.tsx:235-239` and
`TradeSide.tsx:17-22`) — **#320 supersedes it** (D-320-1).

**Fix — server (tier source):** additive `tier` key per pick row on
`GET /api/league/picks` (`backend/server.py:9106-9108`, alongside `label`):

```
tier = RankingService.tier_for_elo(seed_elo_for_value(pool_value), <pos>, fmt)
```

- `seed_elo_for_value` (`backend/data_loader.py:96`) is the server-side
  inverse of the value map, so the year-discounted `pool_value` lands back on
  the tier bands' Elo scale — the canonical band walk, never a client-side
  derivation from the display value (#263 rule holds).
- Tier bands are position-uniform by design (`tierBands.ts:12-14`), so the
  position argument is a pass-through; LLD picks the constant.
- Absent on old servers → client falls back to today's numeric (additive,
  non-breaking).
- **Named expected behaviour, worth one operator sentence (D-320-2):** the
  badge reflects *today's discounted value*, not the pick's name — a 2028 2nd
  may badge `3rd`. That is the honest read (it IS what the calculator prices
  it at) and exactly the cross-surface consistency the item asks for, but it
  can look like a mislabel to a first-time viewer.

**Fix — client:**

- `api/league.ts` `OwnedPick`: `tier?: Tier | null` (mirrors the #277
  `FreeAgentRow.tier` comment style: "never re-derive client-side").
- `InLeagueCalculator.tsx`: merge pick tiers into the existing `tierById`
  memo (240-246) from `picksQ.data.all_picks` (`p.pick_id → p.tier`), then
  simplify the four `tierOf` call sites to `tierById[p.id] ?? null` — no
  `CalcPlayer` type change, no `PlayerPickerModal`/`TradeSide` prop changes;
  the `TierBadge` path in both components lights up automatically.
- `shareAssets` (501-508) keeps `tier: null` for picks — the #277/#280 share
  card decision stands unless the operator says otherwise (D-320-3).
- Live/demo modes hold no pick assets (`TradeCalculatorScreen.tsx:913-915`,
  `tierFor` at 404-408), so that screen needs no change for this item.
