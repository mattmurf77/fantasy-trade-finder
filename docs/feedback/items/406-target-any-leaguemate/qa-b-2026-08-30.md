## Findings

### B-1 — NON-BLOCKING: the honest-display remount can wipe a hand-built canvas mid-search (zero-results case loses it)

The calculator's host key (`TradeBuildCanvas.tsx:174`) includes `effectiveOpponentId`, and
`opponentUserId={scopedOpponent ?? null}` (`TradesScreen.tsx:7432`). Concrete failure scenario:

1. Scoped search for @X (member tap → `scopedOpponent = 'X'`); browse session; session ends via
   the pager Clear / pass-exhaustion → blank restore, calculator remounts with
   `initialOpponentId='X'` (chosen — the user did tap X; dropdown honestly reads @X).
2. Team sheet → **Any league mate** (no remount — props unchanged). User hand-builds a give side.
3. **Find a Trade** → payload `opponent: null` (correct) → `handleInlineFindATrade` calls
   `setSheetOpponent(null)` (`:3055`) → `scopedOpponent` flips 'X' → undefined → the key steps
   `…-X` → `…-none` → **the calculator remounts immediately, with the stale blank prefill's
   empty `initialGiveIds`** — the user's built package vanishes from the canvas while the
   league-wide sweep runs.
4. If ≥1 idea lands, the seeding effect re-fills the canvas with the fronted idea (~the anchor),
   so the damage is a 1-2 s empty flash. **If the sweep returns zero ideas (fair-zero) or fails,
   the built package is simply gone** — no control restores it (the anchor receipt's non-session
   "Change" only scrolls, `TradesScreen.tsx:3161-3164`, whose comment "the canvas still HOLDS the
   assets — this screen never remounts it on search" is false on this path; the ids survive only
   in `inlineAnchor` for the error card's retry).

Pre-FB-406 this combination (`effectiveOpponentId` non-null ∧ payload null) was reachable only
via the rare departed-member prefill; the Anyone flow makes it a headline path. Wire truth, the
note, and analytics stay correct throughout — the casualty is canvas contents, in a corner
(scoped session → end → Anyone → build → zero results). E-4 never exercises this sequence (step 5
goes Anyone-after-scoped on an *empty* canvas; step 2's prior search is untouched-default, so
`scopedOpponent` was already null). Not shippable-blocking, but real: recommend (a) an E-4
addendum step or TEST_LEDGER note, and (b) a follow-up on the host key (the remount exists to
serve NB-1's display honesty; keying on `canvasKey` alone with an explicit prefill for partner
adoption would keep the display honest without discarding built state). Fixing it inside this
diff would breach the one-line host-diff contract — correctly out of scope.

### B-2 — NON-BLOCKING: stacked member chip never resets `partnerAny` — a mid-session `calc.merged_layout` kill strands a lying receive header and a dead Add button

`setPartnerAny(false)` exists only on the merged sheet's member row (`:1586`); the stacked chip
row's onPress (`:1111-1116`) does not reset it, and the team-sheet Modal mounts only under
`merged` (`:1505-1617`). In pure stacked operation `partnerAny` can never be true, so this is
unreachable today. But `merged` is a live flag read (`useFlag`, hot-reloadable): if the operator
kills `calc.merged_layout` while a mounted calculator sits in the Anyone state, the stacked
layout renders with `partnerAny === true` — the receive column header reads "any team" even
after a chip tap selects a real partner (`:1197`), the receive hint renders on the stacked page
(`:1219`), and the receive Add opens a team sheet that no longer mounts (`:1211` — permanently
dead button until remount). Kill-switch-only, self-heals on any remount, no wire dishonesty
(the stacked page has no Find a Trade). Cheapest hardening if ever touched again: add
`setPartnerAny(false)` to the stacked chip onPress (mind the 20c-bis 200-char window) or reset
`partnerAny` when `!merged`.
