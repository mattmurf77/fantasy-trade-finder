## 1. What shipped, in plain words

In a 1QB league nobody trades two first-round picks for a quarterback, but the
app was pricing the top QBs there. The fix lowers the *price* of elite 1QB
quarterbacks — it does not relabel them. Every QB now sits at "1 1st" or below
in 1QB leagues, in the same order as before, and superflex is untouched.

Two dials in `model_config` control it, and setting either to 0 turns the whole
thing off without a deploy.

## 3. The mechanism

Knobs are Elo; the map runs in DP-value space. `K = seed_value_for_elo(1580) =
1538.77`, `C = seed_value_for_elo(1785) = 4772.33`. For a 1QB pool row with
`pos == "QB"` and blended value `v`:

```
v' = v                                          if v <= K       (identity)
v' = K + (min(v, VALUE_MAX) - K) x (C - K)/(VALUE_MAX - K)   if v > K
```

Strictly increasing on `(K, VALUE_MAX]` (slope ≈ 0.382), so the QB board's
order survives. `min(v, VALUE_MAX)` mirrors the ceiling `seed_elo_for_value`
already applies — DP occasionally serves values above 10000 (10208 in the
checked-in pool), and those already tied at the ceiling before this change.

Kill switch: `qb_1qb_cap_elo <= 0` **or** `qb_1qb_cap_knee_elo <= 0` → the input
map is returned untouched. A degenerate ordering (knee ≥ cap, cap ≥ VALUE_MAX)
is also a no-op rather than an inverted, order-destroying map.

## 10. Where the plan was wrong or imprecise

1. **`C ≈ 4771` (plan) vs `4772.33` (actual).** The plan's inverted-affine
   constants are rounded approximations; the code derives them from
   `seed_value_for_elo` at runtime rather than hardcoding, so nothing depends on
   the plan's figure. Allen's landing spot (plan: "≈3635 → Elo ≈1734"; actual on
   live values: 3635.4 → 1733.9) is confirmed.
2. **Blast radius said trends/movers are "built on `dp_values_history`".** They
   are not — `dp_values_history.py` is an offline backtest module that never
   touches the seed pipeline. The live movers strip reads
   `player_value_history` snapshots. The *predicted effect* (a one-time
   step-down showing as movement) is still correct; only the named module is
   wrong. Detail in § 8.
3. **The plan did not anticipate the `test_ktc_blend` collision.** Its file
   footprint lists only `data_loader.py`, `database.py`, and new tests. Adding a
   third default-on knob inside `_apply_consensus_blend` necessarily breaks the
   two existing kill-switch tests that assert the *function* is a no-op with the
   *blend* knobs neutral. Handled in § 7, with the doc consequence in § 9.
4. **The plan's test table missed a seventh case worth having.** All six named
   sabotages target `_apply_consensus_blend`. Nothing pinned the *loader entry
   point*, so a future refactor that stops routing through that function would
   drop the cap silently with every listed test still green. Added
   `test_fetch_dynasty_process_serves_capped_1qb_qbs`.
5. **Rounding scope, worth knowing but not a defect.** Once any key changes,
   `_apply_consensus_blend` re-rounds the whole map to 1dp (pre-existing
   behaviour, line 453). DP serves integers, so this is a no-op in production —
   but it means "sub-knee QBs are byte-identical" holds on real data rather than
   for arbitrary fractional inputs. Recorded in the test's docstring rather than
   changed, since altering the rounding scope would be an unrequested change to
   #145's behaviour.
