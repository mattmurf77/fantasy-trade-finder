## 3. R-6 — is the data-loss defect actually closed?

### Forward trace — no path from the decline branch writes `{give: [], receive: []}`

The only writer is `handleBrowseSidesChange` (`trades:5732-5742`), fed by the calculator's
`onSidesChange` effect (`calc:404-409`). That effect fires on `[giveIds, receiveIds]`
change. The only way the action row can empty both is `clear()` (`:860-865`
`setGiveIds([]) / setReceiveIds([])`). In state C `clear` is **not referenced anywhere
inside the fork's `whenTrue`** — AST-pinned by `4m2`, and textually confirmed: the sole
`clear` identifiers in the file are `:355` (guide-target registry), `:860` (definition),
`:1368` (Clear branch), `:1558` (stacked ghost). **No indirect route exists either:**

- No `useEffect` in `InLeagueCalculator.tsx` calls `clear` (grep: `clear` appears at only
  the four sites above plus comments).
- The canvas remount key (`TradeBuildCanvas.tsx:184`) resets `sidesAnnouncedRef`
  (`calc:402`), so a remount's initial seed is **silent** — a remount can never announce
  `([], [])`.
- `handleBrowsePass` does no cleanup of its own (`trades:5752-5766` — five statements, none
  touching the canvas or the edit map; `4c` pins `!/\.edits/` on it).
- The exhaustion path *does* call `setCanvasPrefill({give: [], receive: []})`
  (`trades:5657`) — but `browseSeededIdRef.current = null` is set **first** at `:5656`, and
  `handleBrowseSidesChange` early-returns on a null id (`:5733-5734`). Also
  `edits[rawId]` was already deleted at `:5650`. Safe.

### Inverse — does the next idea front with its own sides intact?

`removeBrowsedIdea` (`trades:5629-5661`): splices `deck`, clamps `deckIdx` to
`min(i, remaining-1)`, deletes `edits[rawId]`, increments `passed`. The seeding effect
(`:5813-5824`) keys on `browseCurrentId = rawTopCard?.trade_id` (`:5812`), so the new
front id refires it: `browseSeededIdRef.current` ← new id (`:5816`), then
`setCanvasPrefill({… give: edited ? edited.give : rawTopCard.give_player_ids …})` (`:5817-5822`)
and a `prefillSeq` bump. **The next idea seeds from its own edit snapshot, or the engine's
original if it has none.** ✓

> Micro-NOTE: between the splice commit and the seeding effect, `browseSeededIdRef` still
> holds the *removed* idea's id. A stray `onSidesChange` in that window would resurrect a
> dead key in `edits`. Nothing changes the canvas in that window, and `removeBrowsedIdea`
> already deleted the key, so it is inert garbage at worst. Pre-existing.
