trades you're still waiting on the other owner for, with an Undo window and no

demand from the existing public evaluate endpoint — nothing new server-side for

leans on that contract is marked **[CONTRACT]** so the build agent can swap in

### Data answer: payload-insufficient → lazy fetch (Path A)

The match payload does **not** carry what `TradeValueBar` needs. Two ways to
get it:

- **Path A (chosen): client fetch on expand.** `POST /api/trade/evaluate`
  (`mobile/src/api/calc.ts:136-153`, public, Mode A consensus) returns exactly
  the bar's inputs: `give_value`, `receive_value`, `favors`,
  `gap{value, firsts, pick_equivalent}` (`CalcEvaluation`,
  `calc.ts:99-124`). This is the **same server-side construction that stamps
  deck cards**, so the bar cannot disagree with the deck. Fetch only when the
  user expands (disclosure-gated `useQuery`), so a scroll through the inbox
  costs zero extra requests.
- **Path B (rejected for this wave): backend enrichment** of
  `/api/trades/matches/all` + `/api/trades/awaiting` with the four fields
  (the #216 asset-ideas precedent). Zero per-row POSTs and the existing
  `TradeCard` gate would light up for free — but it grows two API responses
  (docs + api-reference + backend footprint) in a wave where our footprint is
  mobile-only, and it prices every row eagerly for a section most users won't
  expand. Recorded here so a future wave can promote it; the client shape
  below degrades to it cleanly (if the payload ever carries the fields, the
  section can skip its fetch).

`handleOpenInCalc` (screen-level, one definition for both segments):

```tsx
async function handleOpenInCalc(row: { league_id, counterparty_user_id,
                                       my_side_player_ids, their_side_player_ids }) {
  haptics.selection();
  track('trade_edit_in_calculator_tapped', undefined, 'Matches'); // see § Analytics
  if (row.league_id !== activeLeagueId) {
    const target = leagues.find((l) => l.league_id === row.league_id);
    if (!target) { setToast({ msg: 'Switch to that league to open the calculator', tone: 'warn' }); return; }
    await useSession.getState().setLeague(target as SavedLeague);  // existing switcher path
  }
  navigation.navigate('TradeCalculator', {
    prefill: {
      opponentUserId: row.counterparty_user_id,
      giveIds: row.my_side_player_ids,
      receiveIds: row.their_side_player_ids,
    },
  });
}
```

**Why league-switch-then-navigate:** `TradeCalculatorScreen` hard-wires
In-league mode to the ACTIVE league (`TradeCalculatorScreen.tsx:656-671`), and
Matches is a cross-league inbox. Switching first uses the exact machinery the
TopBar switcher uses (`useSession.setLeague`, `useSession.ts:195,392-405`) so
the calculator opens against the right rosters/opponent. The cleaner long-term
fix — `prefill.leagueId` honored by `TradeCalculatorScreen` — touches a screen
in `wave-calc`'s likely footprint; **noted as a coordination option, not taken
here**. `setLeague` re-runs league session init (visible spinner-time on
switch); acceptable for a deliberate "work this league now" action. If the
row's league is not in the cached `leagues` list (stale-league edge the filter
chips already handle at `MatchesScreen.tsx:361-378`), the CTA toasts honestly
instead of navigating into the wrong league.

**Scoring-format caveat (surfaced, decided):** the evaluate call uses the
session `activeFormat` fallback chain (`sf_tep`/`1qb_ppr`, the
`TradeCalculatorScreen.tsx:114-118` rule). `LeagueSummary` carries **no
per-league format** (`shared/types.ts:78-...`), so a superflex league's match
viewed while a 1QB league is active prices by the active format. This is the
same behaviour every calculator prefill already has after a league switch —
and the CTA path *switches leagues first*, which re-detects format via
`useLeagueFormatDefault`. For the in-place bar we accept active-format pricing
and note it in the scope block as a known approximation (operator may promote
Path B later, which prices server-side per league).

## Dismissal UX (three sentences)

A "Dismiss" button (pass-variant, same construction as the mutual tile's)
joins the send button in the awaiting card's actions row; tapping it removes
the row instantly and shows the standard 5-second "Dismissed — Undo" toast
(flag `ux.swipe_undo` on) or posts immediately (flag off), exactly mirroring
the mutual-match dismiss. The POST is held for the undo window rather than
reversed (there is no un-dismiss endpoint), and a failed POST restores the row
with the "Could not dismiss — try again" toast — the row never silently
vanishes on a failure. When the last visible awaiting row is dismissed, the
existing "No pending trades." empty state renders on its own; the counterparty
never sees any of this (their deck suppression is the backend's job).

The LeagueHome group froze the Matches side of #307's league-scoped deep link
and the orchestrator routes it to this group because we own
`MatchesScreen.tsx`. **This is a build requirement for our build agent, additive
to #318/#319.** Source of truth:
`docs/feedback/items/307-matches-link-routing/plan-2026-08-13.md` §4.3 on
branch `wave-league`, commit `6368e31` — implement §4.3 verbatim; the summary
below is for orientation, the frozen text wins on any discrepancy.

- **Param contract:** `navigate('Matches', { segment: 'mutual' | 'awaiting',
  leagueId: string, at: number })`. `leagueId` optional; producer sends the
  sender's active league id; consumer accepts leniently — an id not in
  `filterChips` degrades to the existing "No matches in this league yet"
  empty-state fallback (`MatchesScreen.tsx:380-386`), never a crash, never a
  silent ignore. Absent `leagueId` (push-tap routing, plain tab presses) →
  `filterLeagueId` untouched, so existing callers are unaffected by
  construction.
- **Consumption:** extend the existing FB-91 effect (`MatchesScreen.tsx:116-119`)
  exactly as frozen:

  ```ts
  useEffect(() => {
    const s = route.params?.segment;
    if (s === 'mutual' || s === 'awaiting') setSegment(s);
    const lid = route.params?.leagueId;
    if (typeof lid === 'string' && lid) setFilterLeagueId(lid);
  }, [route.params?.segment, route.params?.leagueId, route.params?.at]);
  ```

  Keying on `at` preserves the re-tap contract (tap tile → manually toggle the
  chip to "All" → tap tile again → rescopes, because `at` changed even though
  `leagueId` didn't).
- **Chip testIDs (asserted by the LeagueHome group's Maestro flow — must land
  in OUR build):** the filter-chip `Pressable` (`MatchesScreen.tsx:575`) gains
  `` testID={c.id === 'all' ? 'matches.league-chip.all' : `matches.league-chip.${c.id}`} ``.
  Selection stays asserted through the existing
  `accessibilityState={{ selected }}` (`:578`). Registry rows for
  `matches.league-chip.all` / `matches.league-chip.<league_id>` join our
  Appendix A proposal; must pass `testid-lint.sh`.
- **Test we author (named sabotage, per §4.3's ask):**
  **`mobile/tests/check-matches-league-param.js`** — S-10 *re-tap sabotage:*
  key the effect's dep array on `leagueId` only (drop `route.params?.at`) →
  fails. Asserts the effect reads `route.params?.leagueId` AND its dep array
  includes `route.params?.at`, so the re-tap-after-manual-change path can't
  silently die while first-tap demos pass.
- **Interaction with our items:** none functional — #318/#319 don't read route
  params; the chip testID edit touches the same chip row `Pressable` this plan
  otherwise leaves alone. All three workstreams (#307 handoff, #318, #319)
  land in the one `MatchesScreen.tsx`, so the build brief must carry all three
