## 1. Context

Three feedback reports, one mechanism, one new feature:

- **#295/#296 (v1.12.0):** the mock draft excludes the user's team entirely —
  never on the clock, roster still draftable, mock born complete.
- **#305 (v1.12.1):** the same defect observed on a second platform (Newton,
  ESPN, 14 teams → 13-pick rounds), **plus** a priority feature request:
  manual-draft-for-all-teams.

Root cause (plan §1, re-verified at file:line on `3b64a44`): the app-wide
session convention is that `sess["league"].members` holds the leaguemates
**excluding the caller** — `/api/session/init` builds it from the client's
`opponent_rosters` and explicitly refuses to re-add the caller
(`backend/server.py:14655`, `:14661`). The mock-draft create path reads that
list as "everyone in the league" at four sites, so `owners` never contains the
user, `is_user` never fires, and `advance_cpu` drafts the whole board at
create. A third defect makes the assigned-order branch fail differently:
`teams = len(owners)` while `owner_of` indexes the possibly-longer platform
`order`, silently dropping the last slot (`mock_draft_service.py:989`/`:1007`;
now live on ffv3, whose 2026 draft has a 12-slot assigned order).

Two workstreams: **W1** repairs membership and makes the next silent exclusion
a loud refusal; **W2** adds `mode: "cpu" | "manual"` as a create-time setting
with exactly one engine lever.

## 2. The architectural frame

The mock-draft feature is already built as two layers with a deliberate
boundary, and the whole design of this build is to respect it:

**`backend/server.py` — the resolution layer.** Owns the session, the league,
the flag gate, and the *translation* of session-domain facts into engine-domain
inputs. Session-domain facts carry conventions (caller-excluded `members`, the
active scoring format, the caller's own roster living in `sess["user_roster"]`
rather than in `members`). The resolution layer's job is to erase those
conventions before anything crosses the boundary: what it hands the engine must
be self-describing — a frozen `MockContext` plus explicit `owners`,
`user_owner_id`, `order`, `mode`.

**`backend/mock_draft_service.py` — the pure engine.** Total functions over
explicit inputs. Imports no HTTP client, no Flask, no DB
(`MockContext` docstring, `mock_draft_service.py:362-386`: "Everything the
engine knows; nothing it can look up itself"). It has no concept of a session
or a caller and therefore *cannot know* the members-list convention. Its
contract for `owners` has always been "every team in the draft".

**The defect is a boundary fault, not an engine fault.** The route passed a
session-domain value (`members`, caller-excluded by convention) where the
engine contract wants a draft-domain value. Consequently:

- The **membership repair belongs in the resolution layer** — the four
  `server.py` sites (R1–R4). Teaching the engine to re-add a caller would
  invert the dependency: the engine would need to know a session convention it
  is structurally built not to see, and every non-route caller (tests, future
  CLIs) would inherit a hidden `+1`.
- The **guards belong in the engine** — `start_refusal` and `build_settings`
  are where "the user is in this draft" is checkable *as a property of the
  inputs*, independent of how any caller assembled them. A guard in the route
  would protect one call site; a guard in the engine protects every present
  and future one, which is the point of fail-loud.

Everything below is an application of this frame.

## 3. W1 — the repair

### 3.1 Membership repair — four sites, one layer (plan §2.1, R1–R4)

All four fixes are edits to the resolution layer's translation step, and they
are **one invariant stated four times**: *every engine input derived from
league membership includes the caller.*

| Site | What it feeds | Invariant restored |
|---|---|---|
| R1 `_mock_league_context` return (`server.py:11796`) | `owners` → `start_refusal`, `build_settings` | user ∈ owners |
| R2 `_mock_league_context` rosters (`:11775`) | `ctx.rostered_ids`, `ctx.rosters` | user's players excluded from the pool; user's roster feeds severity |
| R3 `_mock_context_from_row` (`:11812`/`:11827`) | resume-path `rostered_ids` | **create/resume parity** — both paths compute the same pool, so `consensus_rank` cannot shift between create and resume |
| R4 `_mock_capability` (`:11851`) | probe's `owners` | **probe/create parity (G2)** — the probe counts the same teams the create will |

R3 and R4 are not "also fix" items — they are parity invariants with names.
The engine's frozen-pool recap semantics (`consensus_rank` against the
pre-draft pool) and the G2 capability contract ("a client that rendered an
enabled button can never be told something the probe did not already say",
create-route comment at `server.py:12056`) both die if either pair diverges.
The LLD should express R1/R4 and R2/R3 as shared construction, not four
parallel edits, so the pairs cannot drift.

### 3.2 The teams-from-order rule (plan §2.2)

New engine invariant, owned by `build_settings`: **the slot table and `teams`
derive from `len(resolved_order)`; `owners` never sizes the draft.** After
this, `owners`' residual roles are exactly three: the shuffle pool when no
platform order exists, the persona keying, and the refusal-ladder count. The
ladder keeps counting `owners` on both the probe and the create path (both
call `start_refusal(ctx, owners)` before any order resolution), so G2's
probe/create agreement is preserved — the rule changes the draft's *shape*,
never the refusal answer.

Two boundary details the plan does not address; both are LLD decisions (§14):
a platform order can contain an entry absent from `owners` (persona and roster
lookups fall soft — `advance_cpu` already defaults the persona at
`mock_draft_service.py:1191-1193`, and a missing roster just means no
exclusion for that team), and a degenerate platform order could be *shorter*
than `MOCK_MIN_TEAMS` even though the ladder passed on the owners count.

### 3.3 The fail-loud guard — why the rung is at the probe and the raise is at the engine

The guard is deliberately **two enforcement points with one client-visible
vocabulary**, because the two points can see different things:

**The rung** — `REASON_USER_NOT_IN_DRAFT = "user_not_in_draft"`, fourth and
last in `start_refusal` (after `league_too_small`, per the shipped ladder's
own ordering logic: last because it is the least actionable by the user).
`start_refusal` is the *shared* probe/create ladder — the single reason
vocabulary `capability()` serves to `GET` and the create route serves as a
typed-empty. Membership-in-`owners` is checkable **before any resolution**,
cheaply, with exactly the inputs the probe already holds — so the rung lives
here, and the client can render a *disabled entry state* without ever POSTing.
Signature grows keyword-only (`user_owner_id: str | None = None`) so every
existing positional call site and test is untouched; `capability()` forwards
the same argument (G2 again: probe and create must run the identical ladder).

**The raise** — `UserNotInDraft(MockDraftError)` from `build_settings` when
`str(user_owner_id) not in resolved_order`. Only `build_settings` knows the
*resolved* order — an explicit platform order can omit a user who **is** in
`owners` (stale roster takeover, commissioner rebuild), a state the ladder is
structurally blind to. `build_settings` is also the last point before a row is
persisted: raising here means a born-broken mock **can never be written**,
which is the actual promise of fail-loud. It is an exception rather than a
refusal-return because at this depth a missing user signals a contract
violation between the layers, not a league condition — but the route maps it
to `empty_payload(REASON_USER_NOT_IN_DRAFT)`, byte-identical to the ladder's
refusal, so clients see one vocabulary and never learn which enforcement
point fired. That mapping (exception → typed-empty) is route-owned, like the
existing `NotYourTurn`/`PlayerUnavailable` mappings on the pick route.

The guard is **mode-blind**: manual mode still mocks *this user's league*, so
both enforcement points apply identically in both modes (plan §2.3).

The #305 loop (sim → stop at user's turn → pick → resume) is already the
shipped engine's contract — `advance_cpu`'s user-stop and `apply_user_pick`'s
validate → append → re-advance. **W1 changes who is in the draft; it does not
touch the turn machinery.** R1 alone makes the loop reachable.

## 4. W2 — manual mode

### 4.1 Shape — a toggle on the existing engine

One request field, one settings key, one engine lever, one sheet control
(plan §3). No new route, no schema change, no new flag — `settings` is
already a JSON blob (`mock_drafts`, `backend/database.py:1655-1668`) and
`draft.mock` already gates the surface. The engine gains constants
`MODE_CPU = "cpu"` / `MODE_MANUAL = "manual"` beside its other closed
vocabularies; the route owns request validation (unknown value → 400
`bad_mode`, parity with the existing `bad_basis`); the engine owns the
semantic default (`settings.get("mode", MODE_CPU)` — see §9).

The lever is one line of truth in `next_pick`
(`mock_draft_service.py:1061`): in manual mode `is_user` is true for **every
owned slot**. Everything else — create-time advance stopping at pick 1, the
pick route's turn validation, `_append`'s completion flip, the recap — falls
out of shipped code with zero changes, because the entire engine already
routes turn decisions through that one flag. That is the design's proof of
minimality: if any second site needed a mode check, the lever would be in the
wrong place.

### 4.2 Mode is create-time-immutable — the call and the reasoning

**Decision: immutable after create.** Four reasons, in strength order:

1. **It joins an existing immutability class rather than creating a mutable
   exception.** Every other member of `settings` — order, ownership overlay,
   personas, noise parameters, lineup template — is snapshot-at-create by
   design, and that snapshotting is *why* the replay and zero-egress
   invariants hold. A mutable `mode` would be the blob's first mutable key and
   would need its own persistence path (`update_mock_draft` currently writes
   `picks_json` + `status` only, `server.py` pick route).
2. **Replay integrity.** `picks[]` plus frozen `settings` is the complete
   record of a mock. If mode could flip mid-draft, interpreting the persisted
   stream would require knowing *when* it flipped — a mode-change journal —
   for the recap's `by`/delta semantics to stay honest.
3. **The manual→CPU direction is semantically muddy.** CPU completion of a
   half-manual draft blends two pick regimes into one recap with no
   disclosure; the consensus-delta story ("the CPU reached here") stops being
   attributable.
4. **The escape hatch already exists and is cheap.** Abandon + recreate is two
   taps; creation's only platform cost is the Draft Room's own cached board
   read. A future "take over / hand off" verb can be added as an explicit new
   endpoint without disturbing this build — it is named in §13 as out.

### 4.3 Recap and abandon semantics carry unchanged

The engine already distinguishes **who moved the piece** (`by`:
`user`/`cpu`) from **whose team it is** (`picked_by_user_id`). In manual
mode every pick is `by: "user"` while `picked_by_user_id` walks the order —
and `my_picks` filters on `picked_by_user_id == user_owner`
(`mock_draft_service.py:1333`), so the recap's "My picks" remains the user's
own team in both modes with no code change. This is the intended semantics,
not a coincidence to be papered over: the LLD and PRD must **not** introduce
any client logic keyed on `by` to mean "my team". Abandon (#292) is
row-status bookkeeping and stays mode-blind. The refusal ladder also stays
mode-blind, including `cpu_model_unvalidated` — strictly irrelevant when no
bot picks, but the rung is unreachable today (`CPU_MODEL_VALIDATED = True`)
and forking the ladder by mode would fork the G2 probe contract for a state
that cannot occur. Noted; do not build (plan §3.2).

### 4.4 What `settings_echo` guarantees the client

`settings_echo` gains `mode`, and the guarantee is: **`settings_echo.mode` is
present on every state payload and is the only source of mode truth.** A
client must never infer mode from `by` values, from `on_the_clock.roster_id ≠`
the session user, or from pick cadence. For rows persisted before this build
the server echoes the *effective* mode — `settings.get("mode", "cpu")` — so
the field is never absent and clients need no undefined-handling branch. The
`capability` payload is unchanged: mode is a property of a request, not of a
league, and the probe describes leagues.

### 4.5 Client surface (summary — PRD/mockups own the detail)

Setup sheet gains a two-option segmented control (default CPU, plan §10 Q2
pending operator confirmation); `mockDraft.ts` gains the type and
pass-through; `MockDraftScreen`'s clock card states **whose team the user is
picking for** when `is_user` is true but the slot is another team — owner
name resolves from the `order[]` rows the screen already holds, no new data.

## 6. Data flow, both modes

The lifecycle is identical in both modes except at the two starred points —
which is the architectural claim that W2 is a toggle, not a second engine.

```
CREATE  POST /api/mock-draft {league_id, rounds?, type?, mode?, rng_seed?}
        server: flag gate → session → validate mode (INV-8)
        _mock_league_context ──► ctx + owners            [owners include caller: INV-1]
        start_refusal(ctx, owners, user_owner_id=uid)    [4-rung ladder: INV-5]
             └─ refusal ⇒ 200 typed-empty (incl. user_not_in_draft)
        _mock_real_draft ──► order/ownership/type        [the ONLY platform touch: INV-9]
        build_settings(…, mode) ── raises UserNotInDraft [INV-6] ⇒ route maps to typed-empty
             teams = len(resolved_order)                 [INV-4]
        new_state → advance_cpu:
   *      cpu mode:    CPU drafts until first is_user slot (user's own team)
   *      manual mode: is_user true at pick 1 (INV-7 lever) → zero CPU picks
        persist row (settings_json, picks_json, seed, status) → state_payload
                                                          [settings_echo.mode: §4.4]

PICK    POST /api/mock-draft/pick {mock_id, player_id}
        _mock_context_from_row (settings snapshot + DB + process pool only)
        apply_user_pick: turn check (NotYourTurn) → pool check (PlayerUnavailable)
             → _append(by=user) → advance_cpu
   *      cpu mode:    CPU resumes to the user's next slot or completion
   *      manual mode: advance_cpu returns immediately at the next owned slot
        persist picks_json + status

RESUME  GET /api/mock-draft — loads row, _mock_context_from_row [INV-2 parity with create],
        state_payload. Same in both modes; the client learns mode from settings_echo.

COMPLETE _append flips status at total_picks; recap = picks[] with consensus deltas;
        my_picks keyed on picked_by_user_id in both modes (§4.3).

ABANDON POST /api/mock-draft/abandon — row-status bookkeeping (#292), mode-blind.
```

## 7. Zero platform egress

The invariant (`docs/architecture.md`, `mock_draft_service.py` row): **zero
platform egress after creation, structural rather than incidental.** It is
enforced at three places, and this build must leave all three intact:

1. **Module import surface** — `mock_draft_service.py` imports no HTTP
   client, no Flask, no DB. Neither workstream adds an import.
2. **`MockContext.fetchers()`** (`mock_draft_service.py:388-396`) — the
   fetcher shim binds only the injected maps, so a stray platform read
   *raises* instead of going live.
3. **`_mock_context_from_row`** (`server.py:11799-11832`) — the resume-path
   context is rebuilt from the settings snapshot + DB + process pool only;
   the lineup template and scoring format come off `settings`, never a
   league-meta fetch.

W1's edits read `sess` (in-memory) — no new egress. W2's `mode` is a settings
key — no egress. The `UserNotInDraft` raise happens in pure code before any
row exists. **Constraint on the LLD:** nothing mode- or membership-related may
be resolved via a fetch; if a design sketch ever needs one, it is wrong by
this invariant, not merely expensive.

## 8. Determinism

`Random(rng_seed * 10007 + pick_no)` is a pure function of `(seed, pick_no)`
— never of call order — so a resumed mock replays byte-identically.

- **The repair changes who picks, not the stream.** Post-R1, more slots are
  user-owned and the CPU consumes draws for a different *set* of `pick_no`s,
  but each CPU pick's draw is still the same pure function. Honest statement
  for the record: the *same seed* produces a *different draft* pre- vs
  post-repair (membership and teams changed) — that is a semantic change to
  settings construction, not a determinism break; persisted rows replay under
  their own snapshotted settings, untouched.
- **Manual mode: user picks are inputs, not RNG draws.** The per-pick RNG is
  simply never consulted (no CPU picks). The seed still exists and still
  seeds the randomized-order shuffle in `build_settings`, so order derivation
  is identical in both modes; replay of a manual mock is a pure re-read of
  `picks[]`.

## 9. Compatibility

- **Pre-mode persisted rows: read-time default, no migration.** Rows created
  before this build lack `settings["mode"]`; every reader uses
  `settings.get("mode", MODE_CPU)` and the echo carries the effective value
  (§4.4). A persisted CPU mock resumed after the build behaves byte-identically
  (pinned by T-305-05).
- **Shipped 1.12.x clients vs the new reason string:** the mobile reason enum
  is open by construction (`mobile/src/api/mockDraft.ts:35-39`,
  `… | (string & {})`) and `MockDraftScreen`'s `emptyCopy` has a `default:`
  arm — old clients degrade to the generic unavailable copy. No forced
  upgrade.
- **Old clients vs `mode`:** the field is optional on POST with the server
  defaulting to `"cpu"`, so a 1.12.x create is unchanged. `settings_echo`
  gaining a key is additive; shipped clients ignore it.
- **API surface:** POST body `mode` + `settings_echo.mode` + fourth ladder
  rung + `user_not_in_draft` typed-empty are the entire contract delta.
  `docs/api-reference.md` § Mock draft carries them plus the O-4 carried
  edits (the two deliberately-unapplied edits from
  [`operator-answers-2026-08-11.md`](operator-answers-2026-08-11.md));
  `docs/cross-client-invariants.md` gains the `mode` enum and the reason
  string — both in this build's own commit, per the plan's §7 docs table.

## 10. Analytics architecture

State on this base: **zero** mock events registered; the 2026-08-11 waiver's
premise (family in flight elsewhere) no longer holds. This build designs as
**owning** the family (plan §9), with one structural condition:

- **Registration is isolated in its own commit** — `analytics_taxonomy.py`
  additions plus the two NON_INTENT names into
  `backend/analytics_queries.py:63` `NON_INTENT_EVENTS`, **same commit**
  (INTENT is a deny-list; a NON_INTENT name registered without its deny-list
  row silently distorts DAU/retention from ship day — the P0-7 addendum's
  lesson). Pure additions, no neighbouring reformatting: the file records
  four concurrent branch claims this week.
- **Ordering rule:** the registration commit precedes (or accompanies) any
  emitter commit on the branch. DEFAULT-DENY drops unregistered events
  silently, so emitters-first would repeat the NULL-`platform` incident's
  shape with a different symptom.
- **Drop-if-superseded protocol:** if the spun-out session lands its version
  first, this branch's registration commit is dropped/reverted cleanly (it
  is isolated precisely for this) and the emitters re-point at the landed
  names. Any name/prop divergence is an operator escalation, never a silent
  merge. Plan §10 Q1 stays open for the operator.

All five events are **client-fired** through `track()`
(`mobile/src/api/events.ts:188`), `platform` = league platform, required.
Architectural note, considered and accepted: client-fired `mock_completed`
undercounts (app death before the status-flip render). A server-side emission
would require a `SERVER_FIRED_EVENTS` name — the taxonomy's import-time
disjointness invariant forbids the same string in both namespaces — so a
split-namespace family for one event's completeness is the wrong trade;
one family, one namespace, honest undercount on a NON_INTENT outcome metric.
`mock_completed.user_picks` counts `my_picks` (the user's *team's* picks),
not `by == "user"` — the §4.3 distinction, restated for the prop spec.

## 11. Test architecture

(The cases are the LLD's; this is the shape.) Three rings, each pinning a
different layer of §5's invariant table:

**Ring 1 — pytest, route + engine (`backend/tests/test_mock_draft.py`).**
The organising rule, from the plan's five-false-passing-tests finding: *the
harness must not be allowed to reconstruct the coincidence that blinded
#291*. Concretely: the shared session fixture is rewritten to the production
(caller-excluded) shape; a **fixture-contract test** (T-295-02) pins that
shape itself, so the suite fails if anyone "fixes" the fixture back; at least
one route test derives `owners`/`user_owner_id` the way the route does rather
than hand-passing both; and every behavioural test is **proven red on a
sabotaged build** (revert the single change it guards; show the red run in PR
evidence). Ring 1 pins INV-1..8 and the §9 compatibility pins.

**Ring 2 — Maestro, hermetic, on the `draft-pre` profile.** The d3 blocker is
still verbatim-true (`mobile/.maestro/flows/rookie/d3-mock-draft-loop.yaml:24-33`:
`standard.json` declares one league; d1/d2/d3 target ffv3, which appears in no
profile). The remedy is **retarget, not patch**: `draft-pre.json` is a
purpose-built world — 12-team, pre-draft, assigned order, full rookie class,
seeded through the app's own session-init so the caller-excluded shape
reproduces — created precisely because the mock is unreachable on every other
profile. Patching `standard.json` instead would widen a shared world and drag
d1/d2 re-verification into this build's blast radius; the principle worth
recording is that **hermetic profiles are per-purpose worlds, and coverage
gaps are fixed by pointing flows at the right world, not by growing one world
until it covers everything**. Two flows: extend d3 (clock card names the
user's own team — the UI-level statement of #295 that #291's flow never
asserted — then one full pick → resume → recap lap) and one new manual-mode
flow. All testIDs through `mobile/scripts/testid-lint.sh` (CI).

**Ring 3 — live Tier-2 operator verification.** The coverage claim at this
ring is the **platform-branch matrix**, because §1's two branches fail
differently: ffv3 (Sleeper, *assigned* order — 12-team rail including slot
12, operator on the clock at slot 8, own roster absent from pool), Newton
(ESPN, *randomized* branch — 14-pick rounds, user prompted; #305's arithmetic
inverted), Dependables (MFL, randomized + the D-16 no-`mfl:`-string check),
negative control: the real Draft Room unchanged. Sign-off = an operator pick
taken on ffv3 **and** Newton, both modes exercised at least once somewhere.

Sim-gate tier: fresh operator decision per the `docs/runbook.md` matrix,
recorded in the scope block — the previous O-3 skip does not carry (plan §5
row 8, §10 Q3). `npm run test:mock-lifecycle` by hand (not in CI).

**Key Flows, new flow after Flow D:**

> ### Flow E — Mock rookie draft (two modes)
> 1. Client `GET /api/mock-draft` → capability probe (shared refusal ladder) renders the entry state without a create.
> 2. `POST /api/mock-draft {rounds?, type?, mode?}` → server resolves league context **including the caller**, order/ownership from the Draft Room's own cached board (the only platform touch); engine builds settings (`teams = len(order)`), advances CPUs (cpu mode) or stops at pick 1 (manual mode); row persisted.
> 3. `POST /api/mock-draft/pick` loop: validate turn → append (`by: user`) → CPU resume to the user's next slot (cpu) or next owned slot (manual). Deterministic replay via `Random(rng_seed·10007 + pick_no)`; user picks are inputs, not draws.
> 4. Completion → recap (`my_picks` = the user's *team's* picks in both modes); abandon retires the row + the league's completed backlog (#292).
