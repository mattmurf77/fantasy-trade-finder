## 4. The flag coupling (deviation 2 — no operator ruling exists)

**What `trade.presentment_rules` controls today** (`docs/config-reference.md`, Presentment-rules table): R1 `overpay_ok` (#340), R2 `pos_net_ok` (#341), R3 `pick_gap_ok` (#339), R5 `need_gate_ok` (#304) as construction rules inside every v1 generator; R4 (#336) awaiting-like/live-match eligibility at `_dedup_and_sort` and on the likes-you injector; the per-job kill counters and the `presentment-tripwire` WARNING; and now, per D-178, the exclusion set on `POST /api/trades/asset-ideas` and `POST /api/trades/fair-packages`.

**If the operator kills the flag for an unrelated R1/R2/R3/R5 incident, what else silently changes?**

Decks lose the overpay kill, the positional body-count cap, the pick-is-the-gap kill and the need gate — that is the intended revert. They *also* lose R4, so the deck resumes re-offering trades the user has live in Awaiting. And **the shop window and the anchored sweep resume re-offering every package the user has already sent** — feedback #418, back in production, with no deploy, no code change, and no log line that names it. The `presentment-tripwire` WARNING counts R1/R2/R3/R5 kills only (`server.py:5853-5856`), so it goes quiet in a way that looks like the revert worked.

**How would anyone notice?** They would not. There is no analytics signal for a re-offered idea (B-7), the two routes emit no kill counter, and the tripwire ignores R4 by construction. The first evidence would be another feedback ticket that reads exactly like #418.

**The mitigating fact the PRD does not state, and the one that decides this:** the operator does **not** need the flag to neutralize any single construction rule. Each has its own deploy-free DB knob — R1 `max_overpay_min_value` (`trade_service.py:824`), R2 `pos_net_cap` (`:829`), R3 `pick_gap_min_value` (`:837`), R5 `need_gate_min_value <= 0` disables the gate outright (`:843`). The flag is only reached for a **group panic revert** or to kill R4, which has no knob of its own.

### Recommendation: **keep the coupling. Add a runbook line, not a flag.**

The builder's parity argument is right and the alternative is worse. A dedicated flag would mean two switches for one rule (R4), which is precisely the drift the G6 wave designed this flag to prevent — and the first time someone kills R4 on the deck and forgets the second switch, the two surfaces disagree about the same package for the same user, which is a harder bug than the one being reverted. Ungated is worse still: it falsifies the config-reference's "R4's only switch" sentence silently. **Trade-off named plainly: keeping the coupling means a panic revert of `trade.presentment_rules` also silently un-fixes #418, and nothing will tell you.** Buy that risk down for the cost of two lines rather than a flag: (1) add to `docs/runbook.md`, at the presentment-rules kill procedure, "killing this flag also restores #418 — the shop and the anchored sweep will re-offer already-sent packages; prefer the per-rule knobs (`max_overpay_min_value`, `pos_net_cap`, `pick_gap_min_value`, `need_gate_min_value`) for a single-rule incident and reserve the flag for a genuine group revert"; (2) if the operator wants a tripwire, log the exclusion-set size on both routes so a flag-off shows as an abrupt drop to zero. The per-rule knobs already make a flag-level revert rare, which is what makes keeping the coupling cheap.

## 6. Analytics — can anyone measure that this worked?

**No. As shipped, this change is unmeasurable in prod.** Detail in B-7. Summary:

- The pre-change symptom was a **repeat** ✓ — a re-offered idea sent a second time. That path answers `already_queued: true` from an idempotency probe that returns **before any signal is written** (`server.py:13328-13334`), and the client event drops the value it already holds (`queueCalcTrade.ts:82-84`; `already_queued` is not in `calc_trade_queued`'s allowed props, `analytics_taxonomy.py:1550`). The symptom has never been recorded, so its disappearance cannot be observed.
- Scope §1's proxy is wrong: `shop_opened` carries `{asset_position, source, give_count}` (`:1574-1575`), no idea count.
- **The one existing event that would answer the volume half** is `shop_mode_selected {mode, n_ideas}` (`:1576`) — real, usable, but chip-tap-triggered, so it never samples the default mode on open.
- **Cheapest fix (client-only, one commit):** add `already_queued` to `calc_trade_queued`'s prop allow-set and emit it. Success criterion becomes concrete: `calc_trade_queued {queued: true, already_queued: true}` on screen `ShopAsset` → ~0 after deploy, versus a non-zero baseline before. A server-side `excluded_count` log (C-4) gives the same answer from the other end.

## 8. Prod-verification checklist (post-deploy, operator-runnable)

Runtime evidence per D-056: no simulator, no Maestro. All of this is a TestFlight walk plus one read-only Postgres query. Credentials from `secrets.local.env` (`DATABASE_URL_PROD`).

1. **The fix, cold (the D-178 case).** In a league with a real partner: open a deck card → "More offers" → note the pin, mode and the `1 / X` count → ✓ one idea (toast should read "Queued for @X", *not* "Already queued"). **Force-quit the app**, relaunch, navigate back to the same pin's shop window. The sent idea must be **absent** and the count one lower. This is the whole ruling; if it fails, stop.
2. **The B-5 window.** Same pin. ✓ a second idea, tap back **immediately**, tap "More offers" again within ~30 s. Expect the just-sent idea to still be on screen (known, B-5). 3. **Retraction round-trip (scenario c).** Matches → Awaiting them → dismiss the tile for the offer from step 1. Reopen the shop window (after 60 s, or force-quit first). The idea must be **back**. This proves the exclusion is retractable and not a one-way door.
4. **Decline behavior (B-1) — the decision you have to make.** With a second test account: send an offer, have the partner **decline** it, then reopen the shop on the first account. Expect the idea to **reappear immediately**. Decide there and then whether that is the behavior you want; if not, B-1 names the fix.
5. **The empty state (B-2/B-3).** Pick a pin with a thin Same-value pool and ✓ every idea in it. Reopen. 7. **Exclusion set is real, from the DB.** Read-only, against prod:
   ```sql
   SELECT league_id, count(*)
     FROM trade_decisions
    WHERE user_id = '<your acct_ user id>'

      AND retracted_at IS NULL
   ```
