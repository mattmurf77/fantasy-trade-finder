## Hunt 3 — the receiveIds clause: CLEAN (two NOTEs)

Can `receiveIds` hold assets not on the current `opponent`'s roster? No, structurally:

- Receive writers: initial prefill (`:353`), receive picker `:1557-1561` (pool =
  `oppPoolPlayers` `:595-600` — the opponent's roster + the opponent's own picks;
  free agents unreachable), eveners `:783-790` (`addTo:'receive'` = server-picked from
  "theirs"), balance suggestions `:756-761` (lighter-side roster), #264 one-sided
  options (opponent's roster). Picks on the receive side belong to the opponent —
  scoping on them is sound.
- Staleness is wiped by construction: **any** `opponentId` change clears the receive side
  (`:579-585`), including the default effect's own null→first-leaguemate write. So a
  prefill that arrives WITHOUT an opponentId (e.g. `handleBackToCalculator`'s unscoped
  restore, `TradesScreen.tsx:3402-3406`, pinned receive-wants from arbitrary teams) is
  self-neutralizing: the default fires, the mismatched receive side is wiped before any
  tap, and the gate sees `receiveIds.length === 0`. The scary case — gate scoping to the
  default off another team's players — is unreachable.

N-1 (NOTE): the gate reads `receiveIds.length > 0` while the payload's `receive` array
filters through `playerById` (`:1222`); a receive id that fails to resolve (stale prefill
id absent from the value board) passes the gate and scopes to the partner while sending
an empty receive list. Cosmetic — the partner is still the one the id belonged to.

N-2 (NOTE): a receive-ONLY canvas forks to `model` (`canvasSearch.ts:51` — "counts as
EMPTY") yet the gate scopes it, so the model sweep targets the partner while ignoring the
specific receive asset (D-153: no pins are written). Deliberate engagement with that team
(the user opened "Receive from @X"), unchanged from pre-fix, consistent with the
mini-PRD's rationale — recorded only because the "fair sweep's receive preference"
justification doesn't apply on this fork.
