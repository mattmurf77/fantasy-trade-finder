## Item #311 — Starting lineup for MFL/ESPN trade summaries (polish, TradeCalculator)

### Verbatim
> "For the starting lineup section of trade summary, we should just determine
> starting lineup based on dynasty values for mfl and espn (not supported due
> to no starting lineup data like sleeper provides)"

### Root cause — CONFIRMED, with one refinement

- `_starter_impact` (`backend/server.py:1127`) returns `None` at
  `backend/server.py:1158-1160` whenever `_sleeper_lineup_slots` yields no
  template. Its caller (`backend/server.py:8793-8805`, the Mode B evaluate
  path) then omits `starter_impact`; since #297 the client renders the honest
  empty row.
- `_sleeper_lineup_slots` (`backend/server.py:19916-19937`) is the whole
  blocker. Its guard is `if not league_id or not str(league_id).isdigit():
  return None` (line 19926-19927) *plus* the Sleeper meta fetch. Refinement to
  the briefed root cause: **ESPN and MFL league ids are numeric** (the
  `leagues` PK holds the platform-native numeric id,
  `backend/database.py:255-262`; `espn:`/`mfl:` prefixes are *member* ids,
  `backend/server.py:19170-19171`, `:11702`), so platform leagues pass the
  digit check, hit the Sleeper meta API, fail, and fall out via the
  `slots or None` at line 19937 — same `None`, slightly different path than
  the docstring implies. The fix must therefore branch on the **`leagues.platform`
  column**, not on id shape.
- Slot-filling is already 100% value-based: `optimal_starters` /
  `optimal_starter_slots` over `LINEUP_SLOT_ELIGIBILITY`
  (`backend/power_rankings.py:38-131`). "Based on dynasty values" is already
  true wherever a template exists — **the only missing input is the template.**

**Is the template already in the DB? No — plumbing plus one derivation.**
- ESPN sync fetches `view=mSettings` (`backend/espn_service.py:94`) — the raw
  payload carries `settings.rosterSettings.lineupSlotCounts` — but `parse`
  (`backend/espn_service.py:515-527`) extracts only name/size/playoff count.
  Nothing lineup-shaped is persisted.
- MFL sync reads the league export's `starters.position` limits **only** for
  superflex detection (`backend/mfl_service.py:735-747`); not persisted.
- So today there is no stored template for any non-Sleeper league, and no
  request-time source without a platform re-fetch.

### Fix design (recommended: Phase 1 now; Phase 2 logged as follow-up)

**Phase 1 — scoring-format-aware standard template, no schema, no sync change.**
This is literally the operator's ask ("just determine … based on dynasty
values"): give platform leagues an honest *standard* template and let the
existing value-optimal fill do the rest.

New helper in `backend/server.py` beside `_sleeper_lineup_slots`:

```
def _league_lineup_slots(league_id: str) -> list[str] | None:
    """Template resolution, all platforms.
    1. leagues row lookup by PK (one indexed select: platform, default_scoring).
    2. platform in ('espn', 'mfl')  →  standard template:
         1QB:    ["QB","RB","RB","WR","WR","TE","FLEX","FLEX"]
         sf_tep: ["QB","RB","RB","WR","WR","TE","FLEX","SUPER_FLEX"]
       keyed off leagues.default_scoring (NULL → '1qb_ppr', the existing
       convention at database.py:253).
    3. platform 'sleeper'/NULL → existing _sleeper_lineup_slots(league_id)
       behavior, byte-identical (live meta via the #179 cache).
    4. No leagues row, or any other platform (incl. 'league_demo') → None.
    """
```

- Standard template rationale: the 1QB shape matches `_MOCK_DEFAULT_LINEUP`
  (`backend/server.py:11698` — `QB/2RB/3WR/TE/FLEX`) in spirit; we propose
  `2WR + 2FLEX` vs the mock's `3WR + 1FLEX` **only if the operator prefers
  it — otherwise reuse `_MOCK_DEFAULT_LINEUP` verbatim plus a SUPER_FLEX
  swap for sf_tep, so the app has exactly one standard template.**
  Recommendation: reuse `_MOCK_DEFAULT_LINEUP` + (sf_tep → append
  `SUPER_FLEX`) — one constant, no second opinion of "standard".
- Call-site change: `backend/server.py:1158` (`_starter_impact`) switches to
  `_league_lineup_slots`. **Surgical**: the other two consumers are left
  untouched — mock draft (`server.py:11862`) already has its own fallback;
  power rankings (`server.py:20064`) would visibly light up the League
  Analyzer starters/bench split for ESPN/MFL leagues, which is outside this
  item (one-line follow-up if the operator wants it — flagged below).
- No API-shape change: `starter_impact` is an existing optional field; when a
  template exists it now appears for ESPN/MFL leagues with the exact
  already-documented shape (`server.py:1132-1155`). Clients already render
  it on presence — zero client work.
- Rosters are available: ESPN/MFL imports upsert `league_members`
  (`load_league_members` at `database.py:5585`), which `_starter_impact`
  reads at `server.py:1162`.

**Phase 2 (follow-up item, not this wave):** persist the *real* template at
import — precise for ESPN (`lineupSlotCounts` slot-id map → eligibility keys;
`mSettings` is already fetched), heuristic for MFL (per-position limit mins +
overflow flexes from `starters.count`). Requires a `leagues.lineup_slots`
column (schema bright line) and a re-sync/backfill story for already-imported
leagues. Phase 1's fallback remains the safety net either way.

## Item #313 — 1QB consensus QB values cap at 1 1st (bug, DraftRoom)

### Verbatim
> "Consensus QB value for the 1QB format should cap out at 1 1st (some QBs
> sitting at 2 1sts right now)"

### Root cause — CONFIRMED empirically

- 1QB consensus values: DynastyProcess `value_1qb` (`backend/data_loader.py:63-65`),
  optionally KTC-blended (`_apply_consensus_blend`, `data_loader.py:312-364`),
  mapped to seed Elo by `seed_elo_for_value` (`data_loader.py:96-108`) — the
  #117 affine recalibration anchoring DP 10000 → Elo ≈ 1927 (4 firsts).
- Live DP CSV, fetched 2026-08-13 and run through the exact production
  formula: **Josh Allen `value_1qb=7025` → Elo 1858.9; Drake Maye `5890` →
  1825.0** — both inside the `firsts_2` band **[1788, 1864]**
  (`backend/tier_config.json`, `1qb_ppr.QB`; mirrored in
  `docs/cross-client-invariants.md:17` and `mobile/src/utils/tierBands.ts:42`).
  Jayden Daniels (1786.6) and everyone below read `1 1st` or lower via the
  top-down band walk (`RankingService.tier_for_elo`,
  `backend/ranking_service.py:1272-1297`).
- Where the operator saw it: `DraftRoomScreen.tsx:1418,1440` labels rows with
  the client-side `tierForElo` walk over the served consensus Elo. The label
  is **derived** — the value is the defect.

### Mechanism — pin: VALUE-side recalibration, not a label cap

Two candidate mechanisms, very different blast radii:

| | (A) Value cap at pool build — **recommended** | (B) Label cap via tier bands |
|---|---|---|
| What changes | 1QB QB seed values compressed post-blend, pre-`seed_elo_for_value`, in `_apply_consensus_blend` (structurally beside the sf_tep TE-uplift block, `data_loader.py:353-357`) | `tier_config.json` `1qb_ppr.QB` bands collapse everything ≥1788 into `first_1` |
| Trade math | QBs re-price in every 1QB surface — **this is the ask**: "consensus QB *value* … should cap" | Unchanged — Allen still *trades* like 2 firsts; the complaint survives everywhere values are shown or summed |
| Cross-client invariants | **Untouched** — bands, hexes, enums identical; labels self-correct because they derive from Elo | `tierBands.ts` is a single format/position-agnostic ladder (`mobile/src/utils/tierBands.ts:9-43`); a per-position band fork means a mobile mirror redesign + invariants doc change + `apply_tiers` (`ranking_service.py:1306`) Quick Set bands losing reachable tiers for QB |
| Verdict | Honest, self-consistent, no client work | Cosmetic, invasive on the bright-line surface |

**Design (A), exact shape** — in `_apply_consensus_blend`, after the KTC
blend and before the Elo re-map, guarded by `fmt == "1qb_ppr"`:

- Two `model_config` knobs (read beside `_blend_config`,
  `data_loader.py:198-207`, same defensive defaults):
  - `qb_1qb_cap_elo` — default **1785.0** (top of `first_1` in every format
    cell of `tier_config.json`; 3 Elo below `firsts_2.min`=1788).
  - `qb_1qb_cap_knee_elo` — default **1580.0** (`first_1.min`).
  - Kill switch: `qb_1qb_cap_elo <= 0` → pipeline byte-identical (the
    ktc/tep-knob precedent).
- Let `K` and `C` be the DP-scale values whose seed Elo equals knee and cap
  (invert the affine map in `data_loader.py:90-108`; `K ≈ 1539`, `C ≈ 4771`
  under the default curve). For every pool row with `pos == 'QB'` and blended
  value `v > K`:
  `v' = K + (v − K) × (C − K) / (VALUE_MAX − K)` — **monotone piecewise-linear
  compression**: strict order among QBs is preserved (a draft board
  requirement; a hard clamp would tie Allen/Maye/Daniels), every QB lands in
  `[first_1.min, first_1.max]`, none can reach `firsts_2`. Sub-knee QBs and
  all non-QBs byte-identical. Under today's data: Allen 7025 → ≈3635 → Elo
  ≈ 1734 ("1 1st"). Round to 1dp like the blend (`data_loader.py:361`).
- Applied **post-blend** so KTC's rank-normalization can't push a QB back over
  the cap; sf_tep untouched (`fmt` guard).

### Blast radius (state it, don't hide it)
Every 1QB **consensus** surface re-prices top QBs downward once, at next pool
build: trade generation fairness and deck composition, calculator verdicts and
eveners, DraftRoom board and pick-equivalent labels, starter impact, power
rankings, anchor wizard landings, likes-you synthesized fairness
(`server.py:2909-2919`). **Untouched:** user personal boards/Elo (swipe-derived),
sf_tep pool, pick values (`backend/pick_values.py` — independent ladder), tier
bands and every client mirror. **One-time side effect:** trends/movers built on
`dp_values_history` (`backend/dp_values_history.py`) will register the step-down
as movement for ~the top-5 QBs on the transition day — cosmetic, self-heals,
worth a release-note line.

### Path recommendation
**Needs-operator-decision before build (bright line).** The code is small, but
it changes trade valuations in every 1QB league. Ask the operator to confirm,
in one message:
1. Value-side (A) over label-side (B) — recommended (A); the item's wording
   ("consensus QB **value** … should cap") reads as (A).
2. Compression (order-preserving, recommended) vs hard clamp at the cap.
3. Defaults `cap_elo=1785 / knee_elo=1580` as specced.
After a confirming yes, this section is build-ready with no PRD.

## Item #318 (BACKEND HALF) — Dismiss "awaiting them" trades (polish, Matches)

### Verbatim
> "Users should be able to dismiss trades awaiting the other users' review
> from the 'awaiting them' section. We should ensure that this removes the
> offer from the receiving users trade deck as well."

### How "awaiting them" and the receiver's deck actually work — CONFIRMED

- **"Awaiting them" is derived state, not rows.** `load_awaiting_trades`
  (`backend/database.py:6860-7006`) = the caller's `trade_decisions` rows with
  `decision='like'` (up to 500, `:6885-6893`) minus keys that matured into
  `trade_matches` (`:6946-6960`), deduped by
  `(league_id, frozenset(give), frozenset(receive))` (`:6971-6977`; the same
  trade re-liked across deck regenerations produces **multiple rows sharing
  one key**). Served by `GET /api/trades/awaiting` (`backend/server.py:13008`).
  There is **no per-item id to flip** — dismissal must suppress a key.
- **The offer reaches the receiver's deck at generation time.**
  `_inject_likes_you_cards_impl` (`backend/server.py:2819-2939`) reads
  league-mates' like rows via `load_recent_league_likes`
  (`backend/database.py:4425-4472`, 90-day window) and either injects a
  synthesized `likes_you` card or flags+boosts an organic equivalent. Decks
  are per-(user, league, format) cached jobs, ~30-min reuse
  (`server.py:9744-9749`), dropped by `_invalidate_trade_jobs`
  (`server.py:5257-5286` — takes any `user_id`, in-process, single web
  worker).
- **A dangling like can still mature into a match**: `check_for_match`
  (`backend/database.py:6554-6633`) scans the *target's* like rows when the
  receiver later swipes the mirror (`server.py:10265-10289`). Dismissal must
  block this too, or the "dismissed" offer springs back as a match.
- Existing precedent for dismiss semantics: `dismiss_match`
  (`backend/database.py:7016-7051`) — per-user, idempotent, **no Elo**.

### Fix design

**Schema (bright line): one nullable column.** `trade_decisions.retracted_at`
(String, ISO UTC, NULL = live). Added to the Core table def
(`database.py:308-317`) and to `_migrate_db`'s idempotent
`ALTER TABLE … ADD COLUMN` list (`database.py:1868`, pattern at `:2004`).
The decision row itself is never rewritten — audit trail, swipe Elo signals,
impressions training joins (`:4478` onward) and `_past_decision_keys`
(`trade_service.py:2176`) all deliberately keep seeing the row (a dismissed
offer must NOT resurface in the *dismisser's own* deck as a fresh card).

**Suppression reaches the receiver at exactly four touch points:**
1. `load_awaiting_trades` — add `retracted_at IS NULL` to the SQL where
   (`database.py:6890` region) → gone from the dismisser's Awaiting list.
2. `load_recent_league_likes` — same filter (`database.py:4452` region) → the
   receiver's **next deck generation** neither injects the likes-you card nor
   flags/boosts the organic equivalent.
3. `check_for_match` — same filter (`database.py:6599` region) → a retracted
   like can never mature into a match.
4. `_invalidate_trade_jobs(user_id=partner_id, league_id=league_id)` called
   from the new route → the receiver's *cached* deck job is dropped, so their
   next `/api/trades/generate` regenerates without the offer instead of
   serving the ≤30-min-old snapshot.

**Re-like reappears by construction:** a later like writes a new row with
`retracted_at` NULL — no timestamp bookkeeping, no dismissals table.

### FROZEN API CONTRACT (the Matches mobile agent codes against this verbatim)

```
POST /api/trades/awaiting/dismiss
Auth: session cookie/token, @_gate_unverified_write (same gate as
      /api/trades/matches/<id>/dismiss, server.py:13091-13092)

Request body (JSON, all fields required):
{
  "league_id":  "<string>",            // as returned by /api/trades/awaiting
  "my_give":    ["<player_id>", ...],  // non-empty; caller's give side, verbatim
  "my_receive": ["<player_id>", ...],  // non-empty; caller's receive side, verbatim
  "partner_id": "<string>"             // the awaiting tile's partner_id
}

Semantics:
  Marks EVERY trade_decisions row of the CALLER with decision='like', the
  same league_id, and set-equal give/receive (order-insensitive,
  frozenset comparison — matching load_awaiting_trades' key) as
  retracted_at=<now ISO UTC>. No Elo signal, no swipe row, no effect on
  trade_matches. partner_id is used ONLY to invalidate that user's cached
  trade-deck job (best-effort, in-process); it can never mutate the
  partner's data.

Responses:
  200 {"status": "ok", "dismissed_likes": <int >= 0>}
      dismissed_likes = number of like rows newly marked. 0 is still "ok"
      (idempotent repeat, or key already matured/absent — never a 404).
  400 {"error": "league_id, my_give, my_receive, partner_id are required"}
      any field missing/empty, or malformed JSON body.
  400 {"error": "session not initialised"}   // no user in session (matches
                                             // dismiss_trade_match, :13107)

Idempotency: repeat call with the same body → 200 {"status":"ok",
  "dismissed_likes": 0}. Safe to fire-and-forget with one retry.

Client expectations (informative):
  - Optimistically remove the tile on 200; re-fetch /api/trades/awaiting to
    reconcile.
  - A like re-swiped AFTER a dismissal legitimately reappears in Awaiting.
  - Dismissing does not touch mutual matches: if the trade matured while the
    screen was stale, the tile is already gone from Awaiting and the match
    is governed by the existing match endpoints.
```

Implementation: route handler beside `dismiss_trade_match`
(`server.py:13091`); new `retract_awaiting_likes(user_id, league_id, give,
receive) -> int` in `backend/database.py` beside `load_awaiting_trades`
(select the caller's live like rows in that league, compare frozensets in
Python — JSON ordering makes SQL set-equality impossible — update matching
ids in one `WHERE id IN (...)` statement inside `engine.begin()`).

### Known residuals (documented, accepted)
- The receiver's **client-held** deck (already fetched into app state) shows
  the card until their next generate; same staleness class as untouchables /
  not-interested. Server-side cache is handled by touch point 4.
- Any push/inbox **notification** already sent for the like cannot be
  retracted; out of scope.
- Retraction does not undo the like's original Elo signal — by design,
  mirroring `dismiss_match`'s no-Elo doctrine (`database.py:7026-7028`).

### Path recommendation
**Full gates, buildable from this plan — no separate PRD.** One design
semantic for the operator to see (not a blocker; recommend as specced):
a dismissed like also stops future **match maturation** (touch point 3). If
the operator instead wants "hide from my list but let a match still form",
touch point 3 is deleted — say so before build, because the two behaviors are
irreversible in opposite directions from the user's viewpoint.
