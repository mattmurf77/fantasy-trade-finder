# Bounded prepared inventory — implementation revision

2026-09-22. This revision precedes implementation and supplements [the original plan](plan.md). Owner authorization remains plan, build, deploy, then prepare all resolvable linked teams. Caching remains OFF while this revision is qualified.

## Why the revision is necessary

The second production canary, on merge `2cff90c7`, failed with `InvalidArtifact` before saving any inventory. Its precise cause is still unknown; the new allowlisted diagnostic codes and phase labels will identify it without logging private data. Separately, the unchanged real constructor produced 13,728 offers in a dense synthetic 12-team case. Its full bundle was 461,530,265 logical bytes / 15,083,835 compressed-text bytes and exceeded the whole-copy node guard before saving. This is a reproduced capacity defect, not a proven explanation of that production failure.

Do not solve this by increasing the global JSON envelope limit, reducing search budgets, dropping offers, changing rankings/fairness/model arms, or adding paid infrastructure. Store and validate bounded records rather than repeatedly cloning one enormous object.

Evidence limitation: that dense fixture has suggestion telemetry disabled and therefore no candidate-set singleton. Candidate-set capacity needs a separate telemetry-enabled test; its size cannot be inferred from the 461 MB measurement.

## Contract

1. Add a versioned private staging/sealed manifest, ordered pages, and original diagnostic nodes. Reuse existing sweep/target/worker and account-lifetime primitives. Staging is never ready or adoptable; every participant is deletion-indexed before any private content is written.
2. Capture logger batches incrementally. Serialize individual card/evidence pairs and byte-bounded pages. The full native generator may still retain its cards; packaging must not add full-inventory copies or full expanded diagnostic graphs. Generate the public projection lazily in preparation mode. No change to native search, order or offer count.
3. Keep original proof and valuation strings byte-exact, original IDs/terms/order/timestamps, first authenticated snapshot representation and source links. Validate duplicate snapshot representations by expanded scoped identity, not raw packing equality. Never canonicalize away native proof-string identity.
4. Page metadata, candidate dependencies, source/receipt records and mutations are part of the resource contract, not exceptions. Retain existing candidate-set JSON compatibility as an explicitly bounded indivisible record, with a documented measured byte ceiling. Oversized indivisible records fail with a numeric reason, never a partial deck. Bound total SQL parameters per statement as well as individual encoded rows; split writes by bytes, not merely 200 rows.
5. Before sealing, verify complete generation, contiguous ordinals, unique trade/impression identities, exact card/evidence terms, candidate links, complete scoped diagnostic DAG, checksums, original expiry and before/after input/model receipts. DAG bounds apply before expansion allocation, including repeated-reference amplification. Small caches/indexes must not conceal retained full expanded graphs.
6. Seal and active-scope replacement are atomic. Failed/abandoned staging leaves an earlier valid inventory intact. Every append/seal verifies the original generation claim and participant/account lifetimes. Short work units renew bounded leases where needed; retries never renew original artifact expiry. Crash recovery may regenerate abandoned unsealed work, but never adopt it.
7. The initial implementation repeated full integrity/semantic preflight before the first actionable 30 cards. Measured qualification below revises admission: full semantic validation happens against a pinned immutable root before sealing, with a reserved store-minted versioned attestation. Admission checks that attestation and every root-authenticated compact disposition entry, then fully validates each publishing batch and its original diagnostic closure. A corrupt late page may leave an earlier independently valid prefix, but the affected batch must never be published and no fresh-generation suffix may be mixed after commitment. Missing, legacy or unknown attestation is a cache miss, never an inferred validation pass.
8. Existing freshness, source, disposition, source-like, model, expiry and read guards remain mandatory. Commit original candidate/diagnostic/impression evidence before checkpointing and publishing. Bind every checkpoint to inventory root and lease token; validate only the newly advancing exact suffix, not the entire historical prefix on every batch. Retries recover exact IDs and first-adoption timestamps without duplicate exposure rows.
9. Deleting any consumed participant removes/fences staging, sealed and retired manifests plus all pages/nodes. Export metadata only. Prune abandoned/expired artifacts in bounded transactions. Old binaries cannot know new private tables: rollback to a pre-v2 binary requires cache OFF plus verified v2 purge, or a deletion-compatible bridge release. Disabling caching alone is a safe operational rollback without a binary downgrade.
10. No simulated human sessions, impressions, actions, rankings, notifications or platform trade sends during preparation. No new adoption-success claim without real evidence. Existing authentic app actions remain the only source of behavioral success metrics.

## Measured admission revision — 2026-09-23, before implementation

The actual native constructor produced 936 offers in a three-team synthetic case. The initial v2 implementation preserved every original offer/proof/order, prepared in22.36s, and adopted in37.84s, but the first30 durable offers took17.06s. Repeated admission preflight cost12.45s; the native worker itself took10.05s. Local SQLite, suggestion telemetry off, peakRSS270221312B; not production/device timing. This is insufficient for the owner's three-second goal. Merely caching an expensive full validation is not a product improvement.

Independent review identified repeated all-node SQL/decode, full diagnostic expansion, native proof parsing, and a second full-card hydration solely for disposition checks. Do not weaken per-offer validity or drop offers to fix this. Move the invariant full-inventory work into silent preparation; keep current-input and exact publishing-batch work at admission.

### Revised implementation specifications

- **A, store:** add `admission` as another bounded page kind in the existing page table (no new infrastructure). Freeze the complete descriptor tree/root while staging transitions to validating, before semantic validation. The validating reader must verify every page/node against that pinned root; final seal checks the same pinned root/header/metadata/counts and original live generation token. Only the sealer may mint the reserved versioned semantic attestation after that scan succeeds. Bind the attestation to validated tree, header, original metadata, counts, codec and validator identity; bind it into the final manifest root. Reject caller-supplied attestation in metadata. Sealed reader must expose a verified attestation, not a caller-controlled boolean. Checksums protect integrity under trusted database/store-writer authority; they are not protection against an administrator replacing the whole database.
- **C, codec:** emit bounded compact admission entries with ordinal, trade ID, exact ordered give/receive IDs, partner, likes-you flag, standing-offer marker, source-like impression ID, original impression ID and expiry. Full seal validation checks exact correspondence with every native card/evidence pair plus global order/count/uniqueness. The fast sealed opener validates scope/version/metadata/candidate/attestation/expiry, not all native proofs again. It scans every authenticated admission entry and exposes lightweight disposition objects. Publishing batches still restore native proofs, validate complete original diagnostics/evidence and recheck their exact admission entries before commitment. Existing full preflight remains available for sealer/tests; do not silently change its meaning.
  Dense qualification found two complete compact-index scans (opener integrity, then runtime dispositions) still cost3.85s to first30, including1.54s opening. Fuse a bounded100-entry disposition callback into the existing complete opener pass. An ordinary current-disposition mismatch is a distinct cache miss, never evidence of stored corruption. Preserve whole-index validation, exact original order and counts; no card or search limit changes.
- **Parent, runtime:** use only the recognized store-attested opener for v2 interactive adoption; verify all disposition entries before starting. Keep fresh provider/source/model/account receipts, read guards, original expiry, current dispositions, exact evidence-before-checkpoint-before-publication and no mixed fresh suffix. Runtime lookup of original records stays batch-local. No simulated production interaction to prove adoption.
- **Parent, cleanup boundary:** the five-minute cleanup tick currently applies a60-second total-age timeout to all running memory jobs. Private preparation is governed by its existing live300-second persistent generation claim and bounded same-token renewals, not that unrelated interactive timer. For v2 interactive adoption, only successful durable batch/checkpoint progress resets the existing60-second stall timer; original artifact/card/read-guard expiry remains unchanged. Ordinary generation retains its current timeout. Test these scoped distinctions; do not extend a stalled adoption merely because it is polling or reading.
- **Parent, retention:** disabling cache generation/adoption must not disable hourly expiry/abandoned-stage pruning. Retention cleanup remains private, bounded and silent; no discovery, refresh or new cache generation while rollout is off. The24-hour bound is eligibility; physical deletion occurs on the next successful maintenance pass, not an exact-time guarantee.
- **A/Parent, corruption recovery:** a proven invalid stored payload must not remain an active reusable cache. Add a narrowly fenced retire operation for the exact failed inventory ID/root; clear its active pointer/adoption token without deleting durable exposure history or touching a replacement. Invoke only for store integrity/resource-invalid or codec semantic failures, not transient SQL outages or stale-work errors. An earlier valid prefix remains the failed job's only output; the next request can miss and use ordinary generation, and later preparation can replace the retired artifact. B verifies exact-root fencing, no repeated corrupt hit and retryability after transient writer failure. Retention pruning runs before the maintenance `_active` early return so a long deferred sweep cannot indefinitely prevent cleanup.
- **B, independent review:** challenge forged/missing/unknown attestations, caller-reserved-field injection, mutation between freeze/scan/seal, late-page corruption before admission, wrong/duplicate/missing index entries, modified source-like/expiry fields, prefetched corruption, deletion/stale inputs and interrupted evidence publication. The updated late-corruption expectation explicitly permits only the preceding valid prefix. Verify unchanged native proofs/order and quiet preparation.

Do not edit model-hashed source while the initial dense baseline is running. After the revision, repeat actual936 and13728 qualification, including full inventory parity, SQL bounds, first30/full timing and RSS. Qualification is not complete until improved admission is measured, full/hosted gates are green and a fresh production canary passes. ## Active adoption feedback boundary — before implementation

An admitted inventory must remain usable while its owner acts on the first30 cards. The full admission receipt remains unchanged and must still exactly match before adoption. It is not the per-batch invariant: ordinary like/pass writes trade history and within-tier ranking feedback, so comparing that whole receipt after every batch incorrectly revokes unrelated prepared offers.

- **B, input receipt:** add `active_dependency_receipt` beside the existing full receipt, preserving the full receipt's default schema and hashes. The active receipt retains current source/binding/scope, player/market/availability/pick/lineup inputs, preferences, model configuration/flags, original ranking seed and explicit overrides/stamps, ranking-only comparisons/placements/confidence, and persistent explicit inputs for all consumed managers. Retain member ranking Elo/confidence snapshots, users' ranking method/tiers/overrides/scale/stud settings, league/asset preferences, picks and recorded picks, league data, standing offers, suppression/reset policy and trade block. Preserve unknown swipe types conservatively; exclude only the recognized `trade`/`disposition` feedback rows. Direct partner SQL board or outlook edits must revoke an active job even without a process-local epoch notification.
- Do not hold mutable aggregate ratings, trade decisions/matches, exposure/outcome history, or action-derived disposition/exclusion sets invariant during active adoption. Trade feedback changes `_trade_swipes` and computed Elo but does not publish `member_rankings`, alter explicit overrides, release placements or add ranking comparison evidence. Standing offers, deck suppressions/fatigue resets and proposals remain guarded unless a separately reviewed current-card projection covers them. This is a narrow active-adoption rule, not permission to reuse an old inventory for a new request whose full receipt differs.
- **Parent, runtime:** capture and compare the active receipt before and after each evidence batch, retaining existing model, source, account, epoch, expiry and read guards. Apply current exact pass/source-like and awaiting/matched-package exclusions at publication/public reads so an ordinary first like/pass—including a like creating a mutual match—removes affected cards without invalidating unrelated frozen terms. Do not regenerate, reprice, reorder or mix in a fresh suffix, and preserve original evidence and durable prefix accounting. Failed history verification must not silently assert current interest. A history mismatch is not stored corruption and must not quarantine the artifact.
- **B, independent controls:** witness real first-prefix Flask like/pass failure before the repair, then require successful unrelated continuation with unchanged original proof and persisted decision. Keep direct-SQL counterparty board/outlook invalidation controls. Add root/runtime tests for matched-like and source-interest/exclusion projection. No provider calls, new database fields or production changes are part of this amendment.
