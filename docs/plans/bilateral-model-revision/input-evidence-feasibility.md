# Existing-input feasibility: starter benefit and age provenance

September 22, 2026. Read-only source investigation under [the parent specification](spec-input-evidence-feasibility.md). No runtime/test changes, provider calls, credential access, database inspection or production actions. This establishes source-contract feasibility, **not** whether any deployed league currently has a usable snapshot, forecast accuracy, manager acceptance or release qualification.

## Finding

There is an implementation-feasible, **conditional Sleeper-only** path: reuse the existing immutable Win Now player/week forecasts and normalized league snapshot through a new cache-only reader. The data include both teams, actual slots, league scoring and active/reserve/taxi membership. A missing, stale, mismatched or approximate record must leave actual starter benefit Unknown. Calling the existing Win Now loader from Find a Trade would not meet the latency requirement: it can fetch multiple providers and run a full season simulation.

Two qualifications prevent treating existing records as universally ready:

1. Durable snapshots preserve forecast normalization time and serving expiry, but not every original provider-response observation timestamp. Some inputs may have come from an in-process cache. A narrow provenance addition at existing preparation is needed for exact source-age checks.
2. Win Now is an experimental, uncalibrated forecast model with explicit availability assumptions and, for some formats, scoring exclusions. A successful Win Now snapshot is not automatically exact-format, complete-availability evidence for a new enforcement rule.

Missing age is separately recoverable **before** pool construction: the raw player cache and nullable players-table age distinguish absence from a genuine 25. The ordinary `Player` and current owner request capture lose that distinction. Preserve a private pool-bound provenance sidecar; do not rewrite public ages, prices or all player schemas.

### Forecast and snapshot contract

`season_forecasts.import_projection_snapshot` validates a complete batch envelope: schema version `1`, provider, model version `player_week_normal_v1_experimental`, season, explicit weeks, timezone-bearing capture/publication times, unique player/week identity, supported positions, finite event vectors and availability in `[0,1]` or Unknown. It hashes the content. Stat vectors are **conditional on playing**, not dynasty values. Revision/publication timestamps are explicitly not evidence of historical availability; imported files keep their original capture time. Full-feed game-date/kickoff cutoffs survive roster filtering.

`fetch_projection_snapshot` (`season_forecasts.py:212`) fetches Sleeper's experimental weekly projection feed for each required week. It does not turn ADP-only placeholders into forecasts. Verified byes produce zero availability/zero points. A current injury status makes future availability Unknown; no injury status yields availability `1` with `availability_basis=current_status_only`. The latter is a disclosed assumption, not a calibrated season-long health probability. Row `source_updated_at` is retained separately. Provider quality explicitly says experimental, uncalibrated and not historical-as-of validated.

`win_now_service.load_league` only accepts supported in-season Sleeper leagues. It captures all teams' active player IDs, `all_player_ids`, reserve/taxi `inactive_ids`, recorded starters, actual starter slots, active roster capacity, raw/effective scoring, schedule/checkpoint and trade rules. It rejects unsupported lineups, live weeks and other unsupported formats. ID mapping must use platform + league + season + roster identity; numeric IDs alone cannot distinguish Sleeper from ESPN/MFL. Co-owner/account identity must resolve to the exact captured roster, not an assumed owner-ID equality.

`load_bundle` performs source acquisition and `simulate_season` before persistence. It uses `win-now-season-v1-beta`, normally 1,000 simulations (bounded 256–4,000), not a cheap cache getter. Its snapshot identity binds normalized league, forecast snapshot ID, service model version and simulation count. The baseline also carries forecast/model/input hashes. The linked durable tables are `season_forecast_snapshots` and `season_projection_snapshots` (`database.py:69,76`); the projection payload is `{league, baseline}`, with forecast ID and created/expiry timestamps in columns. Save methods enforce immutable payload identity; history is retained for 400 days, **not** fresh for 400 days. There is no existing cache-only forecast/projection read method in `win_now_store`.

The Win Now serving lifetime is at most 900 seconds and bounded by forecast capture + 900 seconds and the earliest whole-feed game cutoff. Date-only cutoffs conservatively mean midnight UTC, not an invented kickoff. Missing cutoffs, old captures or captures over one minute in the future are rejected. `season_forecasts.snapshot_freshness` has a separate 24-hour default; using that default would wrongly relax this serving contract.

Exact source age is not fully durable today. `_fetch` (`win_now_service.py:93`) caches meta/rosters for 30 seconds, users/future schedule/projection responses for up to 300 seconds, retaining fetch-start timestamps only in memory. A newly normalized forecast batch receives the current invocation's capture time even when raw responses are cache hits. The league payload lacks those original observation timestamps. Importing a previously captured normalized file correctly preserves its age, but does not solve the live-cache provenance gap. Do not relabel normalization time as a fresh network observation or `source_updated_at` as receipt time.

Finally, `load_bundle` can remove unsupported nonzero `st_ff`, `st_fum_rec`, `st_td` and `fum_rec_td` coefficients, retaining `scoring_exclusions` and a beta warning. That deliberate approximation must not silently satisfy “exact league scoring.” Initially qualify only snapshots with no relevant exclusions; any broader approximation needs a separate explicit contract. K/DEF coefficients for absent slots are different: `normalize_scoring_for_slots` removes only known irrelevant categories.

### Roster, availability and cuts

The full-roster pure boundary already exists in `trade_roster_adapter.build_context` and `trade_roster.evaluate`. It distinguishes observed/estimated rules, unavailable and reserve/taxi assets, capacity Unknown, and explicit caller-resolved cuts. The wrapper's player-cache freshness is based on file age up to 48 hours, not a player/week availability forecast. Its “no live point provider exists yet” comment predates the separate Win Now foundation; it should not be used as evidence that the foundation is absent.

`season_simulator.select_projected_lineup` (`:124`) is a pure Hungarian assignment over actual weekly projected points and legal slots, including overlapping flex eligibility. `projected_lineup_points` (`:181`) applies exact trades and returns weekly before/after-ready rosters without Monte Carlo. It validates the full league/horizon and checks starter coverage and unknown availability that could change the chosen lineup. It may still emit `unprojected_bench_excluded`; success alone does not prove complete roster coverage. A strict initial measured-benefit contract should require complete eligible before/after coverage for both teams, or explicitly retain partial-coverage Unknown rather than upgrading this warning to certainty.

This lineup helper does **not** resolve roster capacity or choose cuts. Win Now's optimizer separately rejects `mandatory_drop_unhandled` (`win_now_optimizer.py:182`), while the roster evaluator reports explicit cuts/overflow. For a larger incoming package, require observed post-trade active capacity and either no necessary cuts or a specific valid cut plan whose lost production/value is included. Do not assume spare reserve space, select a free cut, or count picks as active roster occupants. Inactive traded assets need an explicit legal status transition; the initial cache-only path can leave them Unknown rather than auto-activate them.

`trade_outlook_utility.evaluate_outlook_utility` (`:60`) already accepts fresh points, basis and units and recomputes both full rosters after resolved cuts. Its projection input is a scalar per player. Do not sum rest-of-season player points and optimize one fixed lineup: weekly byes, availability and flex choices differ. Use the existing weekly assignment, preserving an explicit shared horizon and per-week deltas; any aggregation or outlook weighting is a later model decision. Do not invoke full `evaluate_trade` simulations per ordinary generated offer.

### Platform gap and other caches

`_league_lineup_slots` (`server.py:28233`) explicitly returns a standardized dynasty-value template for ESPN/MFL/Fleaflicker, not observed rules. `leagues` (`database.py:400`) persists mapped roster lists and coarse `1qb_ppr`/`sf_tep`, not the full source settings. `espn_service.parse_league` (`:475`) drops roster-entry slot/status and most settings from the fetched payload. `mfl_service.parse_bundle` (`:617`) drops roster status/full rules; `detect_scoring_format` (`:776`) only reduces QB/TE signals to the coarse format. Raw responses already exist during these platforms' import/refresh paths, so a later adapter can normalize and capture them there without another Find a Trade fetch. The present persisted data cannot certify real slots, scoring or cut capacity. A source player-ID crosswalk alone does not fix that.

General Outlook's fan-out cache stores weekly matchup results/pairings. Its non-matchup league/roster/user reads intentionally remain live (`_outlook_sleeper_fetch`, `server.py:29236`); it is not a hidden fresh raw-roster cache. `SleeperProjectionsStrength` and `OwnModelStrength` remain registered stubs (`outlook/strength.py:372`). Historical team totals and value-based starter proxies must remain separately labeled.

## Smallest bounded integration proposal

Parent should write a separate implementation spec before changes:

1. **Preparation provenance at existing Win Now boundaries.** Preserve original source-response observation times/identities through `_fetch`, `load_league` and `_forecast_batch` into the immutable saved evidence, along with normalized schema/adapter versions. Keep normalization time distinct. Existing successful season-projection requests and the existing Win Now background search worker (`win_now_api.py:76,97`; `win_now_service.py:549`) already populate these tables. Reuse that preparation; do not trigger a search, provider fetch or simulation from `_owner_generation_context`. A never-prepared league remains Unknown. Additional automatic warming requires its own authorization/spec, not a new queue design here.
2. **One cache-only joined read.** Add a bounded reader in `win_now_store` joining the latest eligible league projection to its exact immutable forecast ID. At owner-context capture, validate platform/season/roster mapping and exact ownership against captured request rosters; validate source observation age, expiry and game cutoff, supported schema/model/dependency identities, unchanged full scoring/slots and complete same-horizon evidence. Never silently repair a mismatch with current provider data. If the current request lacks independent fresh settings/status, label the result “as of captured snapshot,” not freshly reverified provider state. Legacy records missing required provenance fall back to Unknown.
3. **Immutable private request evidence.** Capture a versioned bundle once for all managers in the request, with roster/rule/forecast hashes, timestamps, horizon, coverage, availability basis and reason codes. Preserve it for replay; do not repeat entire forecast batches in every offer proof. Each exact offer can reference that bundle plus compact both-team before/after lineup and cut evidence. Gate qualification on both teams independently. A missing partner input cannot inherit viewer certainty. Recheck expiry/version before publication without fetching. Public cards, tier/pick equivalents and other managers' boards stay unchanged/private.
4. **Pure measured diagnostics first.** Reuse weekly assignment and roster legality for exact packages with memoized unchanged baselines; measure incremental cost before allowing it into uncapped generation. Missing/stale/unsupported/mismatched data produce reasoned Unknown, not a fabricated point gain or a silent dynasty-proxy substitution. This investigation does not authorize changing admission, weights, thresholds or inventory based on the three audited examples.

This avoids new infrastructure and critical-path provider calls, but requires narrow source-provenance/capture code and performance verification. Forecast accuracy/coverage, availability assumptions and counterparty willingness remain independent quality gates. The underlying sources cannot support a universal measured-starter-benefit claim today.

## Missing-age provenance

`database.sync_players` (`:10434`) stores a missing/unparseable raw age as NULL, with `birth_date` and `last_synced` retained (`database.py:1319,1320,1339`). It does not impute 25. The raw bulk-player cache also retains missingness.

The loss occurs in `server.build_universal_pool`: the enriched branch uses `db_row.get("age") or int(raw_age or 0) or 25` (`:1624`), and the raw-only branch uses `int(raw_age or 0) or 25` (`:1643`). `Player.age` has no provenance field (`ranking_service.py:255`). `_owner_selected_assignment` currently serializes only position/age/team/injury status for players (`server.py:14867`), so a captured age 25 cannot reveal whether it was genuine. Current DB/cache reads cannot retroactively reconstruct the exact old pool input; treating every 25 as imputed would also be wrong.

Narrow proposal: at `_build_universal_pools_locked`/`build_universal_pool` (`server.py:1757`), where the same raw cache and one enriched DB read already build both formats, construct a private sidecar keyed by player ID and the exact pool generation. Record selected source, validated raw age or Unknown, whether fallback was used, source observation/sync time where available, and provenance schema/identity. Preserve source priority and leave existing `Player.age`, valuation and public serialization untouched. Copy the relevant sidecar into versioned owner request evidence, separate from the strict `Player(**attrs)` replay payload; missing legacy sidecars remain Unknown. Bind it to pool invalidation/rebuild so a newer raw cache cannot be accidentally paired with older Player objects.

A later candidate-only age-evidence accessor can distinguish a true observed young player from default 25, using captured validated positive age and provenance. Boolean/nonfinite/invalid ages are not evidence. If birth-date derivation is desired, specify its as-of date and provenance separately; it is not necessary for the first narrow fix. This is a feasible correction to future evidence collection, not grounds to rewrite historical proofs or globally change player/value behavior.
