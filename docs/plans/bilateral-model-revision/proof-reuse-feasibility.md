# Exact-proof reuse feasibility — read-only audit

Agent C followed [the parent specification](spec-proof-reuse-feasibility.md). No runtime, grader or third performance prototype was implemented.

**Verdict: potentially feasible with a new authenticated evaluation-state boundary; not safe as a drop-in request-hash cache today.** A registry can prove that a server generated an exact proof, but cannot by itself prove that the dependencies of a fresh final evaluation are unchanged. Until that second obligation is established, the existing full evaluation must run.

## Evidence of possible redundant work

`server._owner_cards_valid` first checks proof/card matching and constructor identity, then invokes the selected batch evaluator on every matched occurrence and replaces its proof with the fresh result. The evaluator constructs another `_Search`, recomputes full-board coordinates, market/roster inputs and each card's decision. It preserves duplicates and authenticates partial selection separately for each occurrence.

C compared the retained strict policy3 native export with the actual worker's stored final proofs. All **3,306 served occurrences** have a matching exact native package, and all original proof payloads equal the final re-evaluated payloads after converting only the database JSON formatting back to the original compact sorted encoding. Zero payloads changed. This is one stable reconstructed context, not a proof for every context or mutable production execution. It suggests work worth investigating; it is not a measured reuse speedup.

## Dependency audit

| Dependency | What a valid certificate must cover |
|---|---|
| Entire request, not just traded assets | All players, full seed universe, both raw boards/source maps, rosters, league/member identity and membership, `has_rankings`, format, selected/inferred outlooks, every preference, slots/capacity/inactive state, draft-context/own-next/expired lists, selections and their order, exact-give/partial authority, requested fairness, intent/swap/lateral scope, dispositions/exclusions and complete configuration. Full-universe percentiles mean even a non-rostered, nontraded player's board value can change proof bytes. |
| Player objects | `_owner_generation_context` copies the player mapping but not its `Player` objects. Position, team-as-pick marker, age and injury affect valuation/roster features. Fallback outlook inference additionally uses `search_rank` and `pick_value` through `dynasty_value`. An offer-only `{position, age, team, injury}` projection misses those latter fields. Capture full supported player data or fail to the ordinary evaluator. |
| Effective numerical configuration | `_Search` merges `_c` values, raw `_cfg` owner limits and caller configuration. `_cfg_override` applies during much of evaluation, but bilateral initialization also calls `elo_to_value` outside its own override. Therefore bind actual resolved configuration and ambient thread-local state, not merely `context['config']` or the reported subset of config keys. `reload_config` mutates the global dictionary in place. |
| Feature flags and pricing | `FLAGS` is a live proxy. Crown-asset reads in package pricing/overpay are not pinned by `_cfg_override`; a refresh can change both prices and proof eligibility. Outlook-inference flags are gated by optional signals currently absent on this owner path, but their transitive dependency remains part of any future generalized capsule. Stud mode is explicitly pinned to `market` during the owner evaluation loop. |
| Static evaluator state | Bind selected generator/evaluator implementation and version; owner/bilateral/candidate constants and weights; loaded `TIER_CONFIG`/`ORDERED_TIERS`; roster `ELIGIBILITY`/`UNAVAILABLE` and assignment implementation; age curves; pick-identity parser and generic-rung definitions; pricing/overpay helpers. File hashes alone do not detect an in-memory monkeypatch or changed loaded table. Static data can instead be immutable under a process/code-generation identity, with tests enforcing that assumption. |
| Historical proof and mutable caches | Keep the exact original `OwnerDecisionContext` and JSON bytes. `_side_cache`, `_features`, `_plan_cache` and candidate composition enrichment are mutable search internals, not a sealed proof of unchanged inputs. Never hand them out or use their object identity as the certificate. |

### DP/pick distinction

There is **no direct DP file/provider read in the reviewed owner decision loop**. `make_consensus_value_fn` converts the captured seed Elo through the current value/age configuration. First-round package exemption parses IDs; the generic-rung lookup is static. DP-derived prices have already entered upstream seed/pick data. Consequently a DP cache refresh alone, with identical captured owner inputs, does not justify inventing a new owner-evaluator dependency or bypassing any freshness check. If fresh DP preparation changes the captured seed or pick data, that must invalidate reuse. The complete owned-pick ledger, provider legality, latest rosters and final significance checks remain separate serving responsibilities and must still run.

### Existing hashes are insufficient

`_owner_selected_assignment` intentionally removes serving/significance settings, sorts selection arrays and omits some player fields. Its role is experiment assignment, not trusted exact execution authentication. `_owner_request_snapshot` further projects boards/players to the offered assets. The proof's market and personal-board hashes likewise do not cover every decision dependency. Do not repurpose any of these as a cache authorization token, and never accept a matching client-supplied digest or historical proof as permission to reuse.

## Narrow proposed design, not implementation approval

1. Introduce a private, typed **evaluation capsule** before generation. It must own detached, read-only request inputs and resolve all relevant ambient dependencies. Preserve ordered arrays, numeric types and every input used for ranking/proof construction; reject unsupported values to the existing path instead of using `default=str`. Record the exact generator/evaluator and applicable policy identity. No public fields or persisted binary cache are needed.
2. Establish that generation actually consumed that capsule consistently. This is the unresolved architecture obligation. Options are pure dependency injection, or a complete monotonic generation/epoch guard spanning every mutable dependency. A before/after value hash alone misses change-and-change-back races. Existing flags normally swap dictionaries on reload, so retaining the exact old dictionary can guard official replacements; `_cfg` updates in place and shared Player/nested-preference mutations lack the required universal epoch. Merely adding that flags check is insufficient. Changing evaluation to freeze previously live inputs must be an explicit reviewed semantics decision, not disguised as an optimization.
3. Immediately after successful generation, mint a request-local registry retaining strong references to the original card and proof objects, exact ordered terms/participants/prices, original JSON bytes, partial-selection evidence and capsule identity. Keep it only in trusted worker-local state. Do not serialize it, place it in the public card, key it by trade ID alone, share it across requests or persist it for polling/restarts. A copied/replaced/historical/unregistered proof takes the ordinary evaluator path even if its JSON is equal.
4. At final owner validation, keep all current match/version checks. Authenticate the same registry and unchanged authoritative dependencies; then return that original proof only for a certified occurrence. Any missing or changed certificate invokes the existing evaluator, or fails closed according to its current error handling. Preserve input order and multiplicity; never deduplicate the accepted list. Mixed reuse/miss batches must be tested against the existing full-batch evaluator, because cache enrichment/order is part of exact proof parity.
5. Continue every final roster, market/disposition, significance, policy3, current-model/policy revocation, account/job supersession and durable-write/publication check. Preserve final `matches()` during impression assembly, all private proof/diagnostic contents, first30 durability and later exact prefixes. A valid owner proof is not permission to serve after any of these checks fails.

The initial private experiment should be confined to one explicit worker entrance and current revision. Other selected, overhaul, historical-card and legacy entrances retain the normal evaluator unless independently supported. Disabling reuse must be byte-identical to today's path. A new global pool, persistent worker or skipped final gate is outside this design.

## Required falsification tests before a private performance claim

These are proposed tests, not newly run evidence:

- Baseline unchanged capsules must yield identical fresh versus reused eligibility, exact proof JSON, native/final inventory, all diagnostic/persistence fields and every publication prefix. Cover every retained panel context plus explicit partial/exact-give cases; label the disclosed panel regression evidence, not a blind holdout.
- Mutate one dependency at a time: participant/league, ownership, roster, slot eligibility/count/capacity, inactive/injury status, age/position/team-pick marker, inferred-outlook `search_rank`/`pick_value`, selected/inferred plan, any board/source entry, unrelated full-universe player, full preferences, draft year/expiry/own-next list, fairness and exclusions. Each must miss the certificate and match ordinary re-evaluation behavior.
- Reorder give/receive arrays and requested pins, alter `exact_give`, change omitted partial pins or transplant a partial proof from another request. Preserve `_authenticated_partial`'s original request authority; set equality is not sufficient.
- Change actual card price/type, replace/deepcopy the proof, use a forged equal proof, mutate returned `as_dict` data, reuse a trade ID across requests/managers, change the generator while keeping the same arm, and change loaded tier/weight/helper identity. No unauthorized reuse may occur.
- Flip crown flag or effective configuration during generation, after generation and at validation; include an A→B→A sequence and concurrent jobs with different thread-local overrides. Mutate a nested Player/preference object while mapping identity is unchanged. A simple pre/post hash deliberately must fail these controls until a consistent-state mechanism exists.
- Update upstream DP seed/pick inputs versus refresh an irrelevant DP cache with unchanged captured inputs; distinguish actual owner dependencies from separate final freshness/ledger checks.
- Mutate a search-side cached record, create repeated occurrence aliases, mix fast-path and slow-path occurrences, and reverse evaluation order. Require exact agreement with current full-batch evaluation, including rejected/empty/error cases and original immutable proof retention.
- Force roster/significance/disposition failure, same-arm revision change, account revocation, supersession and evidence-write failure. A registry hit must not publish a card or impression that the existing pipeline would withhold.

Only after these pass under a separately approved private implementation should alternating matched full-worker runs measure whether certificate capture/checking actually costs less than repeated evaluation. No card cap, smaller search budget, thinner proof, skipped validation or changed durability boundary may manufacture the result. Current latency and quality release gates remain unchanged.
