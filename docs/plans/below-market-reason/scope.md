## 0. What changes, in one paragraph

The operator kept seeing Davante Adams as the give-side piece in trade after trade. His own board had Adams well below consensus; he read the repetition as "the app overrates him", while the engine's actual reasoning was "you rate him below the market, so he is your best currency" — which the operator, on reflection, agreed with. The model is right; the card never said WHY. One new `model_config` knob, **`reason_below_market_frac`** (default **0.0** = off), makes it say so: after every gate and every composite multiplier in the `_generate_trades_v2` per-member loop, when the give side's **headliner** (the C4b `deck_give_headliner` — the highest-seed give-side *player*; a pick never headlines a mixed give side and a picks-only give side never fires) is priced on the user's **shrunk** board (`_shrink_user_elo` output — the board the engine prices with) at least `frac` below his consensus value, `(seed_value − user_value) / seed_value ≥ frac`, the card gets one plain-English line in `TradeCard.reasons`: **`You rank {name} below the market — that gap is what this trade cashes in.`** (≤ 90 chars with a typical name; no line without a name). Both bases (divergence v2/v3 and consensus). **Presentation only:** nothing about which cards exist, how they score, or how they order moves at any knob value — property-tested. The line rides a field the wire already emits (`trade_card_to_dict`, gated on `trade_math.human_explanations`, **true in prod**) and both clients already render, so it reaches users on deploy with no client change.

## 1. Analytics scope

- [ ] **(a) New events specced:** none.
- [ ] **(b) Existing events cover it** — partially, and it is worth saying exactly how. `reasons` is **not** in the deck-outcome corpus: `features_json` at `backend/server.py:4498-4529` names its keys explicitly and `reasons` is not among them (checked 2026-09-02). So "did cards carrying the line get liked more" is **not directly answerable**. What IS logged per impression and identifies the population the line fires on: `user_value_basis` (`server.py:4528` — `"personal"` iff `ranked_player_count > 0`, i.e. the user has any board at all; a `"consensus"` user can never carry the line, §0), the give-side ids (`give` on the card row) and `ranked_player_count`. A like/pass split on "give headliner is below the user's market" therefore needs the user's shrunk board re-derived at analysis time from the give ids + the rankings tables — feasible, not a query on `features_json` alone. Adding `"below_market_reason": bool` to `features_json` is the one-line follow-up if the lead wants the corpus to carry it; it would touch the analytics surface and is out of scope here (same call the D-172 `consensus_fit` stamp made).
- [x] **(c) WAIVED — no NEW analytics needed because:** a presentation line on an existing wire field; no new event, no taxonomy or data-dictionary entry. The knob's live effect is bounded by the share-of-cards measurement in [results.md](results.md), which is what sets the live value.

## 2. Schema & flag scope

- New/changed tables or columns: **none**. `TradeCard.reasons` already exists (`trade_service.py:4353`); no new field, no new wire key (`reasons` is already emitted at `server.py:11886-11891`).
- New/changed feature flags: **none**. The line is doubly gated: the knob (0 = nothing stamped) and the existing `trade_math.human_explanations` flag on the wire (`config/features.json:28`, true). Either one alone kills it deploy-free.
- New env vars / `model_config` keys: **`reason_below_market_frac`** (float, default 0.0) → registered in **both** stores: `trade_service._DEFAULT_CFG` (`:574`, the block next to `need_fit_weight`) and `database._MODEL_CONFIG_DEFAULTS` (`:2436`, the row after `need_fit_weight`) — the DB seed is what makes `PUT /api/admin/config/reason_below_market_frac` reachable (`set_config` raises for an unseeded key). Documented in `docs/config-reference.md` § Trade engine v2 (Tier 1). **Ship-the-knob:** deploy at 0.0 → `GET /api/admin/config` shows `reason_below_market_frac: 0.0` → `PUT /api/admin/config/reason_below_market_frac` to the recommended value in [results.md](results.md) § Recommendation. **Rollback:** the same PUT back to `0` — deploy-free, and `POST /api/feature-flags/reload` with `trade_math.human_explanations: false` is a second, independent lever.
- **D-099 bake-off note (presentation, not engine):** the knob changes no deck output on any arm, so it is not an engine-affecting knob change and does not censor the window under D-099's rule as written. It IS a presentation change that lands on arms A, B and D (all three flow through `_generate_trades_v2`) and NOT on arm C (`trade_gen_v2`) or arm `fit` (`trade_gen_fit`), which build cards outside that loop and never carry the line. If C or `fit` is serving when the flip happens, their cards will be the only ones that cannot explain themselves — a presentation confound worth logging with the flip timestamp; today prod serves A/B/D (`bakeoff_include_gen_v2` / `bakeoff_serve_fit` dispositions in the phase-2 scope).
- **Injector asymmetry (pre-existing pattern, follow-up, not fixed here):** three server-side paths construct `TradeCard` directly and never pass through `_generate_trades_v2`, so their cards never reach the stamp — the likes-you injector (`server.py:3535`), standing-offer cards (`server.py:3650`) and the client-echo rebuild on swipe (`server.py:12717`). The same give headliner therefore explains itself on an organic card and not on an injected/rebuilt one. Same class as the arm-C/`fit` note above; every other post-generation stamp (`need_fit`, `lane`, `gap_sweetener`, …) already has this asymmetry.
- Bake-off disposition: **EXCLUDED** from `MODEL_A_PROFILE` (presentation-only; its default is the identity; a pin would only strip the line from arm A's served cards, making A the one served arm whose cards cannot explain themselves). Recorded in `backend/tests/test_bakeoff_arm_a_golden.py::_PINNED_KNOBS` (with the reasoning) and `docs/plans/three-model-bakeoff/scope-phase2.md`; `test_below_market_reason.py::test_arm_a_excludes_the_knob_and_the_drift_alarm_knows_it` pins the disposition.
