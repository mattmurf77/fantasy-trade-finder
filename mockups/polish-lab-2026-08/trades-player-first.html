Polish Lab · Player-First Trades? — is the specific-player page better than find-a-trade? (#211)

Operator note, verbatim (#211):

"I think the specific player trade page is better than the current find a trade page. No action needed as I'm interviewing some other testers first. So just a note."

No build requested — this lab is mockups only, exploring what "player-first" could mean if the tester interviews confirm the preference. Full code-level comparison and open questions: docs/feedback/items/211-player-first-trades/status.md.

The honest finding

Both pages are the same screen (TradesScreen) in a different finderMode (guided/team/player, switched in place by TradeFinderModeBar), sharing one pin store (useFinderTargets). Guided mode already has a targeting mechanism — a flat SEND/GET chip list buried under Outlook and Fairness in the Controls Card (TradesScreen.tsx:3537-3634). What's actually different is (1) player mode's two-column TRADE AWAY / TRADE FOR board leads instead of hiding behind other controls, and (2) it's a spatial, direct-manipulation board instead of a flat chip list. Once either mode reaches exactly one pin, they already converge on the same collapsed pin summary → Featured Trade window → idea list (#216/#209/#243, all shipped).

Interplay with #257

#257 (controls card → full edit sheet) is in flight this same release but not on origin/main as of this lab. None of the 3 directions below resurrect the old inline Outlook/Fairness/lane-filter card — wherever those controls are needed, the mocks route through a generic "Edit trade setup" entry (dashed box below) standing in for whatever #257 ships. The two-column pin board is treated as its own primary surface, not folded into that sheet — see status.md's open question on whether #257 should own it too.

2+ pins keeps today's existing behavior unchanged (multi-pin never triggers singlePin) — the deck stays, filtered/regenerated around the package, PackageToggle (#174) appears exactly as it does in today's Player mode. Nothing new to build here beyond making the board itself unconditional.
Notes — C3

Pro: no mode to choose wrong — one page, continuously as "player-first" as the user wants it, from 0 to N pins. Most faithfully resolves "the player page is better" without sacrificing the deck's zero-input case. Con: the biggest real change of the three — finderMode === 'player' currently gates the two-column board vs. the flat list (TradesScreen.tsx:3427); merging removes that condition and makes the board unconditional, which raises the open question of whether #257's edit sheet should own it too. Also flattens Team mode's distinct identity unless kept as an orthogonal filter rather than a mode (not mocked here — out of scope for this lab).

Recommendation

(c) is the most honest fix for what the operator responded to, but it should be sequenced behind #257 landing first — building the merge before the edit-sheet consolidation exists means re-deciding the inline-vs-sheet boundary twice. If something needs to ship before #257 lands, (b) is the safe interim step: cheapest, smallest surface area, reuses shipped mechanism end to end, and doesn't foreclose (c) later. (a) isn't recommended as a real change — it trades away the deck's core value prop for a single power-user's preference with no cohort read — but it's included because it's the cheapest possible mock of "what if we just believed the operator's note verbatim."
