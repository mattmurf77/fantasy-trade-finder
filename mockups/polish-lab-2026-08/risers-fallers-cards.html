"I like the risers and fallers cards and the concept of market driven rankings (plus risers and fallers). This feels like something that can be app wide and league specific. That was audited as a data-plumbing pass, not a UI build (see docs/business/product/2026-07-26-dynastygm-app-teardown.md, which surfaced the idea from a DynastyGM screen recording, and the readiness doc above). This mock is the UI half the operator explicitly deferred — it exists so a shape can be pre-approved now and built the moment the backing data has accumulated enough to be meaningful, without a design detour later.

Data framing — read this before the frames below: every number here is labeled "FTF community value," never "market consensus." The daily snapshot table (player_value_history) already exists and already records (cron-provisioned, #57/this readiness pass) — it's the cleanest source for a daily sparkline — but its consensus_value column is itself seeded from external DP+KTC blends, so calling it "the market" would overclaim what FTF observed. It's the same number the app already calls "Consensus" everywhere else (ConsensusVerdictCard, the "hasn't ranked yet — balanced trade by consensus value" copy) — this mock just uses the plainer word "community" for a card whose whole pitch is trustworthiness. The genuinely FTF-native alternative — aggregating real users' elo_history board edits — is real (writers cover every ranking flow since #164) but has no aggregation query built yet at all, app-wide or cross-league; see the data notes at the bottom.

Notes — D1

Data notes — what exists today vs what each variant needs

  • Exists and already recording: player_value_history — one row per universal-pool player per scoring format per UTC day (consensus_elo, consensus_value, search_rank, adp), written by the unflagged POST /api/cron/value-snapshot route, now reliably cron-provisioned (value-snapshot-daily in render.yaml) with an hourly-tick fallback guard so a missed day is nearly impossible. This is the cleanest source for all three variants' sparklines — daily granularity, no gaps, already used for the /api/rankings trend glyphs (FB4-61).
  • Also exists, different scope: elo_history — per-user personal Elo snapshots, written on every board-mutating action since #164 (trios, tiers, reorder, anchors). trends_service.compute_risers_fallers + GET /api/trends/risers-fallers already use it — but that endpoint answers "how has MY board moved," and only powers TrendsScreen in the Rank tab. It is the "genuinely FTF-native" alternative signal described in the framing note above, but nobody has written the aggregation-across-users query this mock's "FTF community value" language would need to justify itself fully; today's consensus_value trend is the honest fallback.
  • Missing — the read endpoint (all variants): no GET /api/market/risers-fallers exists. Per the readiness doc's §3a it's a pure read — join today's player_value_history rows against a baseline via the existing load_value_snapshot_baseline(scoring_format, days=N), rank by consensus_value or search_rank delta, take top-N each direction. No new writes, no schema change — this is the single blocking piece for V1 and D1.
  • Missing — league-specific variant (operator explicitly asked for this too): a different signal, described but not built in §3b of the readiness doc — aggregate leaguemates' elo_history rows for a league_id, average the per-user Elo delta over the window, gate on movement shared by ≥K members ("your league is warming up on X"). None of the three frames above show this variant; it would reuse V1's exact card shell with a source toggle ("App-wide" ↔ "Your league") and its own endpoint.
  • Missing — V2's tier-change chip specifically: tiers are derived live from current Elo via tier_config.json; nothing snapshots the tier label itself at each historical date, only the raw value. Computing "Tier 4 → Tier 2" needs re-running the tier-band lookup against the baseline-date value, a small but real addition beyond the plain delta V1/D1 need.
  • Missing — "tap → player context" (V1) / "Player context →" (V2) / "See all movers ›" (V3): there is no single-player detail screen anywhere in the app today. The closest primitives are PlayerContextMenu (a long-press action sheet for in-trade commands, not value history) and TrendsScreen (personal board only, wrong scope for a community/consensus number). Any of the three taps needs either a new lightweight destination or an extension of an existing screen — not assumed to exist, and not designed here.
  • Recommendation: build V1 first — it's the most literal match to the operator's own words ("risers and fallers cards"), the cheapest data lift (one read endpoint over data already accumulating), and mounts exactly where the operator's DynastyGM comparison pointed (the Explore-rows region). Ship V3 alongside it for near-zero extra cost once V1's endpoint exists — same data, and the operator's "app-wide" note makes a second lightweight mount worth having. Hold V2 — the extra tier-diff field plus the still-missing player-context destination make it the most expensive of the three for a feature the operator already called "not a big value-add for now."
