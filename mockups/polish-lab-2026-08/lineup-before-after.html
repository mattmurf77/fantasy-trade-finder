Polish Lab · Lineup Before/After — trade-summary addition (#238)

Operator ask (verbatim):

"Adding a visual of a user's starting lineup before/after a trade is a valuable tool to the trade summary. Let's mock up that addition."

Grounded in a real, already-shipped backend field: POST /api/trade/evaluate (Mode B, In-league) returns starter_impact: {your_delta, their_delta, note} via backend/server.py _starter_impact(), which fills the league's roster slots with each side's highest-value eligible players via backend/power_rankings.py optimal_starters() — before and after the trade — and diffs the totals. Today that field carries one summary sentence only; it does not name which slot changed or who filled it. The variants below explore how much slot-level detail to add and where the module mounts. Trade example used throughout is internally consistent: the lineup totals are computed the same way optimal_starters() would (best value fills QB / RB / RB / WR / WR / TE / FLEX), so every delta shown ties back to real player values, not arbitrary numbers.

Example trade: you send James Cook (RB) + a 2026 4th, you receive Jaylen Waddle (WR). Cook's roster spot is backfilled by bench RB Tyjae Spears; Waddle outvalues incumbent WR2 DeVonta Smith, who slides down into FLEX ahead of Tony Pollard. Net effect: RB2 gets weaker (−325), WR2 and FLEX both get stronger (+285, +330) — starting lineup total 5,422 → 5,712 (+290), even though the raw trade-value edge is a modest +123.

Notes — D1

Data notes — what exists today vs what this needs

  • Exists today: starter_impact is computed and served ONLY by POST /api/trade/evaluate in Mode B (In-league calculator) — it needs two known rosters (caller + opponent) and the league's Sleeper roster-slot template (_sleeper_lineup_slots); see backend/server.py around lines 991–1050 and the call site at ~line 7305. The payload is currently just {your_delta, their_delta, note} — a single sentence, no per-slot names. That sentence is already live at calc.starter-impact in InLeagueCalculator.tsx (line 878) — frame A2 above is not hypothetical, it's what ships right now.
  • Missing for V1/V2/D1's per-slot detail (any mount): optimal_starters() in backend/power_rankings.py (line 50) returns a flat list of starter player IDs — it fills slots in order internally but discards WHICH slot each starter landed in before returning. Showing "RB2: Cook → Spears" needs that function (or a wrapper) to return {slot, player_id} pairs instead, computed before AND after the trade, then diffed by slot position. This is new backend work, not just new UI.
  • Missing entirely for the deck/featured trade window: checked mobile/src/shared/types.ts (the TradeCard interface, ~line 111) — it has no starter_impact field, and neither /api/trades/generate nor the asset-ideas endpoint that feeds FeaturedTradeWindow computes it. Mode B's on-demand evaluate call is fine for one calculator submission; computing full before/after optimal lineups for every card in a generated deck (tens of cards per sweep) is a materially different cost and would need its own perf pass before it ships there. Frames A1, B1 and D1 above are illustrative of the target design — they are not describing an existing capability.
  • Recommended sequencing: ship the slot-labeled backend change once (extend _starter_impact/optimal_starters), land it in the calculator first (V1 or V2 — cheapest integration, reuses the existing Mode B call), then evaluate the deck/featured-window cost separately before committing to V3 there.
