Acquire landing — does the hub page earn its place? (#246)

Operator question, verbatim:

"I'm wondering whether this page even makes sense or whether we should just land the user in the guided flow by default with ways to navigate to the other trade (and FA) pages."

What this lab is designed against

Not today's TradeFinderHubScreen in isolation — against the #245 future, where the tab is renamed Acquire and the hub grows a TRADE section (the four mode cards) plus a FREE AGENCY section (one row, finder-hub.card.free-agents → root-stack FreeAgents; the same destination the League tab's Explore tile and the deck's own trades.explore.free-agents row already reach). #245 is a presentation-level rename — tab.trades and the route name Trades are unchanged, only the label and the hub's in-page title ("Find a Trade" → "Acquire"). Frame A1 is that page, as shipped.

Two related operator signals inform the read: #211 — "the specific player trade page is better than the current find a trade page" (a vote for the focused surfaces over the launcher) — and the whole #243 scroll audit, whose top lever was making the newest focused surface (single-pin) start showing its trade above the fold. Both point the same way: value lives on the mode surfaces, not on the chooser.

Method

Real 393×852pt frames; usable content viewport 658pt (852 − 59 top inset − 52 TopBar − 49 tab bar − 34 bottom inset), same arithmetic as the #218 hub pass and the #243 audit. Fold lines and per-block pt chips are measured live by JS from this file's own DOM, not hand-typed. Each frame also carries a hand-derived taps-to-first-trade meter — the metric this question actually turns on. The green-bordered chip marks the first block on the screen that contains an actual trade; the hub has none, which is the whole argument.

Notes — D2
D3 — what V3 actually needs to exist

New persisted state

  • acquire.hub_seen — bool, per account (acct_ key), not per device: otherwise a second device re-educates and a reinstall re-educates. AsyncStorage alone is wrong here; this wants the same server-side prefs row the DNA uses, or it silently misbehaves across devices.
  • acquire.last_mode — must be scoped per league, not global. "Specific Team" restores a scope (opponentUserId) that doesn't exist in another league; a global key lands a league switch on a mode pointed at a stranger.
  • Player mode has nothing to restore. Pins live in useFinderTargets, session-local and cleared on league switch by design. Restoring "Player" after a switch = landing on an empty pin board, which is a worse landing than the hub. Either pins become persisted state (new work, new invalidation rules) or Player silently degrades to Guided — and a landing that silently isn't what you asked for is the exact failure mode remembered landings are notorious for.
  • Calc can't be a restore target at all: TradeCalculator is a separate pushed route, not a TradeDeck mode. Restoring it means the tab opens on a pushed screen — back-gesture semantics get weird and calc.find-a-trade (#213) would point back at itself.

New failure surface

  • Three landing states (first-ever / restored / degraded-fallback) × 4 modes × league-switch and cold-start crossings. Today's answer is one state. QA can't see state 1 without clearing storage, so it regresses invisibly.
  • The hub page survives — with all its code, its testIDs, its density budget and its future maintenance — for a screen each user sees once. That is the worst cost/benefit ratio of any option here.

What it would take to justify

  • Evidence that mode choice is stable per user and varies between users. That's a user_events question (mode-open counts per account) and it is currently unmeasured. If 80% of sessions are Guided, V3 is elaborate machinery for a constant.

Recommendation — ship V1, borrow one thing from V2

Yes: delete the hub and land the tab in the guided deck (V1), with the mode chips as a persistent strip and Free Agency as a titled section at the tail of the page. Add one V2 idea: make the mode strip's overflow — a "What are these?" affordance, or simply the first-run state keeping the hint line — carry the explanatory copy the chips can't, so nothing that was educational about the hub is actually lost. Do not build V3 yet.

Why. The hub isn't badly designed — #218 made it fit, #212 made its DNA panel sharp — it's structurally unearned: it is a full screen of the app's primary tab that contains no trades, and its own #156 design notes already concede the point by shipping a mode-chip row on every destination "so the one-extra-tap cost of the launcher hub disappears in practice." If the chips are good enough to carry mode switching everywhere else, they're good enough to carry it on arrival, and then the launcher has no remaining job. The three things the hub genuinely owns all have better homes: mode switching → the chip strip that already exists and works; Trade DNA → a sheet over the deck, reached by the "Change" link the deck already renders, where #236's autosave lets the user watch their bias change the trades behind the sheet instead of tabbing back and forth; free agency → a titled section at the page tail, which is both #245's own structure and the shipped trades.explore.free-agents row with a header on it. Guided is the right default because it is the only mode that produces a trade from zero input — Team needs an opponent, Player needs a pin, Calc needs a package — so it is also the only mode that makes cold start better rather than worse; and #211's preference for the Player surface is served by making it one chip away rather than one screen and one card away. I'd hold V3 not because remembered landings are wrong but because this one is unaffordable right now: it keeps the hub alive for a screen seen once, needs account-scoped and league-scoped new state, and its most attractive case (restore Player mode) lands on an empty pin board after any league switch, because pins are deliberately session-local. If mode-open events later show real per-user variance, V3 is a small addition on top of V1 — the chip strip is already the switcher it needs — which is another reason to build V1 first and let the data decide the rest.
