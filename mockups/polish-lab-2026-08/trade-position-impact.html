"But it's also nice if this is a bit objective and says hey you are a contender and only have 10 ppg in your TE position and we found a way to get that to 17 in your starting lineup etc. This ups your championship odds to X … This trade makes your playoff / champion odds in 2026 at ? 2027 @ _ 2028 @ _"

Operator review of the first pass (A1 fold-in / B1 standalone strip / C1 deck hook) — verbatim directives:

B1: "Nope. Abandon."  ·  A1: "Should be from TE x to TE x OR from Tier x to Tier x. Mock up both versions."  ·  C1: "Same feedback as A. Mock up both versions."

What changed in this pass: B1 is removed — the standalone "Why this trade" strip frame and its writeup are gone, folded value narration stays inside the shipped #238 table (A) or the deck hook (C) only, never a new mounted module. A1 and C1 are each split into two framings in place of the single raw-value sentence they shipped before ("your TE value goes 380 → 810"): a positional-rank version ("TE21 → TE4") and a tier version using the real shipped 8-tier pick-value ladder labels (docs/cross-client-invariants.md — "FA / 4th / 3rd / 2nd / 1 1st / 2 1sts / 3 1sts / 4+ 1sts", not invented "Tier N" numerals). This is a UX-framing decision, distinct from the ppg-data-availability question below: raw dynasty value ("380 → 810") was and still is computable with zero new backend, the operator just doesn't want that unit shown to users — rank and tier are the two alternatives worth mocking.

Grounded in the shipped #238 lineup before/after table (mockups/polish-lab-2026-08/lineup-before-after.html frame C1 → InLeagueCalculator.tsx's LineupImpactTable, live since 2026-08-03). That table returns, per starting slot, {slot, before:{name,position,value}, after:{...}, delta} from POST /api/trade/evaluate Mode B's _starter_impact() (backend/server.py). Neither tier nor positional rank is on that payload today, so — unlike the old raw-value sentence, which really was zero-backend client arithmetic — both new framings need one small additive change to _starter_impact()'s slot_entry() builder: attach a tier field (walked off the raw seed Elo via RankingService.tier_for_elo — the exact call the route already makes elsewhere in this same function for evener rows, #277's _evener_tier closure) and/or a positional-rank index (sort the route's already-loaded _pool_players by position + value once, look up each slot player's index). Both read data the route already has in memory — no new endpoint, no new network call, no schema change, no new data source — but they are not literally zero-code the way the raw-value delta was. See the data-notes block at the bottom for the full audit, including why points-per-game framing ("TE: 10.2 → 17.1 ppg") remains not computable at all — the app has no fantasy-points data source anywhere — that gap is unrelated to and unaffected by the rank-vs-tier framing choice.

Example trade used in every variant below (a cleaner story for position framing than #238's Cook/Waddle example, which touched three slots at once): you send Rome Odunze (WR, bench — not a starter) + a 2026 4th, you receive Sam LaPorta (TE). Your incumbent starting TE, Cade Otton, gets benched; every other starting slot is untouched. Starting-lineup total moves 5,650 → 6,080 (+430), entirely from the TE slot — the trade's whole lineup impact is legible as "your TE spot." Illustrative positional-rank and tier numbers for the two players: Otton ≈ dynasty TE21, tier 4th (fringe-starter/waiver-adjacent); LaPorta ≈ dynasty TE4, tier 1 1st (true top-of-position asset).

Data-availability audit — computable today vs. needs new work

  • Rank and tier framing (used in A1a/C1a and A1b/C1b's COMPUTABLE TODAY lines): both derive from data the app already computes and serves — no new data source, no schema change, no new route. Tier is walked off a player's raw seed Elo via RankingService.tier_for_elo(elo, position, format) — the identical call already made inside this exact function for evener rows (backend/server.py, #277's _evener_tier closure). Positional rank is a 1-based index into GET /api/trade/values' pool, sorted and filtered to one position — the same pool _starter_impact() already has loaded in memory as _pool_players. Neither field is on the evaluate payload's starter_impact.slots rows today, though — unlike the old raw-value delta (which really was zero-backend client arithmetic over an already-shipped field), both need one small additive change to _starter_impact()'s slot_entry() builder in backend/server.py. Tier is the cheaper of the two: it reuses an existing call verbatim; rank needs a new sort/index step with no precedent elsewhere in the codebase for this purpose.
  • Raw dynasty-value framing ("TE: 380 → 810 value") — still literally computable with zero backend changes, but out of scope per operator review: the per-slot {position, value} before/after breakdown is already on POST /api/trade/evaluate Mode B's response (_starter_impact() → backend/power_rankings.py optimal_starter_slots(), shipped 2026-08-03, #238). This was the framing in the original A1/B1/C1 pass; the operator's review directed rank/tier framing instead, so it no longer appears in any frame above. Recorded here only so the data-availability picture stays complete — this is a UX-framing call, not a capability gap.
  • Computable today, but needs light integration (not built into any variant above, flagged here for completeness): "your TE is below the league average / your weakest position" needs a second, already-live endpoint — GET /api/league/power-rankings (backend/power_rankings.py compute_power_rankings()) returns every team's positions: {QB|RB|WR|TE: {count, value}}. Joining that with the evaluate call's starter_impact.slots gives a real "weakest starting position vs. the league" claim — no new computation, but it is a second network call the trade-summary flow doesn't currently make, and reconciling whole-roster positions_value against a single STARTING slot's value needs a defined comparison (starters-only vs. full roster are different denominators). Worth a scope block if pursued.
  • NOT computable today, needs new backend work (flagged NEEDS NEW DATA everywhere it appears): points-per-game framing ("TE: 10.2 → 17.1 ppg"), the operator's original literal phrasing. git grep -n "ppg\|points_per_game\|per_game" backend/*.py returns nothing outside test files — the app has no fantasy-scoring data source anywhere. The one place weekly points DO exist is backend/outlook/ (dark behind the unwired outlook.odds flag): league_state.py pulls real Sleeper matchup points_for/points_against, and strength.py's RosterValueStrength provider maps a team's TOTAL roster value to a WHOLE-TEAM weekly-points estimate via a documented, unvalidated heuristic (mu = 110 + 12 × z(starting_lineup_value)). Neither is position-level — there is no per-slot or per-position points model anywhere in the codebase, real or heuristic. Building "TE ppg before/after" would mean inventing a new position-level scoring model from scratch (own projections, or an nflverse-style per-position points source), which is a real backend research/design effort, not a mockup follow-on. This gap is orthogonal to the rank-vs-tier framing question — it was never in play as a build option for this pass.
  • Deck/featured-card mounting (Variant C) is its own gap, independent of framing: neither C1a's rank nor C1b's tier reaches the deck today. starter_impact is computed on-demand for one Mode-B evaluate call; the deck generates many candidate cards per sweep and would need per-card optimal-lineup computation (plus, for these framings, a rank or tier lookup on top) at deck-generation cost — the same "phase 2" gap #238's status doc already called out for its own before/after table. Both C1a and C1b above are layout illustrations only.
  • Recommendation — tier framing over positional rank: ship A1b (tier) first if/when Variant A moves off mockup. Three reasons. (1) Cheaper, more precedented build: tier reuses an existing call in this exact function (#277's _evener_tier pattern) verbatim; positional rank needs a new sort/index step nothing else in the codebase does yet. (2) Vocabulary the app already teaches: the 8-tier pick-value ladder is the mental model the Pick Anchor wizard, every TierBadge chip, and the tier-consolidation work elsewhere in this same polish batch (#277, `trades-home-inline.html`) already train the user on — tier framing extends a concept the user has seen, rank framing introduces a second one. (3) Less noisy: a tier only changes when a player crosses a real qualitative threshold on the ladder; a positional-rank number can swing by several slots on small value wobbles near a crowded position band, which risks reading as jittery or inconsistent week to week. Positional rank's own case is real — "TE12" reads instantly to anyone who's used KTC/FantasyCalc/Sleeper's own rankings, and it's more granular than an 8-bucket ladder — so it's the fallback if user testing shows the tier chips read as too coarse or unfamiliar outside this app. Either way: leave the deck mount (Variant C) and PPG framing out of the near-term build; both need dedicated scope blocks (deck-scale lineup computation; a new points-per-game data source) before any code gets written.
