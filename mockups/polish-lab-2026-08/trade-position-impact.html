Notes — C1

Data-availability audit — computable today vs. needs new work

  • Ships today, zero new backend (used in A1 and B1's SHIPS TODAY line): the per-slot {position, value} before/after breakdown already returned by POST /api/trade/evaluate Mode B (backend/server.py _starter_impact() → backend/power_rankings.py optimal_starter_slots(), shipped 2026-08-03, #238). "Biggest single-slot mover" is a client-side max(abs(delta)) over an array the client already receives — no new route, no new field, no schema change. This is the only tier the required fold-in (Variant A) needs.
  • Computable today, but needs light integration (not built into any variant above, flagged here for completeness): "your TE is below the league average / your weakest position" needs a second, already-live endpoint — GET /api/league/power-rankings (backend/power_rankings.py compute_power_rankings()) returns every team's positions: {QB|RB|WR|TE: {count, value}}. Joining that with the evaluate call's starter_impact.slots gives a real "weakest starting position vs. the league" claim — no new computation, but it is a second network call the trade-summary flow doesn't currently make, and reconciling whole-roster positions_value against a single STARTING slot's value needs a defined comparison (starters-only vs. full roster are different denominators). Worth a scope block if pursued.
  • NOT computable today, needs new backend work (flagged NEEDS NEW DATA everywhere it appears): points-per-game framing ("TE: 10.2 → 17.1 ppg"). git grep -n "ppg\|points_per_game\|per_game" backend/*.py returns nothing outside test files — the app has no fantasy-scoring data source anywhere. The one place weekly points DO exist is backend/outlook/ (dark behind the unwired outlook.odds flag): league_state.py pulls real Sleeper matchup points_for/points_against, and strength.py's RosterValueStrength provider maps a team's TOTAL roster value to a WHOLE-TEAM weekly-points estimate via a documented, unvalidated heuristic (mu = 110 + 12 × z(starting_lineup_value)). Neither is position-level — there is no per-slot or per-position points model anywhere in the codebase, real or heuristic. Building "TE ppg before/after" would mean inventing a new position-level scoring model from scratch (own projections, or an nflverse-style per-position points source), which is a real backend research/design effort, not a mockup follow-on.
  • Deck/featured-card mounting (Variant C) is its own gap, independent of PPG vs. value: even the value-based framing that A1/B1 ship today doesn't reach the deck. starter_impact is computed on-demand for one Mode-B evaluate call; the deck generates many candidate cards per sweep and would need per-card optimal-lineup computation at deck-generation cost — the same "phase 2" gap #238's status doc already called out for its own before/after table. Variant C above is a layout illustration only.
  • Recommendation: ship Variant A (required fold-in) first — it's additive to an already-shipped payload, one new client-side line, no backend PR. Variant B is the same data with a heavier mount; pick it only if the operator wants the headline to lead the card rather than live inside the lineup table. Leave PPG framing and the deck mount out of the near-term build; both need dedicated scope blocks (new points-per-game data source; deck-scale lineup computation) before any code gets written.
