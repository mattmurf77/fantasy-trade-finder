Settings IA — hub page + second-level pages

The question: the shipped Settings screen is one modal sheet holding ~25 controls across 7 sections. Can it become a top-level hub plus second-level pages — and a real pushed page instead of a half sheet — without making anyone hunt for a setting they used to be able to see?

Plan: docs/plans/settings-ia-hub/plan.md · Scope: docs/plans/settings-ia-hub/scope.md

Operator decisions, 2026-08-18 — these bind the frames below:

  • Sign out moves to the Account page, not the hub. Placed under the identity block; Delete account stays last, at the opposite end of the page.
  • Ranking and Trade values stay two pages, grouped under one hub banner.
  • account.settings_v2 retires in Phase 4, same wave.

What the hub is doing, row by row

1Identity block, not a nav row. Who you are, whether you're verified, and a tap through to Account. The verification chip is warn-bordered while unverified — the state the capture actually shows.
2Group banners are TickLabels (3px ice bar + Archivo 600 11 UPPER), the same primitive the shipped screen uses for section headers. Ranking and Trade values sit under one banner so they read as related without being merged into one page.
3Nav-row title is 16px sentence case (type.title), not the 11px uppercase type.label that shipped rows use for their key. With a 13px preview underneath, a label-styled title would be smaller than its own subtitle. This is a new construction and needs a spec row in docs/design/components.md § Navigation before it ships — flagged in the plan, not decided here.
4"Not chosen yet" is rendered faint and italic — the honest-empty case. Plan rule: a preview that isn't known for free isn't rendered at all. A settings page that lies about a setting is worse than one that says nothing.
BTrade values has no preview — and that is the rule working. This frame originally read "Stud tax: Market · Picks: Tier ladder". It was drawn from the app's defaults, not from the user's stored setting: stud tax and pick pricing are fetched by bare effects with no React Query key, so on a cold hub open there is nothing free to read. Printing the default as if it were the user's choice is exactly the lie rule 4 forbids, so the built hub renders title + chevron only. Corrected here after the build caught it.
5Nothing below the last row. Sign out lives on Account now (operator decision), so the hub is purely navigational and fits one screen with no scroll — the first time Settings has.

Cost of the previews: zero network. Leagues and Ranking read the session store; Trade values and Notifications read the React Query cache if it's already resident; version comes from expo-constants. Opening Settings goes from six queries plus two fetches to none.

Back chevron at the left using the existing HeaderBack (RootNav.tsx:168) — the #151 pattern, needed because the native back control is dead on iOS 26 when the previous screen runs headerShown: false, which Main does. What the push buys, beyond looking right

1The nav hack goes away. Every outbound link today calls goBack() then navigate(), because pushing onto a modal stack strands the user. Cost: back from Verify account lands on the tabs, not on Settings. On a pushed page it's a plain navigate and the back stack works.
2Feedback becomes possible. #188 exempts modals from mounting FeedbackFAB, so Settings is one of the only surfaces where a tester can't file in place. Pushed pages aren't exempt.
3Deep links get a destination. ux.deeplink_router_v2 is on in prod; settings/notifications can open a real page with a real parent instead of a modal with none.
!The one regression risk. Testers on the shipped build dismiss Settings by swiping down. A pushed page swipes right. That's a learned gesture and it's item 1 on the TestFlight checklist.

#130 is not being reverted. The ✕ was a real fix for a real complaint about an undiscoverable exit; the plan removes the presentation that caused it, and records that in DECISIONS.md so a later session doesn't re-add a modal citing #130.
