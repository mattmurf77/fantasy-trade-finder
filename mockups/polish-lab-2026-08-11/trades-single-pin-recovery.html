Single-pin trade surface — #298 (repro) · #297 (not a regression)

#298 (TradesHome, bug): "The UI when selecting a team or player is regressing. All versions should still have the find a trade UI and let the user accept / decline the trades as any other suggested trade."

#297 (TradesHome, bug): "The summary of a trade seems to have regressed. The lineup change feature that shows the players traded and the impact on starting lineup doesn't appear anymore."

Both filed 2026-08-10 against shipped v1.12.0. They land on the same surface — the single-pin featured-trade view on TradesHome — which is why they share a page. Their causes are unrelated, and neither is what the reports (or the pre-briefed leads) say it is.

#298 — reproduces, but the experiment is not the cause

The lead pointed at the trades_home_inline experiment (TradesScreen.tsx:468-481), on the theory that the operator's strip variant rebuilt this surface. It did not. showInlineHome (:507) only swaps TradeFinderModeBar for TradeHomeUtilityRow and mounts TradingWithStrip (:3436-3479) — both branches render inside the same {finderMode ? … : null}, and neither touches the deck or the CTA. TradeBuildCanvas is canvas-only and explicitly additive.

The actual cause is two singlePin null-gates that fire identically in the control group. singlePin is true when exactly one asset is pinned (TradesScreen.tsx:1038-1045). Both of these read {!firstRun && singlePin ? null : (…)}:
  • TradesScreen.tsx:4232 — removes the Find a Trade button (testID="trades.find-btn").
  • TradesScreen.tsx:4569 — removes the entire deck wrapper, and with it every accept/decline path: the swipe handlers (SwipableTopCard onLike/onPass, :4641-4642), the trades.pass-btn / trades.like-btn row (:4734-4767), and the VoiceOver actions (:5426-5433). All of them funnel into advance('like'|'pass') at :2979.
What replaces them (:4314-4340) is FeaturedTradeWindow + AssetIdeasPanel. With trades.player_offers_calc on (config/features.json:186) the featured window renders an InLeagueCalculator, whose only actions are Send in Sleeper and Clear trade. AssetIdeasPanel has zero accept/decline affordances. That is the reporter's sentence, verbatim, in code.

Reverting the experiment will not fix this. Pin one player in the control group and the same thing happens.

#298, second half — the team path has a different bug

Selecting a team via the strip's "Trading with" pill calls pickSheetOpponent (:618-623, reached from :653-656), which changes scopedOpponent and fires the effect at :1918-1926. That effect calls resetDeckForNewTargets() — setDeck([]); setJob(null) — but only auto-regenerates when finderMode === 'team'. The strip keeps the user in 'guided'. So picking a team silently empties the deck and regenerates nothing, dropping the user to "Hit "Find a Trade" to start" (:4913). The "Preferences changed — tap to refresh" strip can't rescue it: it is only set in handleEditSheetClose (:567-580), which this path never calls. Here the strip variant is implicated — not as the cause, but because it puts a pre-existing footgun one tap from the deck.

#297 — not a regression. It was never on this surface.

LineupImpactTable is defined at mobile/src/components/InLeagueCalculator.tsx:999 and is not exported — the file's only export is the default InLeagueCalculator. It has exactly one render site, the guard at InLeagueCalculator.tsx:947-953. There are zero occurrences of LineupImpactTable, starter_impact or any lineup string in TradesScreen.tsx, TradeCard.tsx, AssetIdeasPanel.tsx, web/ or extension/.

git log -S "LineupImpactTable" and -S "starter_impact" return only additive commits — c5f6f9c created the table for the calculator on 2026-08-03, 29a25c0 extended it for #169 on 2026-08-09. Nothing was ever deleted, and there was never a mount on the deck or on a read-only trade card. #238's own record says so: "Out of scope (phase 2) — Deck/featured TradeCard mounts: /api/trades/generate and the asset-ideas endpoint don't compute starter_impact…"

Most likely what the operator actually saw. The table is reachable from TradesHome today — via the featured window's calculator. But _starter_impact returns None when there is no Sleeper lineup template: backend/server.py:1152-1154 bails on _sleeper_lineup_slots(league_id), and that helper (:19058-19079) returns None for any non-numeric league id — ESPN, MFL, Fleaflicker, demo. v1.12.0 is the build that shipped MFL support. On a non-Sleeper league the field is simply absent and the guard at InLeagueCalculator.tsx:953 renders null — silently, with no copy at all. A feature that vanishes without a word is indistinguishable from a regression. That silence is the real defect in #297, and it is cheap to fix.

Two lesser possibilities worth ruling out with the operator: the featured-window calculator requires exactly one pin (going to zero or two removes it), and the TradeBuildCanvas mount is canvas-variant only — if the experiment moved the operator from canvas to strip, that calculator (and its table) would genuinely disappear from TradesHome with no code change.

The cheap fix — and it may be the whole of #297

Before any deck work, close the silence. Today the third branch of InLeagueCalculator.tsx:947-953 renders null: the section simply isn't there, with nothing to explain why. One honest row turns a phantom regression into a known limitation:

Starting lineup
Lineup impact needs a Sleeper league — this league is on MFL, so FTF can't read its starting-slot template.

Copy is illustrative; the platform name comes from data the client already has. If the operator's league turns out to be Sleeper after all, this row still costs nothing and the investigation moves to the singlePin / experiment-assignment possibilities above.

If the operator does want it on the deck (true phase 2)

  1. Batch the computation. _starter_impact is a single-trade, on-demand call that runs optimal_starters twice per side and needs _pool_players plus both rosters. The deck generates many candidates per opponent per sweep. Hoist _sleeper_lineup_slots and the roster fetch out of the loop and memoize the caller's "before" lineup once per sweep — it is constant across every card. This is the perf pass #238 explicitly deferred.
  2. Serialize it in trade_card_to_dict (server.py:9352) so it survives into _public_job's cards, and mirror it in /api/trades/asset-ideas if the idea rows should carry it too. Updates docs/api-reference.md.
  3. Flag it — new gate (e.g. trade.deck_lineup_impact), four touches per convention: backend/feature_flags.py, config/features.json, backend/tests/fixtures/flags/release.json, docs/config-reference.md.
  4. Client. LineupImpactTable is local and unexported and closes over module-local styles, slotShortLabel, posRankLabel and SLOT_SHORT — lift it into its own component file, add starter_impact to the TradeCard type in mobile/src/shared/types.ts, then mount it.
  5. Prefer the one-line hook on deck cards. #169's approved lab (mockups/polish-lab-2026-08/trade-position-impact.html) already recommends a single-line tier framing ("TE: 4th → 1 1st") for card real estate rather than the full 7-slot table. The V1 frame above uses a 2-row changed-slots-only variant, which is the same argument applied to the featured window's larger surface.

This is a schema + API-contract + flag change, so by the CLAUDE.md bright line it is not a "quick fix" and cannot go express without an explicit confirming yes from the operator.
